# Account networking audit

## Summary

- **Mode:** C, a targeted audit of the account networking area.
- **Scope:** `AccountRepository.swift`. It is the only file I was given. `APIClient`, `Account`, the screens that call the repository and the backend are not in the fixture.
- **How I checked it:** static code review against the networking and data/state checklist. I had no device, no backend, no oracle request and no git history, so the backend side of each finding is marked **Suspected** until someone confirms it with the questions below.
- **Result:** I found one High problem and one Medium problem. The High one is that the read (`refresh`) is sent as a write (`PUT`). Fixing it is a one-word change on the app side, but you need to confirm `GET /accounts/{id}` exists first.

## Findings

### F1 [High] Account "refresh" is sent as a `PUT` with no body: a write used as a read
- **Status:** Verified in code. The server-side effect is Suspected.
- **Where:** `AccountRepository.swift:7` (`PUT /accounts/{id}`, `body: nil`)
- **What the user sees:** Depending on how the backend handles a `PUT` with an empty body, one of these can happen:
  - the profile fields are wiped or reset every time the account screen opens;
  - users without write permission get an error instead of their account;
  - "last modified" and audit data change even though the user did nothing.
- **Cause:** `refresh` should fetch data, but it calls `api.request(method: "PUT", …, body: nil)`. `PUT` means "replace this resource with the body you send", and here the body is empty. It is the same method and path that `save` uses on line 11.
- **Trigger:** This runs on **every launch and every time the account screen appears** (doc comment, line 5), so it happens all the time for every user. There is no special condition.
- **Possible consequences** (which ones happen depends on the backend, so confirm them there):
  1. **Data loss:** a strict `PUT` with an empty body sets the account's fields to null or defaults. If that happens, the user's profile is silently erased on every app open. That would be **Critical**.
  2. **Needs write permission:** read-only or limited tokens, and roles or a gateway that only allow `GET`, get 401, 403 or 405. The account screen then fails or logs the user out.
  3. **Side effects:** `updated_at`, ETags, audit logs, webhooks, "profile changed" emails or sync events fire on every screen view. That data becomes useless and can cause load or spam.
  4. **Concurrency:** two devices, or a refresh and a save, both write the same row. A write by the refresh can overwrite the other device's newer save (this ties in with F2).
  5. **Caching and retries:** a `PUT` response is never cached by `URLCache`, a CDN or a proxy, so it is always a full round trip. Retry middleware also treats it as a write.
- **Evidence:** lines 5-8 of the file. The method is hard-coded as `"PUT"` and the body is `nil`.
- **Impact map:**

| Axis | Cell | Expected | Current |
|---|---|---|---|
| Consumers | App launch refresh | Read only, no server change | Write (fails) |
| Consumers | Account screen on appear | Read only | Write (fails) |
| Consumers | Any other caller of `refresh` (widgets, pull-to-refresh, push handling) | Read only | Not visible in fixture: not tested |
| States | Normal user token | 200, account unchanged | Suspected: account unchanged only if the backend ignores an empty `PUT` |
| States | Read-only / limited / expired-scope token | 200 | Suspected: 403/405 |
| States | Offline / timeout | Clear error, cached data kept | Not tested: `APIClient` not in fixture |
| States | Save in flight, then refresh | Saved value kept | Fails, see F2 |
| States | Same account on 2 devices | Each device's save kept | Suspected: refresh-write can collide |
| Platforms / siblings | Android / other apps on the same endpoint | Read is a `GET` | Not tested: not in fixture |
| Data source | Backend behaviour of `PUT` with empty body | Rejected (400) or no-op | Unknown: ask the backend owner |

- **Fix** (smallest change, nothing visible changes in the UI):

```diff
--- a/AccountRepository.swift
+++ b/AccountRepository.swift
@@
     /// Called on launch and every time the account screen appears.
     func refresh(accountId: Int, completion: @escaping (Result<Account, Error>) -> Void) {
-        api.request(method: "PUT", path: "/accounts/\(accountId)", body: nil, completion: completion)
+        api.request(method: "GET", path: "/accounts/\(accountId)", body: nil, completion: completion)
     }
```

- **Review gate:**
  - Does it drop or hide any user value? No. It stops the app from writing data the user never asked to write.
  - What does an empty value mean to every consumer? An empty body on `GET` is normal and means nothing.
  - Which impact map cells change? Launch and account-screen refresh become real reads. Read-only tokens should start working.
  - Does it need the backend? Yes. **Before merging, confirm that `GET /accounts/{id}` exists** and returns the same `Account` shape. If only `PUT` exists today, the backend owner must add `GET` first. Shipping the app change alone would break the refresh.
  - The backend should also reject a `PUT` with an empty body (400). Old app builds will keep sending it until users update.
- **Test:** add a unit test with a stub `APIClient` that records the method. Assert that `refresh` sends `GET` and `save` sends `PUT` with a non-nil body. Against the current code, the test fails on `refresh`. Then do a manual check with a proxy (Charles or Proxyman): open the account screen 3 times and check that only `GET` requests appear and that `updated_at` on the server does not change.
- **Also in:** Android, other sibling apps and any web client that uses this endpoint. Grep for `PUT` or `POST` used on fetch, load or refresh paths across the codebase. This file shows the pattern, so it may exist elsewhere.
- **Delivery:**
  1. The backend confirms or adds `GET`.
  2. The app ships a new build on both platforms.
  3. The backend hardens empty `PUT` requests, because old builds stay installed.
  4. If F1.1 (data loss) is confirmed, the backend owner checks the audit history for accounts that were wiped and restores them from backups. That part needs its own owner.

### F2 [Medium] Refresh on appear can overwrite a save that is in flight
- **Status:** Suspected. The callers and `APIClient` are not in the fixture, but nothing in this class prevents it.
- **Where:** `AccountRepository.swift:6-12`
- **What the user sees:** The user edits the profile and taps Save. They leave the screen and come back while the save is still in flight, or the app relaunches during the save. The old values come back. The user may then re-save stale data on top of the change.
- **Cause:** `refresh` and `save` run independently, and both deliver an `Account` to the caller. Nothing orders the responses or marks a refresh as older than a pending save. Whichever response arrives last wins. Because of F1, today both requests are also writes to the same row, so the server-side outcome is order-dependent too.
- **Trigger:** A slow network and a save in flight when the account screen appears again (or the app launches). The completion order is: save response first, then the refresh response that was started earlier or carries the older state.
- **Fix (proposal, needs approval):** have the repository ignore a refresh result that started before the latest save, or that arrives while a save is pending. The UI does not change.

```diff
 final class AccountRepository {
     private let api: APIClient
+    private var pendingSaves = 0          // touch only on the main thread
+    private var saveGeneration = 0
     init(api: APIClient) { self.api = api }

     /// Called on launch and every time the account screen appears.
     func refresh(accountId: Int, completion: @escaping (Result<Account, Error>) -> Void) {
-        api.request(method: "PUT", path: "/accounts/\(accountId)", body: nil, completion: completion)
+        let generationAtStart = saveGeneration
+        api.request(method: "GET", path: "/accounts/\(accountId)", body: nil) { [weak self] result in
+            DispatchQueue.main.async {
+                guard let self else { return }
+                // A save started or is still running since this read began: its response is newer.
+                if self.pendingSaves > 0 || self.saveGeneration != generationAtStart { return }
+                completion(result)
+            }
+        }
     }

     func save(_ account: Account, completion: @escaping (Result<Account, Error>) -> Void) {
-        api.request(method: "PUT", path: "/accounts/\(account.id)", body: account.encoded(), completion: completion)
+        pendingSaves += 1
+        saveGeneration += 1
+        api.request(method: "PUT", path: "/accounts/\(account.id)", body: account.encoded()) { [weak self] result in
+            DispatchQueue.main.async {
+                self?.pendingSaves -= 1
+                completion(result)
+            }
+        }
     }
 }
```

  - **Review gate:**
    - A skipped refresh never hides data. The save's own response, which is the newer server state, still reaches the caller.
    - If the save fails, the next appear refreshes normally.
    - It assumes callers use `save`'s returned `Account` to update the shared state. Confirm that.
    - Moving the completions to the main thread is a behaviour change if callers already hop threads. It is harmless but worth noting.
    - If you prefer, apply only the F1 one-liner now and do F2 separately.
- **Test:** use a stub `APIClient` that holds completions:
  1. Start the refresh.
  2. Start the save.
  3. Complete the save with the new value.
  4. Complete the refresh with the old value.
  5. Assert that the caller ends up with the new value.
  
  The test fails before the fix and passes after it.

## Not covered (not in the fixture)
For each of these, the networking checklist could not be answered:
- Timeouts, and whether every failure reaches the UI: offline, 4xx, 5xx, HTML or WAF pages.
- Whether a non-2xx status is treated as an error even when the body decodes.
- Whether the completion can fire twice.
- Which thread completions run on.
- How 401 is handled (logout once, single-flight token refresh).
- Lenient decoding of `Account`.
- What `account.encoded()` contains: full object or partial, and whether it includes read-only or server-owned fields.
- Whether `accountId` comes from the session and the server checks object ownership. Changing `{id}` must not let one user read or write another user's account (an IDOR test with two test accounts).
- HTTPS and certificate validation.
- Logging of the body.

## Fix order
1. **Backend first:** confirm or add `GET /accounts/{id}`, and say what `PUT` with an empty body does today.
2. **F1 app change** (one line) and a unit test on both platforms, then a new build.
3. **Backend:** reject `PUT` requests with an empty or missing body, to protect against builds already installed.
4. **F2 guard** (if approved) and its test.
5. If F1.1 happened in production: find the affected accounts in the server history and restore them.
