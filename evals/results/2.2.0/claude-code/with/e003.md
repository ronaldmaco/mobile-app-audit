# Why some users always see "Something went wrong" on Home

**Mode:** A, bug verification. **How I checked it:** I read the code (`FeedLoader.swift`) and the backend sample in `combinations.csv`, which gives event counts per venue and category from the events API. **What I could not do:** use a device, simulator, the backend or git history. Anything that needs those is marked "not tested" below.

## Short answer

The app shows the error message whenever the list comes back **empty**, not only when a request actually fails. Whether a user hits this depends only on their saved preferences (venues and categories). The data shows that roughly half of all venue and category pairs have 0 events. So users whose preferences only cover empty pairs get "Something went wrong" every time, on every Home list. Users whose preferences include at least one pair with events never see it. Nothing is broken on the network side. The app labels "no events for your preferences" as a failure.

## Findings

### F1 [High] An empty result is shown as an error
- **Status:** Verified in code, with a concrete trigger from backend data. Not reproduced on a device.
- **Where:** `FeedLoader.swift:5-8`
  ```swift
  case .success(let events) where !events.isEmpty:
      completion(.loaded(events))
  default:
      completion(.error("Something went wrong"))   // also used for an empty list
  ```
  The `default` branch catches two different cases: `.success([])` (the request worked and there are no events) and `.failure` (the request really failed).
- **What the user sees:** "Something went wrong" on every Home list, every time, including after retrying or restarting the app.
- **Cause:** `load` sends `venues: prefs.venueIds, categories: prefs.categoryIds` (`FeedLoader.swift:3`). When that combination has no events, the API correctly returns an empty list, and the loader maps it to `.error`.
- **Trigger:** depends on the user's preferences. Examples from `combinations.csv`:
  - Venue `riverside` with any category (concerts, theatre and comedy are all 0): always an error.
  - Category `theatre` only, at any venue (all 0): always an error.
  - `north-hall` + `concerts` (14), or `old-town` + `comedy` (3): never an error.

  This explains "some users always, others never": the outcome depends on the data, not on timing or the network. The sweep note says about half of all pairs are 0, so a large share of possible preference sets is affected.
- **Evidence:** the code path above, plus `combinations.csv` with 5 of the 9 sample pairs at 0.
- **Second effect of the same line:** real network or server errors look exactly like "no events". The user (and support) cannot tell an outage from an empty preference set. A retry button cannot help the empty case, because the result will be empty every time.

### F2 [Medium, backend/content] Many venue and category pairs have no events
- **Status:** Verified from the sweep sample. I did not re-run the sweep (no backend access).
- **Where:** events data: `riverside` has 0 in every category, and `theatre` has 0 at every venue.
- **Why it matters:** preferences can still be set to options that have no content, such as a venue with nothing scheduled or a category with nothing anywhere. That is the "orphan backend data" pattern. Even after F1 is fixed, those users will see an empty Home.
- **Owner:** backend/content team. Questions for them: is `riverside` still active? Is `theatre` simply out of season? Should the preference screens hide or mark options that have no upcoming events?

## Proposed fix (needs your approval; nothing changed)

The smallest change at the cause: separate "empty" from "failed". The look stays the same. The only addition is an empty state, which the skill allows.

```diff
--- a/FeedLoader.swift
+++ b/FeedLoader.swift
@@
 final class FeedLoader {
     func load(prefs: Preferences, completion: @escaping (FeedState) -> Void) {
         api.events(venues: prefs.venueIds, categories: prefs.categoryIds) { result in
             switch result {
-            case .success(let events) where !events.isEmpty:
-                completion(.loaded(events))
-            default:
-                completion(.error("Something went wrong"))   // also used for an empty list
+            case .success(let events) where events.isEmpty:
+                completion(.empty)                            // valid answer: nothing matches these preferences
+            case .success(let events):
+                completion(.loaded(events))
+            case .failure:
+                completion(.error("Something went wrong"))   // only real failures
             }
         }
     }
 }
```

```diff
--- a/FeedState.swift   (file not in the fixture; shape assumed)
+++ b/FeedState.swift
 enum FeedState {
     case loaded([Event])
+    case empty
     case error(String)
 }
```

The Home list views must then render `.empty` with an empty-state message, for example "No upcoming events for your venues and categories" plus a link to edit preferences. They must not show a retry button for this state. The view code is not in the fixture, so I can't write that diff. Please send it.

**Optional, product decision:** Home is a curated feed, so instead of a bare empty state it may *widen* the query, provided it does so **visibly and in a documented order**. For example: first drop the category and keep the user's venues ("No theatre at your venues; here is what's on at Riverside..."), then fall back to popular events overall. Each widened list must carry a label saying it is not the user's exact selection. Do this only with your approval. Explicit filter or search screens must keep the honest empty state and must not widen.

**Review gate:**
- *Does it drop or hide a user choice or a server value?* No. The user's preferences are still sent unchanged. The empty result is now shown honestly instead of being disguised as an error. With the optional widening, the change is visible and labelled.
- *What does "empty" mean to each consumer?* For a `.success([])` response it means "nothing matches", and it becomes `.empty`. For the request side, I have not checked what empty preference arrays mean to the API; that is the open question above. Do not add any code that drops invalid ids from the request: an empty filter would turn into "any" and show events the user did not choose.
- *Which impact-map cells change?* The "all pairs empty" and "removed option" rows go from an error to an empty state. The failure rows stay errors. The non-empty rows don't change.
- *Backend change needed?* Yes, F2, owned by the backend/content team.
- *Compile impact:* every `switch` over `FeedState` needs a `.empty` case. The compiler will list them, and that list is the set of consumers to check.
