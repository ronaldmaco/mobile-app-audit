# Privacy audit: account screen and analytics (pre-release)

## 1. Summary

- **Mode:** C, targeted audit (privacy of the account/settings screen, sign out, analytics, and the local response cache those flows write to).
- **Scope read:** `SettingsViewController.swift`, `Tracker.swift`, `ResponseStore.swift` (all the code I was given).
- **How it was checked:** static code review only. I had no device, simulator, backend, git history, `Info.plist`, `PrivacyInfo.xcprivacy`, analytics SDK setup or the rest of the app. Everything below is proven from the code shown, plus a trigger. Anything that depends on code I could not see is marked **Suspected**.
- **Verdict:** **do not release as is.** The tracking switch does not stop tracking. The analytics identity is the user's email. Sign out leaves both the analytics identity and the cached server responses on the device. Every successful response, including writes (and probably the login response with its token), is saved in plain files in a backed-up folder.

| ID | Severity | Title | Status |
|---|---|---|---|
| P1 | Critical | The tracking switch never reaches the analytics SDK. Events and identify keep running after opt-out | Verified (in the code shown) |
| P2 | Critical | Every 2xx response, writes included, is saved to `Documents/` (backed up, not cleared, may contain the token) | Verified (storage). Suspected (token content) |
| P3 | High | Analytics identity is the user's email (PII sent to a third party) | Verified |
| P4 | High | Sign out does not reset the analytics identity or clear per-user cached data | Verified |
| P5 | Medium | The consent save ignores the server result: no revert, no error, local and server disagree | Verified |
| P6 | Medium | `tracking_toggled` is sent before the server confirms, and also when the user opts out | Verified |

## 2. Findings

### P1 [Critical] The tracking switch never reaches the analytics SDK
**Status:** Verified for every path in the code shown. If a gate exists elsewhere (for example in the SDK setup in the AppDelegate), please send that file; I did not see one.
**Where:** `SettingsViewController.swift:3-4`, `Tracker.swift:2-3`
**What the user sees:** they turn "Allow tracking" off, but the app keeps sending events and their identity to the analytics provider.
**Cause:** the switch writes `allowTracking` to `UserDefaults` (line 3) and sends it to the backend (line 4). Nothing reads `allowTracking`: `Tracker.identify` and `Tracker.event` call `AnalyticsSDK.shared` without any check, and the SDK's own opt-out or disable API is never called. This is the "consent not reaching the SDK" pattern.
**Trigger:** switch off, then use any screen that calls `Tracker.event`, or sign in again (`Tracker.identify`).
**Impact map:**

| Consumer / state | Expected | Now |
|---|---|---|
| `Tracker.event` after opt-out | no event sent | sent (fail) |
| `Tracker.identify` after opt-out | no identify | sent with email (fail) |
| Fresh install, before any choice | policy default (opt-in where GDPR/ePrivacy applies) | tracks (fail; the default must be decided, see questions) |
| Cold start after opt-out | SDK starts disabled | SDK has no idea (fail) |
| SDK automatic events (sessions, screens, crashes) | disabled | not controlled at all (fail; not tested, I cannot see the SDK config) |
| Other SDKs under the same consent (ads, attribution, push marketing) | follow the switch | unknown (not tested, I cannot see them) |
| Android / sibling apps | same behaviour | not tested (not provided) |

**Fix:** make `Tracker` the single gate, and push the choice to the SDK at launch and whenever it changes (diff in section 4). The look of the screen stays the same.
**Review gate:** this does not hide a user choice. It enforces the user's choice. It does change one thing: if the fresh-install default becomes "off", users will see the switch off until they turn it on. That is a product/legal decision (question 1).
**Test:** unit test with a fake `AnalyticsSDK`: with `allowTracking = false`, `event`/`identify` produce no calls and `setEnabled(false)` was called. Manual test: a proxy (Charles/Proxyman) shows no requests to the analytics host after opt-out, including after a cold start.
**Delivery:** app build. Privacy policy and store privacy labels must match the real behaviour.

### P2 [Critical] Every 2xx response, writes included, is saved in `Documents/`
**Status:** Verified that the data is stored. **Suspected** that the token or other PII is in it: that depends on the login/profile response bodies, which I could not see.
**Where:** `ResponseStore.swift:2-4` (comment on line 3: "called for every 2xx response, any method")
**What the user sees:** nothing on screen. But their account data, and possibly their session token, sits in plain files that go into iCloud/computer backups and stay on the device after sign out.
**Cause:**
1. The folder is `documentDirectory`. It is backed up by default and shown in the Files app if file sharing is ever turned on. Per-user caches belong in `Caches`.
2. **Any method** gets stored: the responses to POST/PUT/PATCH writes are saved too. That covers login (likely the token, which should live only in the Keychain), `updatePreferences`, profile updates, and so on. Writes must never be cached.
3. No file protection option is set, so the files use the default class, which is readable once the device has been unlocked after a reboot.
4. Nothing ever deletes the folder. Sign out (`SettingsViewController.swift:7-11`) does not clear it (see P4).
5. `try?` hides every error. If the `responses` subfolder is never created, every write fails silently. That is not a privacy problem, but the cache may simply not work.
6. Suspected: if `key(request)` is built from the URL only (I cannot see it), user B can be served user A's cached `/me`-style responses on the same device.

**Trigger:** sign in, use the app, and look in `Documents/responses/` (device backup or Xcode container download). Expect login and profile bodies there.
**Impact map:** login response (token?) fails; profile/account GETs fail (backed up, kept after sign out); preference writes fail (write cached); other user on the same device fails/suspected (key); upgrade from this build keeps the old `Documents/responses` files unless migrated (fail).
**Fix:** cache only GET, in `Caches`, with complete file protection, excluded from backup. Clear it on sign out. Delete the old `Documents/responses` once on upgrade (diff in section 4).
**Review gate:** dropping cached writes means offline reads of things that were only ever written (if any screen relies on that) would refetch. I see no consumer that reads them, but the reader of `ResponseStore` was not provided (question 4).
**Delivery:** app build, plus a one-time migration that deletes the old folder. Existing backups already contain the data; if a token was stored, consider invalidating sessions server-side (backend owner).

### P3 [High] Analytics identity is the user's email
**Status:** Verified
**Where:** `Tracker.swift:2`
**What the user sees:** nothing. Their email is sent to a third-party analytics provider and becomes the key that links all their events.
**Cause:** `AnalyticsSDK.shared.identify(user.email)`. The email is direct personal data. It also changes when the user edits their email, which splits their history into two identities.
**Fix:** identify with an opaque, stable internal id (`user.id`, or a server-issued analytics id). Never send the email. Only identify when tracking is allowed (P1).
**Review gate:** dashboards keyed by email will start showing new ids. That is the analytics owner's call (question 2). The App Store privacy label and Play Data safety must list what is actually sent ("Email address, linked to identity" today).
**Also check:** event properties across the app for other personal data (name, phone, free text). Only `Tracker.swift` and one call site were provided.

### P4 [High] Sign out leaves the analytics identity and per-user data behind
**Status:** Verified
**Where:** `SettingsViewController.swift:7-11`
**What the user sees:** after signing out, the next person using the device is tracked under the previous user's identity, and the previous user's cached responses (P2) are still on disk.
**Cause:** `signOutTapped` deletes the Keychain token and clears `Session.shared.user`, but:
- it does not call the SDK's `reset()`/logout, so later events stay attached to the old identity;
- it does not clear `ResponseStore`;
- it does not tell the server (the token stays valid on the server if it was copied, for example from the P2 files). This is Suspected; it depends on whether a logout endpoint exists;
- `allowTracking` stays in `UserDefaults`, so the next account inherits the previous user's consent. Whether consent belongs to the device or the account is a decision (question 3).

**Impact map:** sign out then sign in as another user (analytics identity fails, cache fails, consent unclear); sign out then use the app logged out (events attributed to the old user, fails); kill after sign out (the cache files persist, fails).
**Fix:** a single sign-out routine that clears the token, user, response cache and analytics identity (diff in section 4). No UI change.

### P5 [Medium] The consent save ignores the server result
**Status:** Verified
**Where:** `SettingsViewController.swift:4` (`{ _ in }`)
**What the user sees:** if the save fails (offline, 5xx, expired session), the switch shows the new value with no message. The server keeps the old value, so server-side processing (emails, server-side tracking, other devices) follows a choice the user did not make. On the next settings refresh the switch may flip back without explanation.
**Cause:** the completion is discarded. There is no loading state, no disabling of the switch during the save, no revert and no error.
**Fix (review gate applied):**
- **Turning OFF** takes effect on the device immediately and stays that way. A network error must never re-enable tracking. If the server save fails, show a short error with retry and keep the switch off.
- **Turning ON** is applied only after the server confirms. On failure, revert the switch and show the error.
- Disable the switch while the save is in flight, so fast toggles cannot race.

### P6 [Medium] `tracking_toggled` is sent before success, and on opt-out
**Status:** Verified
**Where:** `SettingsViewController.swift:5`
**Cause:** the event fires right after the request starts, so it is logged even when the save fails. With `on: false` it sends an analytics event at the moment the user withdraws consent. The checklist rule is "events fire once per action, after success". Logging an opt-out to the tracking provider is generally not allowed without consent.
**Fix:** send it only for opt-in, after the server confirms. For opt-out, record it server-side if an audit trail is needed (the backend already receives `updatePreferences`).

## 4. Proposed changes (diffs, not applied)

The SDK method names `setEnabled` and `reset` stand in for whatever the real analytics SDK calls its opt-out and logout APIs. Most have an equivalent (`optOut`, `setAnalyticsCollectionEnabled`, `reset`...). `user.id` is assumed to be a stable, non-PII id.

**Tracker.swift** (P1, P3, P4)
```diff
 enum Tracker {
-    static func identify(_ user: User) { AnalyticsSDK.shared.identify(user.email) }
-    static func event(_ name: String, _ props: [String: Any] = [:]) { AnalyticsSDK.shared.track(name, props) }
+    private static let key = "allowTracking"
+    // Default when the user never chose: decided by product/legal (question 1).
+    static var isAllowed: Bool { UserDefaults.standard.bool(forKey: key) }
+
+    /// Call at launch (before any other Tracker call) and whenever consent changes.
+    static func setAllowed(_ allowed: Bool) {
+        UserDefaults.standard.set(allowed, forKey: key)
+        AnalyticsSDK.shared.setEnabled(allowed)      // SDK's own opt-out, also stops automatic events
+        if !allowed { AnalyticsSDK.shared.reset() }  // drop identity and queued events
+    }
+    static func applyStoredConsent() { AnalyticsSDK.shared.setEnabled(isAllowed) }
+
+    static func identify(_ user: User) {
+        guard isAllowed else { return }
+        AnalyticsSDK.shared.identify(String(describing: user.id))  // opaque id, never email
+    }
+    static func event(_ name: String, _ props: [String: Any] = [:]) {
+        guard isAllowed else { return }
+        AnalyticsSDK.shared.track(name, props)
+    }
+    static func reset() { AnalyticsSDK.shared.reset() }
 }
```
Plus one line at app launch, before any SDK use: `Tracker.applyStoredConsent()`.

**SettingsViewController.swift** (P1, P4, P5, P6)
```diff
 final class SettingsViewController: UITableViewController {
     @IBAction func trackingSwitchChanged(_ sender: UISwitch) {
-        UserDefaults.standard.set(sender.isOn, forKey: "allowTracking")
-        api.updatePreferences(allowTracking: sender.isOn) { _ in }
-        Tracker.event("tracking_toggled", ["on": sender.isOn])

+                        Tracker.event("tracking_toggled", ["on": true])

+                    self?.showSaveError(retry: { self?.trackingSwitchChanged(sender!) })  // existing alert style
+                }
+            }
+        }
     }

```
`showSaveError` stands for the app's existing error alert; I did not see it. If `updatePreferences` does not return a `Result`, adapt the switch. If a logout endpoint exists, call it before clearing the token (question 5).

**ResponseStore.swift** (P2)
```diff
 enum ResponseStore {
-    static let dir = FileManager.default.urls(for: .documentDirectory, in: .userDomainMask)[0].appendingPathComponent("responses")
-    static func save(_ data: Data, for request: URLRequest) {   // called for every 2xx response, any method
-        try? data.write(to: dir.appendingPathComponent(key(request)))
+    static let dir = FileManager.default.urls(for: .cachesDirectory, in: .userDomainMask)[0]
+        .appendingPathComponent("responses", isDirectory: true)
+    private static let legacyDir = FileManager.default.urls(for: .documentDirectory, in: .userDomainMask)[0]
+        .appendingPathComponent("responses", isDirectory: true)
+
+    static func save(_ data: Data, for request: URLRequest) {   // called for every 2xx response
+        guard (request.httpMethod ?? "GET").uppercased() == "GET" else { return }  // never cache writes/login
+        do {
+            try FileManager.default.createDirectory(at: dir, withIntermediateDirectories: true)
+            try data.write(to: dir.appendingPathComponent(key(request)), options: [.atomic, .completeFileProtection])
+        } catch {
+            // cache is best-effort; log in debug only, never the body
+        }
+    }
+
+    /// Sign out, and once at launch to remove data written by older builds to Documents/.
+    static func clear() {
+        try? FileManager.default.removeItem(at: dir)
+        try? FileManager.default.removeItem(at: legacyDir)
     }
 }
```
At launch, run a one-time cleanup of `legacyDir` (or call `ResponseStore.clear()` once, behind a `UserDefaults` migration flag). If `key(request)` does not include the user id, add it, or rely on `clear()` on sign out and on any account switch.

**Regression tests (XCTest)** — first confirm a test target builds:
1. `allowTracking = false`: `Tracker.event`/`identify` make no SDK calls, and `setEnabled(false)` + `reset()` were called.
2. `identify` never passes a value that contains `@`, or equal to `user.email`.
3. Opt-in with a failing fake API: the switch goes back to off, and `Tracker.isAllowed == false`.
4. Opt-out with a failing fake API: `Tracker.isAllowed == false` stays false.
5. `ResponseStore.save` with POST writes nothing. GET writes to `Caches`. `clear()` removes both the new and legacy folders.
6. Sign out calls `Tracker.reset()` and `ResponseStore.clear()`.

Manual check on the release build, through a proxy: no analytics traffic after opt-out (including after a cold start and after a fresh sign in); no email in any analytics payload; `Documents/responses` gone after the update.

## 5. Fix order and delivery

1. **P1 + P6** (consent gate). This blocks release, both for privacy law and for App Store 5.1.1/5.1.2 accuracy.
2. **P2** (response cache) plus the migration that removes the old files. If login responses with tokens were stored, the backend owner should consider revoking existing sessions.
3. **P3** (email as identity). Coordinate with the analytics owner. Update the privacy label, Data safety and privacy policy.
4. **P4** (sign out cleanup).
5. **P5** (save handling).

All of these ship in an app build, on both platforms if Android shares the design. Before calling this done: release build tested through a proxy; privacy manifest/labels updated; Android/sibling apps checked; nothing committed until you approve.

## 6. Questions I would ask (I could not ask them now)

1. **Default consent:** before the user touches the switch, should tracking be off (opt-in, required for EU users under GDPR/ePrivacy) or on? Do you show an ATT prompt, and does this SDK use IDFA or do cross-app tracking?
2. **Analytics identity:** which stable non-PII id should be used (`user.id`, or a server-issued analytics id)? Do dashboards depend on email today?
3. **Consent scope:** does `allowTracking` belong to the device or to the account? If the account, should it be loaded from the server after sign in and cleared on sign out?
4. **ResponseStore:** what does `key(request)` contain, who reads the cache, and does the login response body contain the token?
5. Is there a **logout / token revoke endpoint**, and an **in-app account deletion** flow?
6. Please send: the analytics SDK setup (AppDelegate/SceneDelegate), `Info.plist`, `PrivacyInfo.xcprivacy`, the other `Tracker.event` call sites, any other SDKs (ads, attribution, crash, push), and the Android equivalents. I would then check automatic collection, the manifest, the labels and the siblings.
