# app-a crash in `KeyboardAvoiding.keyboardWillHide`: root cause and fix (app-a and app-b)

**Mode:** A, bug verification (production crash report). I worked from code review only. I had no device, crash log, git history or build info, so I could not reproduce the crash. Each finding below is marked **Verified** or **Suspected**.

## 1. Root cause

**Verified in code. The trigger is concrete but I have not reproduced it on a device.**

`app-a/KeyboardAvoiding.swift:7-10`
```swift
func keyboardWillHide(_ n: Notification) {
    formScrollView.contentSize = originalContentSize!   // line 8
    originalContentSize = nil
}
```

The handler assumes every *hide* follows a *show*. `originalContentSize` is set only in `keyboardWillShow` (line 4), and line 9 sets it back to `nil`. Any `keyboardWillHide` that has no matching earlier `keyboardWillShow` force-unwraps `nil` and crashes. This is the "unpaired events" pattern.

iOS sends unpaired or repeated hide notifications in ordinary use:
- The screen starts observing while the keyboard is already up. For example, it is pushed or presented from a screen with a focused text field, and the first event it gets is the hide.
- iOS sends a second `keyboardWillHide`. This happens on interactive dismissal (`keyboardDismissMode = .interactive`) that is cancelled and then finished, on rotation, on a split or floating keyboard on iPad, on app background/foreground, and when a hardware keyboard is connected while the keyboard is up. The first hide sets the value to `nil` and the second one crashes.
- The keyboard moves from undocked to floating on iPad. iOS sends hide without show.

**Second unwrap on the same line (Suspected):** `formScrollView` is an implicitly unwrapped `UIScrollView!`. If the observer is still registered after the view was unloaded, or registered before `viewDidLoad`, line 8 also crashes, with the same symbol in the stack trace. Only the crash log can tell the two apart:
- "Unexpectedly found nil while unwrapping an Optional value" at line 8, with the column pointing at `originalContentSize!`, is the main cause above.
- A nil `formScrollView` points to an observer-lifecycle problem in the screens that adopt the protocol. Those screens are not in the code I was given.

### Related bug in the same code (Verified in code, not a crash)

`keyboardWillShow` (lines 3-6) has the opposite problem. iOS often sends `keyboardWillShow` several times without a hide in between: when you switch to a field with a different keyboard type, toggle the predictive bar, change the input view, or rotate. Each call:
1. overwrites `originalContentSize` with the **already enlarged** size, and
2. adds the keyboard height **again**.

As a result, `contentSize` gets larger with each repeated show, and the "restore" on hide puts back an enlarged size. The user sees extra blank scroll space under the form that stays after the keyboard closes. It is the same mechanism (show and hide assumed to come in pairs), so it is part of the same fix.

## 3. Fix (smallest change, no visual change)

The same diff applies to `app-a/KeyboardAvoiding.swift` and `app-b/KeyboardAvoiding.swift`. The two files are byte-for-byte identical.

```diff
 extension KeyboardAvoiding {
     func keyboardWillShow(_ n: Notification) {
-        originalContentSize = formScrollView.contentSize
-        formScrollView.contentSize.height += keyboardHeight(n)
+        guard let scrollView = formScrollView else { return }
+        // Keep the size from before the first show; repeated shows must not build up.
+        let original = originalContentSize ?? scrollView.contentSize
+        originalContentSize = original
+        scrollView.contentSize.height = original.height + keyboardHeight(n)
     }
     func keyboardWillHide(_ n: Notification) {
-        formScrollView.contentSize = originalContentSize!
+        // Hide can arrive without a matching show (screen appeared with the keyboard up,
+        // duplicate hide, iPad floating keyboard). Nothing to restore in that case.
+        guard let scrollView = formScrollView, let original = originalContentSize else { return }
+        scrollView.contentSize = original
         originalContentSize = nil
     }
 }
```

Review gate:
- **Does it drop or hide user input or server data?** No. The only thing skipped is a restore when nothing was saved, and in that case the scroll view was never enlarged, so there is nothing to undo.
- **What does an empty value mean?** `originalContentSize == nil` now means "not enlarged", which is how the code was already meant to work.
- **Which behaviour changes?** A hide without a show changes from a crash to a no-op. A repeated show now sets the height to original + current keyboard height instead of adding it again. Everything else stays the same, and the layout, copy and navigation do not change.
- **Backend or CMS change needed?** No.

## 4. Follow-up I recommend but have not done (needs your approval)

Changing `contentSize` by hand fights Auto Layout. A layout pass can overwrite it, or the saved size can be stale when the hide restores it. The usual fix is to change `contentInset.bottom` / `verticalScrollIndicatorInsets.bottom`, or to use `keyboardLayoutGuide` on iOS 15+. That fix is larger and changes the scroll behaviour slightly, so I am proposing it, not including it in the crash fix.

Also check (not visible in the fixture):
- Where each conforming screen registers and removes the observers. It should observe in `viewWillAppear`/`viewDidAppear` and remove in `viewWillDisappear`, or use token-based observers that are released with the view controller.
- `keyboardHeight(_:)`: confirm it converts `keyboardFrameEndUserInfoKey` into the scroll view's coordinate space and returns 0 when the key is missing, not a crash.

## 5. Regression tests (XCTest)

These fail before the fix (the first one crashes, the second fails on the size) and pass after it:

```swift
final class KeyboardAvoidingTests: XCTestCase {
    final class Host: KeyboardAvoiding {
        var formScrollView: UIScrollView! = UIScrollView()
        var originalContentSize: CGSize?
    }
    func note(height: CGFloat) -> Notification {
        Notification(name: UIResponder.keyboardWillShowNotification, object: nil,
                     userInfo: [UIResponder.keyboardFrameEndUserInfoKey:
                                NSValue(cgRect: CGRect(x: 0, y: 500, width: 320, height: height))])
    }

    func testHideWithoutShowDoesNotCrash() {
        let h = Host(); h.formScrollView.contentSize = CGSize(width: 320, height: 800)
        h.keyboardWillHide(note(height: 0))
        XCTAssertEqual(h.formScrollView.contentSize.height, 800)
    }
    func testDoubleHideDoesNotCrash() {
        let h = Host(); h.formScrollView.contentSize = CGSize(width: 320, height: 800)
        h.keyboardWillShow(note(height: 300)); h.keyboardWillHide(note(height: 0)); h.keyboardWillHide(note(height: 0))
        XCTAssertEqual(h.formScrollView.contentSize.height, 800)
    }
    func testRepeatedShowDoesNotAccumulate() {
        let h = Host(); h.formScrollView.contentSize = CGSize(width: 320, height: 800)
        h.keyboardWillShow(note(height: 300)); h.keyboardWillShow(note(height: 340))
        XCTAssertEqual(h.formScrollView.contentSize.height, 800 + 340)
        h.keyboardWillHide(note(height: 0))
        XCTAssertEqual(h.formScrollView.contentSize.height, 800)
    }
    func testNilScrollViewIsIgnored() {
        let h = Host(); h.formScrollView = nil
        h.keyboardWillShow(note(height: 300)); h.keyboardWillHide(note(height: 0))
    }
}
```

Change the expected values if `keyboardHeight(_:)` converts coordinates or subtracts the safe area. First check that the test target builds and runs at all.
