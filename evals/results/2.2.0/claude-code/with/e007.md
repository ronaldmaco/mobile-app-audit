# Audit: lists that load forever and show the wrong picture

## 1. Summary

- **Mode:** C, a targeted audit of networking and remote images. The user complaints are treated as hypotheses.
- **Scope:** the only app code available: `HTTPClient.swift` (generic JSON request helper) and `UIImageView+Remote.swift` (remote image loader used in reusable cells).
- **How it was checked:** static code review only. I had no device, simulator, backend, git history, callers, cells, build settings or tests. Each finding below is **Verified in code** (the mechanism and a concrete trigger are visible in the lines cited). Whether each one is the cause of the specific user reports is **Suspected** until it is reproduced on a device (section 6).
- **Short answer:**
  1. **"Loads forever":** `send` never calls `completion` when the request fails or the response cannot be decoded. The caller's spinner never gets a result, so it never stops. This happens offline, on a timeout, with an HTML/WAF/captive-portal page, with a 5xx/4xx error body, or when the server adds a null field.
  2. **"Wrong picture":** `setRemoteImage` neither cancels nor checks which request is current. In a reused cell, the late image for the previous row lands on the new row. If the new row's download fails or is slow, the old row's picture stays.
  3. Two related problems: HTTP status codes are never checked, so an error response that decodes is shown as real data, and images load through blocking `Data(contentsOf:)` with no cache, no status check and no cancellation.

## 2. Findings (most severe first)

### F1 [High] A failed request never completes, so the spinner never stops
Status: Verified in code (mechanism). Suspected as the cause of the user reports until reproduced.
Where: `HTTPClient.swift:3`, `HTTPClient.swift:4-5`
What the user sees: the list shows a loading indicator forever, with no error and no retry.
Cause: on a transport error (`line 3`) and on a missing/undecodable body (`lines 4-5`), the closure only calls `print` and `return`s. `completion` is never called, so the caller is never told about the failure. The signature promises `Result<T, Error>`, but `.failure` is never delivered. `try?` also throws away the decoding error, so nothing reaches logs or crash reporting either.
Trigger (any of these, which is why it happens "sometimes"):
- offline / airplane mode / network drop mid-request (`NSURLErrorNotConnectedToInternet`, `NetworkConnectionLost`)
- slow network hitting the request timeout (`NSURLErrorTimedOut`, 60 s by default unless the caller sets one)
- the request being cancelled
- a captive portal, proxy, CDN/WAF challenge or 502/503 page returning HTML instead of JSON (decode fails)
- a 4xx/5xx with a JSON error body that does not match `T` (for example 401 after a token expires)
- the backend sending `null` or dropping a field that `T` declares as non-optional
- an empty body (204)
Evidence: lines 3 and 5 return without calling `completion`. Line 7 is the only call.
Impact map:
| Row | Expected | Current |
|---|---|---|
| 200 + valid JSON | data shown | OK |
| 200 + JSON with an extra field | data shown | OK (`Decodable` ignores unknown keys) |
| 200 + null/missing required field | error + retry | **hangs** |
| offline / timeout / connection lost | error + retry | **hangs** |
| HTML body (WAF, portal, 5xx page) | error + retry | **hangs** |
| 4xx/5xx with JSON error body | error (or re-auth for 401) | **hangs** |
| 204 / empty body | defined result | **hangs** |
| pull-to-refresh / pagination after failure | spinner ends, retry possible | **stuck spinner; "is loading" flag may block further loads** (callers not visible) |
| consumers: every caller of `send` | each handles `.failure` | **not tested:** callers not in the fixture |
Fix: see diff D1. Always call `completion` exactly once, on the main queue, with `.failure` for transport, status and decode errors. Nothing changes visually beyond what principle 6 allows: callers that already have an error/retry state will now show it. Callers that never handled `.failure` (because it never arrived) must get a minimal error + retry state in the existing style.
Review gate: does it hide any user choice or server value? No, it surfaces failures that are hidden today. Does it change empty-value meaning? No. Backend change? No, but see the open questions on error body formats.
Test: T1 to T6 below.
Also in: every caller of `send`. Check the Android/sibling app for the same "log and return" pattern (not visible here).
Delivery: new app build (store). Old builds keep hanging until users update. Consider a forced update if this is frequent.

### F2 [High] A late image lands on a reused cell, so a row shows another row's picture
Status: Verified in code (mechanism). Suspected as the cause of the "wrong picture" report until reproduced.
Where: `UIImageView+Remote.swift:2-5` (the code comment on line 5 confirms it is used inside reusable cells)
What the user sees: while scrolling, or after a refresh, a list row shows the image of a different item. Sometimes it flickers to the right one; sometimes it stays wrong.
Cause: three missing pieces:
1. **No identity check:** when the download finishes, it sets `self.image` without checking that this image view still wants that URL. Cell A requests `urlA` and gets reused for row B, which requests `urlB`. If `urlA` finishes after `urlB`, row B ends up showing A's picture **permanently**.
2. **No cancellation:** the earlier request keeps running after reuse, so both race.
3. **No reset:** the old image is not cleared when a new URL is set. Until the new image arrives, and **forever if it fails** (the `if let` just skips), the reused cell shows the previous item's picture.
Trigger: fast scrolling, slow or variable network (cellular), refresh or reorder of the list, any image URL that 404s or is slow. Reproduction rate goes up with network latency variance, which is why it happens "sometimes".
Evidence: line 5 sets `self.image = image` unconditionally. There is no stored task or URL and no `prepareForReuse` hook in this extension.
Impact map:
| Row | Expected | Current |
|---|---|---|
| fast network, slow scroll | correct image | usually OK |
| slow network, fast scroll | correct image or placeholder | **wrong image (late result)** |
| new URL fails (404/offline/non-image) | placeholder/fallback | **previous item's image stays** |
| same cell, list refreshed with new data | new item's image | **old image until (if) the new one arrives** |
| offline | placeholder (or cached image) | **stale image from another row or nothing; no cache** |
| consumers: every list/collection cell and any non-reused view using `setRemoteImage` | correct image | **not tested:** call sites not in the fixture |
Fix: see diff D2. Track the current URL and task per image view, cancel on a new request and in `prepareForReuse`, show the placeholder while loading, and apply a result only if the URL still matches. The look stays the same: the same image ends up in the same place, and the placeholder is the app's existing one (to confirm). If the app already has an image library (Kingfisher, SDWebImage, Nuke), using it is an option, but adopting one needs approval (principle 7).
Review gate: hides nothing the server sent. A failed image now shows the placeholder instead of somebody else's picture, which is honest.
Test: T7 to T10.
Also in: any other place images are loaded by hand (Android `ImageView`/RecyclerView adapters, SwiftUI views), which I could not check.
Delivery: new app build.

### F3 [Medium] HTTP status is never checked, so error responses can be shown as real data
Status: Verified in code.
Where: `HTTPClient.swift:7` (the code comment there says so too)
What the user sees: an empty list or wrong content instead of an error, for example after a 401/403/404/500 whose body happens to decode into `T` (an empty array `[]`, an object whose fields are all optional, an error envelope with the same shape).
Cause: `response` is ignored. Any body that decodes is delivered as `.success`. When the body does not decode, this turns into F1 (a hang).
Trigger: expired session (401), maintenance (503 with JSON), a backend returning `[]` with 500, a CDN serving a cached error.
Impact map: 2xx → success (OK); 3xx is handled by URLSession; 4xx/5xx with a decodable body → **shown as success**; 4xx/5xx with a non-decodable body → **hangs (F1)**; 304 from the cache → OK (URLSession turns it into 200).
Fix: part of D1 (non-2xx → `.failure(HTTPError.status(code, data))`). Separately, decide whether 401 should trigger a token refresh or a sign-out (that code is not visible here).
Also in: image loading (F4) has the same gap.

### F4 [Medium] Images use blocking `Data(contentsOf:)`: no timeout control, no cache, no status check, thread pile-up
Status: Verified in code. The performance impact is Suspected (needs Instruments).
Where: `UIImageView+Remote.swift:3-4`
What the user sees: images load slowly or never on a poor network, everything re-downloads on every scroll, no images offline, extra data usage, and possible scroll jank.
Cause:
- `Data(contentsOf:)` is a synchronous API meant for local files. Apple's documentation says not to use it for network URLs. It cannot be cancelled and gives no response or status.
- Each call blocks a thread from `DispatchQueue.global()`. When a user scrolls fast, many requests pile up and GCD creates more threads (thread explosion). This can delay other background work, including JSON decoding from `send`, and contributes to the "slow / forever" feel.
- No memory or disk cache: re-downloads on every reuse, and nothing shows offline.
- `UIImage(data:)` defers decoding, so the full decode happens on the main thread when the image is first drawn (jank with large images).
- Failures are silent (no fallback image).
Fix: D2 switches to `URLSession.dataTask` (cancellable, uses `URLCache` and the session timeout), adds an `NSCache`, checks the status and decodes off the main thread (`preparingForDisplay` on iOS 15+).

### F5 [Low] Errors only go to `print`, so production failures are invisible
Status: Verified in code.
Where: `HTTPClient.swift:3,5`
Cause: `print` is not collected in production, and `try?` drops the decoding error details. This is why this kind of "sometimes" bug cannot be seen in crash/analytics data today.
Fix: in D1 the error reaches the caller. Optionally log it through the app's existing logger or non-fatal reporting (send no URLs with tokens and no response bodies containing personal data).

## 3. Proposed diffs (not applied; need approval)

### D1, `HTTPClient.swift`
```diff
-func send<T: Decodable>(_ req: URLRequest, completion: @escaping (Result<T, Error>) -> Void) {
-    URLSession.shared.dataTask(with: req) { data, response, error in
-        if let error = error { print("request failed", error); return }
-        guard let data = data, let value = try? JSONDecoder().decode(T.self, from: data) else {
-            print("decode failed"); return
-        }
-        DispatchQueue.main.async { completion(.success(value)) }   // status code never checked
-    }.resume()
-}
+enum HTTPError: Error {
+    case status(Int, Data?)   // non-2xx
+    case emptyBody
+}
+
+func send<T: Decodable>(_ req: URLRequest, completion: @escaping (Result<T, Error>) -> Void) {
+    URLSession.shared.dataTask(with: req) { data, response, error in
+        let result: Result<T, Error>
+        if let error = error {
+            result = .failure(error)
+        } else if let http = response as? HTTPURLResponse, !(200..<300).contains(http.statusCode) {
+            result = .failure(HTTPError.status(http.statusCode, data))
+        } else if let data = data, !data.isEmpty {
+            do { result = .success(try JSONDecoder().decode(T.self, from: data)) }
+            catch { result = .failure(error) }   // keep the DecodingError for logs
+        } else {
+            result = .failure(HTTPError.emptyBody)
+        }
+        if case .failure(let err) = result { print("request failed", req.url?.path ?? "", err) } // no query string: may hold tokens
+        DispatchQueue.main.async { completion(result) }   // exactly once, always on main
+    }.resume()
+}
```
Notes:
- **Timeout:** set an explicit timeout so a stalled request fails in seconds instead of 60. Either do it per request (`req.timeoutInterval = 15`) where the request is built, or use a dedicated `URLSession` with `timeoutIntervalForRequest = 15` and `waitsForConnectivity = false`. The value is a product decision; I would ask.
- **Callers (not visible):** every `switch result` must render `.failure` as the existing error state with retry, and reset the "is loading" / pagination flags. Without that, D1 alone still leaves a spinner.
- If some endpoints legitimately return 204, add an overload for those (`completion(Result<Void, Error>)`) rather than relaxing this one.

## 7. Fix order and what it needs to reach users
1. **D1 + caller error states** (F1, F3, F5): app build. Highest user impact (blocks whole screens).
2. **D2 + `prepareForReuse`** (F2, F4): same build.
3. Tests T1 to T10 in CI.
4. Delivery: merged to the release branch, release build with a new build number, same fix on Android/siblings or the gap stated, store release. Consider a minimum-version prompt if hangs are frequent, because old builds keep hanging.
