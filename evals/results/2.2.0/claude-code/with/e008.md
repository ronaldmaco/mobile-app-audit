# Profile save: bug verification

**Mode:** A, bug verification (a user reported a bug). Only the code summary and one API probe were available. I had no device, no build and no git history.

## Verdict

**Not reproduced. Status: Suspected (unconfirmed).** I can't confirm the bug, and I can't rule it out either. I'm not proposing a fix, because nothing proves a cause yet.

## What the evidence shows

| Check | Result | Strength |
|---|---|---|
| Code path `EditProfileViewController.save()` | Disables the button and sends `PATCH /profile` with the edited fields. On success it updates the session user and closes. On failure it shows the server error and re-enables the button. | Read from the code summary. The happy path and the server-error path look correct. |
| Ground-truth oracle (API) | `PATCH /profile` with the same body on a **test account** returns 200, and `GET /profile` returns the new values. | Verified for that one account, body and environment. |

So the backend accepts and stores the change in the normal case, and the app handles both a 200 and an error response. That covers the common path only. It doesn't cover the user's account, data, build or network, and we know none of those.

## Intake: what I would ask the user (missing information)

1. Which **app version and build**, and where did you install it from (store, TestFlight, internal)? Which **device and OS**?
2. **Which fields** did you change, and to **what values**? Please give the exact text: emoji, accents, a very long name, an empty field, a phone or date format, or a photo.
3. **What exactly happened?**
   - The button did nothing or stayed disabled?
   - You saw an error? If so, the exact text or a screenshot.
   - The screen closed but the old values came back, either right away or after reopening or restarting the app?
   - It worked on this phone but not on another device or on the web?
4. Does it fail **every time** or only sometimes? Did you try again today?
5. What **network** were you on (Wi-Fi, mobile, VPN), and in which **country or region**?
6. **Approximate time** of the attempt yesterday (with time zone) and the **account** email or id, so the backend team can find the request in the server logs.

## Hypotheses to test (all Suspected, none seen yet)

These are ordered by how well they fit "saving doesn't work" when the API works for a test account:

1. **The value is saved, but the UI shows stale data** (read racing a write, or stale cache). The session user is updated, but the profile screen may refresh from a cached `GET /profile`, or a refresh started before the PATCH may finish after it and overwrite the new values. To the user, it looks like the save didn't work. *Check:* what the profile screen reads after the edit screen closes (session user, cache or network), the HTTP cache headers on `GET /profile`, and whether a refresh can land after the save.
2. **Errors with no server response are swallowed.** The summary says a failure "shows the server error". On a timeout, no connection or a parse error there is no server error, so the app might show nothing, or keep the button disabled if that branch doesn't re-enable it. *Check:* the failure branch for transport errors, decode errors and an empty error body.
3. **Data-specific rejection, or a silent drop.** The user's values may fail server validation in a way the test body didn't. Or the server may return 200 but ignore or normalise a field. *Check:* repeat the oracle with the user's exact values, then compare the `GET` result field by field with what was sent.
4. **A 2xx response that isn't 200, or a different response body.** For example, 204 with no body, or a response the app fails to decode, so a success is treated as a failure, or the reverse. *Check:* the status code and body handling in the success branch.
5. **Account or session state.** An expired token gives 401, and the refresh may fail silently. The account may be restricted. *Check:* the server logs for that account at that time.
6. **Old build or the other platform.** The user may run an older build that has a different `save()`, or the Android or iOS sibling. *Check:* the installed version against the code that was reviewed, and the same flow on the other platform.
7. **Region, CDN or WAF.** A challenge page (HTML) returned to the app for `PATCH` from the user's region would surface as a parse error (see hypothesis 2).

## How I would verify (next steps once there is access)

1. **Server logs** for the user's account around the reported time: was a `PATCH /profile` received? Which status code and body came back? That one lookup separates "request never arrived or failed" from "saved but shown stale".
2. **Oracle with the user's exact data:** `PATCH` the user's values on a test account, then `GET` and compare each field.
3. **Device, same build as the user:** run the edit, save and reopen flow 5 or more times. Repeat it on a slow network, with the network cut mid-save, after killing the app right after save, and after an app restart. Each time, check what is shown and what `GET /profile` returns.
4. Repeat steps 2 and 3 on the **other platform** and on any sibling app that shares the backend.

## Impact map (to fill in once the cause is known)

- **Inputs:** unchanged form, one field changed, all fields changed, empty or optional field, very long text, special characters or emoji, other locale formats, photo.
- **Consumers of the profile:** the profile screen, header or avatar elsewhere, settings, any cached copy, and the other platform.
- **States:** online, slow, offline, network lost mid-save, app killed after save, expired token, upgrade with old cached profile, other account.
- **Data source:** whether the server stores and returns exactly what was sent.

## Status

- Bug: **Suspected, not reproduced.** The code path and the API work for one test account with one body.
- Fix: **none proposed.** I'll wait for the intake answers and the server-log lookup, then reproduce before changing code.
- Not tested: device behaviour, the user's build, account and data, network failure paths, and the other platform. I had no access to any of these.
