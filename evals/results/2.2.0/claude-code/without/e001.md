# e001: Favourite venues + Concerts shows concerts at other venues

## Verdict

**The bug is confirmed by reading the code. I have not reproduced it.** I had no device, simulator, backend or git history, so this is based on reading the code only. Yesterday's fix ("Don't send id 0 to the events API") is very likely the cause. It did not fix the bug.

## Evidence

`EventsQuery.swift`, line 8:

```swift
let venueIds = favouriteVenues.map(\.id).filter { $0 != 0 }
```

`api-notes.md`:
- `venue_ids`: an **empty array means no venue filter**.
- The venues endpoint **currently returns several real venues with `"id": 0`** (venues with no page in the CMS).
- The app **also uses id 0** to mean "No favourite venue".

So id 0 has two meanings: a real venue the user can pick, and "no favourite venue". Yesterday's fix removes every 0, so it removes real venues the user picked too.

## How the report happens (step by step)

1. The user picks two favourite venues. Both are among the venues the API returns with `id: 0`.
2. `favouriteVenues.map(\.id)` gives `[0, 0]`. Then `.filter { $0 != 0 }` gives `[]`.
3. The body sent is `{"venue_ids": [], "category_ids": [<concerts>]}`.
4. The backend reads `venue_ids: []` as "no venue filter". It returns **all concerts at every venue**. That matches the report exactly.
5. "Only Concerts works": the category filter is sent unchanged, so it is applied. The venue filter is not.

Related case: the user picks one venue with a real id and one with `id: 0`. The second venue is silently dropped, so its concerts are missing. This produces no error and is harder to notice.

## Proposed fix

There are two separate problems:

1. **The client must not quietly turn "the user picked venues" into "no venue filter".** If the user picked venues, the request must never be sent with an empty `venue_ids`.
2. **Id 0 is not a valid identifier.** "No favourite venue" needs its own representation, not a sentinel id. The backend also needs to give the CMS venues real, unique ids. Even if the app sent `0`, the backend could not tell those venues apart.

### Client diff (fail closed, model "no favourite venue" explicitly)

```diff
--- a/EventsQuery.swift
+++ b/EventsQuery.swift
@@
 // Builds the body for POST /events/search.
-// Previous fix (see git log): "Don't send id 0 to the events API".
+// id 0 is NOT a sentinel: the venues endpoint returns real venues with id 0
+// (no CMS page). "No favourite venue" is modelled as an empty selection,
+// never as a Venue with id 0.
+enum EventsQueryError: Error {
+    /// The user picked venues, but none has an id the API can filter on.
+    /// Sending `venue_ids: []` would mean "all venues", so we refuse.
+    case unfilterableVenues([Venue])
+}
+
 struct EventsQuery {
-    let favouriteVenues: [Venue]   // what the user picked
+    let favouriteVenues: [Venue]   // what the user picked; empty = "No favourite venue"
     let categories: [Category]
 
-    func body() -> [String: Any] {
-        let venueIds = favouriteVenues.map(\.id).filter { $0 != 0 }
-        return [
-            "venue_ids": venueIds,
-            "category_ids": categories.map(\.id)
-        ]
+    func body() throws -> [String: Any] {
+        let venueIds = favouriteVenues.map(\.id).filter { $0 != 0 }
+        // Never widen the user's filter: picked venues but no usable ids
+        // must not become an empty array (= no venue filter).
+        if !favouriteVenues.isEmpty && venueIds.count != favouriteVenues.count {
+            throw EventsQueryError.unfilterableVenues(
+                favouriteVenues.filter { $0.id == 0 })
+        }
+        return [
+            "venue_ids": venueIds,
+            "category_ids": categories.map(\.id)
+        ]
     }
 }
```

Other changes needed alongside this diff (I could not see these files, so these are not diffs):
- Wherever "No favourite venue" is built today as a `Venue(id: 0, …)`, use an empty `favouriteVenues` instead.
- At the call site, handle `unfilterableVenues`. Either show an empty or "this venue can't be filtered yet" state, or stop users from picking id-0 venues as favourites by hiding or disabling them in the picker. Both are better than showing wrong results.
- Choose strict or lenient. The diff above is strict: it throws if *any* picked venue has id 0. A lenient version would only throw when *all* picked venues have id 0, and would show a "some venues couldn't be included" notice otherwise. This is a product decision.

### Backend (the real fix)
Give every venue a unique, non-zero id, even venues without a CMS page. Until then, those venues cannot be filtered correctly, whatever the app sends.

## What I could not verify and what I would ask

- **Which two venues did the user pick?** If neither has `id: 0` in the venues response, this cause does not apply. Then the next things to check are whether the backend really applies `venue_ids`, and the `Venue.id` type and decoding, which I could not see.
- Can I see a captured request body for `POST /events/search` from the user's session or from a debug build? A body showing `"venue_ids": []` with venues selected would confirm this cause.
- Why was yesterday's fix made? Did sending `0` cause an error, or the wrong results? This decides whether sending `0` is ever acceptable.
- Can the backend team assign real ids to the CMS venues without a page, and when?
- After any fix, test on a device with: two id-0 venues + Concerts; one real-id venue and one id-0 venue + Concerts; two real-id venues + Concerts; and "No favourite venue" + Concerts.
