## 1. Critical: `refresh()` uses `PUT` instead of `GET`

```swift
/// Called on launch and every time the account screen appears.
func refresh(accountId: Int, completion: ...) {
    api.request(method: "PUT", path: "/accounts/\(accountId)", body: nil, completion: completion)
}
```

`refresh` is meant to fetch the account. It sends exactly the same verb and path as `save` (line 11), only without a body. This was almost certainly a copy-paste from `save`.

**Why this matters:**
- **Data loss risk.** `PUT` means "replace this resource with the request body." The body here is `nil`, so the request carries either an empty body or something like `null`, depending on `APIClient`. A REST backend could reset or blank the account (name, email, preferences and so on), or it could reject the request.
- **It runs a lot.** The doc comment says `refresh` runs at launch *and every time the account screen appears*. If the server accepts the request, every user who opens the account screen can corrupt their own account.
- **If the server rejects it** with `400`, `405` or `422`, the account screen never loads fresh data. Users would see stale data or an error, and it would look like a "sometimes the account doesn't load" bug.
- **Side effects even if the server tolerates it:** each call may bump `updatedAt` or the version/ETag, fire audit logs or webhooks, and invalidate caches. HTTP caches will never cache a `PUT`, and some proxies or WAFs treat repeated `PUT`s differently from `GET`s.
- **Interaction with `save`.** A `PUT` with an empty body from `refresh` that runs at the same time as a real `save` can land after it and overwrite the user's change (see finding 2).

**Proposed fix:**

```diff
     /// Called on launch and every time the account screen appears.
     func refresh(accountId: Int, completion: @escaping (Result<Account, Error>) -> Void) {
-        api.request(method: "PUT", path: "/accounts/\(accountId)", body: nil, completion: completion)
+        api.request(method: "GET", path: "/accounts/\(accountId)", body: nil, completion: completion)
     }
```

**How to verify the fix** (I could not do this here):
1. Run a proxy (Charles/Proxyman) or check the server access logs, open the account screen, and confirm you see `GET /accounts/{id}` with no `PUT`.
2. Check the backend docs or route table to confirm that `GET /accounts/{id}` exists and returns the same `Account` shape.
3. **Regression check on production data:** query the server logs for `PUT /accounts/*` requests with a zero or empty body since this code shipped. If the backend accepted them, look for accounts whose fields were blanked or reset, and plan remediation (restore from backups or audit log, and notify affected users if needed). This is the most important follow-up. Fixing the client does not repair data that was already damaged.
4. Add a unit test with a mock `APIClient` that asserts `refresh` uses `GET` and `save` uses `PUT` with a body that is not nil.

```swift
func test_refresh_usesGET_withoutBody() {
    let api = MockAPIClient()
    AccountRepository(api: api).refresh(accountId: 42) { _ in }
    XCTAssertEqual(api.lastMethod, "GET")
    XCTAssertEqual(api.lastPath, "/accounts/42")
    XCTAssertNil(api.lastBody)
}
```

## 2. High: concurrent updates can overwrite each other

`save` sends a full-object `PUT` with no concurrency control: no `If-Match`/ETag and no version field that I can see. If two `save` calls overlap (a double tap, two devices, or a retry), the last write wins silently. Separately, if a `refresh` that started *before* a `save` finishes *after* it, the UI shows the old data, and the user may then save that stale copy back.

**Proposed fix**, if the backend supports ETags or a version field (to be confirmed):

```diff
-    func save(_ account: Account, completion: @escaping (Result<Account, Error>) -> Void) {
-        api.request(method: "PUT", path: "/accounts/\(account.id)", body: account.encoded(), completion: completion)
+    func save(_ account: Account, completion: @escaping (Result<Account, Error>) -> Void) {
+        api.request(method: "PUT",
+                    path: "/accounts/\(account.id)",
+                    body: account.encoded(),
+                    headers: ["If-Match": account.etag],   // or send account.version in the body
+                    completion: completion)               // handle 412 → refetch and re-apply or show a conflict
     }
```

(The `APIClient.request` signature I saw has no `headers` parameter. This diff assumes it can be extended. Adjust it to match the real client.) On the UI side, disable the Save button while a save is in flight.

## 3. Medium: no cancellation or deduplication for `refresh`

Each time the screen appears, a new request fires and nothing cancels the previous one. Rapid navigation can stack up requests, and responses can arrive out of order (an older response overwrites a newer one). This becomes worse with finding 1, because each extra call is a write.

Suggestion: return a cancellable token from `APIClient.request` (for example `URLSessionTask`), keep the in-flight refresh task, and cancel or skip a new one if one is already running. Alternatively, move to `async/await` and use `Task` cancellation.

## 4. Low: completion thread is not defined

The callers presumably update UI in `completion`. I can't tell whether `APIClient` calls it on the main thread. If it doesn't, UI updates happen off the main thread. Document the guarantee, or dispatch to main in one place (in `APIClient` or here).

## 5. Low: paths and methods are raw strings

`"PUT"` and `"GET"` are untyped strings, and both methods hand-build the same path. A small endpoint enum (`enum HTTPMethod { case get, put }`, `Endpoint.account(id)`) would make bugs like finding 1 easier to see in review and test.

## Questions I would ask (I can't ask them now)

1. **What does the backend do with `PUT /accounts/{id}` and an empty or `null` body?** Does it reject it, ignore it, or reset fields? This decides whether finding 1 is "broken refresh" or "production data loss."
2. How long has this code been in production, and do you have server logs or audits for `PUT /accounts/*`?
3. Does `GET /accounts/{id}` exist and return the same payload?
4. Does the API support ETags or versioning for optimistic concurrency?
5. Can you share `APIClient` (for its handling of a `nil` body, headers, retries, and completion thread) and the account screen's view controller or view model?
6. Is `APIClient` configured to retry automatically? Retrying a non-idempotent call or a misused `PUT` makes findings 1 and 2 worse.
