# Why some users always see "Something went wrong" on Home

## Short answer

The app shows the error message whenever the API returns **an empty list**, not only when the request fails. Users whose saved preferences (venues x categories) match no events get an empty list, so they get the error. Because their preferences don't change between visits, they get it **every time, on every list**. Users whose preferences match at least one event never see it.

So for most of these users nothing is actually failing. The app is reporting "no events for your filters" as an error.

## Evidence

Everything here comes from the two files in the fixture: `FeedLoader.swift` and `combinations.csv`. I did not run the app, call the backend or reproduce this on a device.

### 1. The code treats "empty" the same as "failed" (`FeedLoader.swift`, lines 5-8)

```swift
case .success(let events) where !events.isEmpty:
    completion(.loaded(events))
default:
    completion(.error("Something went wrong"))   // also used for an empty list
```

The `default` branch catches two different cases:
- `.failure(...)`: a real network or server error.
- `.success([])`: the request worked but returned zero events.

Both show the same "Something went wrong" message. The comment in the code says so too.

### 2. Many preference combinations return zero events (`combinations.csv`)

| venue | concerts | theatre | comedy |
|---|---|---|---|
| north-hall | 14 | **0** | 9 |
| riverside | **0** | **0** | **0** |
| old-town | 6 | **0** | 3 |

The file header says a full sweep finds about **half of all venue x category pairs at 0**.

`load` sends `prefs.venueIds` and `prefs.categoryIds` to the API. Whether a user sees the error depends only on whether their saved preferences match any events:

- **Always see the error:** e.g. a user who follows only `riverside` (0 events in every category), or only `theatre` (0 at every venue), or only `riverside` + `theatre`. They get `.success([])` every time, which shows as the error.
- **Never see the error:** e.g. a user who follows `north-hall` + `concerts` (14 events). They always get a list that isn't empty.

This matches the report exactly. The split is set by each user's preferences, not by chance, network quality or device, so the same people see it every time and the rest never do.

## Fix (proposed diff, not applied)

Add an explicit empty state and keep the error only for real failures:

```diff
 final class FeedLoader {
     func load(prefs: Preferences, completion: @escaping (FeedState) -> Void) {
         api.events(venues: prefs.venueIds, categories: prefs.categoryIds) { result in
             switch result {
-            case .success(let events) where !events.isEmpty:
-                completion(.loaded(events))
-            default:
-                completion(.error("Something went wrong"))   // also used for an empty list
+            case .success(let events) where events.isEmpty:
+                completion(.empty)
+            case .success(let events):
+                completion(.loaded(events))
+            case .failure(let error):
+                // log `error` for diagnostics; keep the user-facing text generic
+                completion(.error("Something went wrong"))
             }
         }
     }
 }
```

And in the `FeedState` definition (not in the fixture, so its exact shape is assumed):

```diff
 enum FeedState {
     case loaded([Event])
+    case empty
     case error(String)
 }
```

The Home list view then needs to handle `.empty`, for example "No events for your selected venues and categories yet" plus a way to change preferences. It should use the existing empty-state styling if there is one, so the design doesn't change. Any `switch` over `FeedState` will fail to compile until it handles `.empty`, which helps find every place that needs updating.

## How to verify the fix

1. Set preferences to `riverside` only (or `theatre` only). **Before:** "Something went wrong". **After:** the empty-state message.
2. Set preferences to `north-hall` + `concerts`. The list should load, same as before.
3. Turn on airplane mode or point at a failing endpoint. You should still see "Something went wrong" (real errors are still reported).
4. Add unit tests for `FeedLoader` with a stubbed `api` returning `.success([])` (expect `.empty`), `.success([event])` (expect `.loaded`) and `.failure` (expect `.error`).

## Open questions (what I would ask)

These don't change the root cause, but they affect how complete the fix is:

1. **How does the API combine venues and categories?** Is it all selected venues x all selected categories (a cross product), or AND/OR? This decides exactly which preference sets come back empty. A sample request/response for an affected user would confirm it.
2. **Is "every Home list" one feed or several sections?** If each Home section calls `FeedLoader` with its own filter, every section needs the empty-state handling.
3. **Can you share preferences for a couple of affected users** (or analytics on `.error` by preference set)? I'd expect them all to fall on zero-count pairs. If any affected user has preferences that *do* match events, there is a second, real failure behind this one (e.g. bad IDs being sent, auth or server errors), and that would need backend logs.
4. **Should the API return events at all for riverside / theatre?** About half of all pairs being at 0 might be real (no events scheduled) or a data or ingestion problem on the backend. The client fix is correct either way, but the content team or backend team should confirm that the zero counts are expected.
5. Product wording for the empty state, and whether to suggest broadening preferences.
