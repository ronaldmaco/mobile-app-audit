# Pre-release privacy audit: account screen and analytics

**Scope:** I reviewed the code only: `SettingsViewController.swift`, `Tracker.swift` and `ResponseStore.swift` (22 lines in total). I had no device, simulator, backend, network capture or analytics dashboard. Everything below comes from reading the code. Where a finding depends on code I could not see, I say so.

**Verdict: not ready to release.** Three issues should block the release:

1. The user's email is sent to the third-party analytics SDK as their identity.
2. The "Allow tracking" switch only changes how the app looks. Analytics keeps firing after the user turns it off.
3. All API responses, including account data, are stored as plain files in `Documents`. They are included in device backups and are not deleted at sign-out. The next person to sign in on the same device can read them.

---

## Findings

| # | Severity | Where | Problem |
|---|---|---|---|
| 1 | **Blocker** | `Tracker.swift:2` | `identify` sends `user.email` to `AnalyticsSDK` |
| 2 | **Blocker** | `Tracker.swift:3`, `SettingsViewController.swift:2-6` | The consent switch is never checked before tracking. An event fires even when the user opts out |
| 3 | **Blocker** | `ResponseStore.swift:2-4` | Every 2xx response, for any method, is written to `Documents`. No file protection, included in backups, never deleted |
| 4 | High | `SettingsViewController.swift:7-11` | Sign-out leaves the analytics identity, cached responses and the tracking preference behind |
| 5 | Medium | `SettingsViewController.swift:4` | Failures when saving the preference to the server are ignored, so the device and server can disagree |
| 6 | Medium (to check) | Project level | Privacy manifest, App Store privacy label and ATT: not in the fixture |

### 1. Email used as the analytics identity (Blocker)
`AnalyticsSDK.shared.identify(user.email)` makes the user's email the key for every event sent to a third party. As a result:
- The App Store privacy label has to declare *Email Address → Linked to user → Analytics*. If the label leaves this out, it is a review and legal risk.
- Under GDPR/CCPA, this sends direct personal data to a processor when an opaque ID would do the same job. A deletion request also has to be carried out in the analytics vendor's system.
- An email address can change, so the same person ends up split across two analytics identities.

**Fix:** identify users by an opaque server-side ID (or a salted hash generated by the server). Never send the email.

### 2. The consent switch does not control tracking (Blocker)
- `trackingSwitchChanged` writes `allowTracking` to `UserDefaults` and to the server. Nothing reads it before tracking: `Tracker.event` and `Tracker.identify` call the SDK unconditionally.
- When the user turns tracking **off**, the handler still sends `Tracker.event("tracking_toggled", ["on": false])`. That is an analytics event sent at the moment the user opts out.
- The SDK is never told to stop. If it has its own opt-out or flush mechanism, it is not used. Events already in its queue still upload.
- Default state: `bool(forKey:)` returns `false` when the key has never been set, but `Tracker` ignores the flag. So in practice tracking starts **on** before the user has made any choice. I could not see where the switch's initial state is set. If it reads `UserDefaults`, it shows "off" while tracking is actually on.

### 3. Response cache stores sensitive data badly (Blocker)
`ResponseStore.save` is "called for every 2xx response, any method". This means:
- Responses to `POST`, `PUT` and `PATCH` are written to disk. That includes sign-in and token responses, profile and account details, and anything else the account screen loads.
- The location is `Documents`. That folder is backed up to iCloud and Finder by default. It is also visible in the Files app if `UIFileSharingEnabled` or `LSSupportsOpeningDocumentsInPlace` is set (I could not check `Info.plist`).
- No `FileProtectionType` is set, so files get the default `completeUntilFirstUserAuthentication` protection. They are readable whenever the device has been unlocked once since boot.
- The code ignores `Cache-Control: no-store`, sets no expiry, and nothing ever deletes the files (see #4).
- `try?` hides all errors. As far as I can see, the `responses` directory is never created. If so, every write currently fails silently. That would hide the leak today, and the leak would appear once someone "fixes" the directory creation. **This needs checking.** I also could not see `key(request)`. If it is built from the URL and the URL carries tokens or emails in its query string, those end up in file names.

### 4. Sign-out leaves data behind (High)
`signOutTapped` deletes only the keychain token and the in-memory user. It leaves the following behind:
- **The analytics identity.** The SDK still holds the previous user's email, so the next user's events are attributed to it.
- **Cached responses** in `Documents/responses`. The next account on the device inherits the previous user's data.
- **`allowTracking`.** One user's choice silently applies to the next user.
- **The server session.** The token is not revoked on the server, so a token copied earlier stays valid (I could not see whether `api` has a logout endpoint).

`Keychain.delete` was not visible in the fixture. Keychain items survive uninstalling the app. If the app does not clear stale keychain items on first launch after a reinstall, the user could be signed back in automatically.

### 5. Preference saved locally even when the server rejects it (Medium)
`api.updatePreferences(...) { _ in }` discards the result. If the call fails (offline, 401 or 5xx), the device says "off" and the server says "on". Any server-side processing (such as server-to-server analytics or marketing) keeps going. Nothing retries the call, the switch is not reverted, and there is no error message.

### 6. Store-compliance items I could not see (to check)
- **`PrivacyInfo.xcprivacy`:** the app uses `UserDefaults`, a required-reason API, so it must declare reason `CA92.1`. `AnalyticsSDK` must ship its own privacy manifest and signature if it is on Apple's list of commonly used SDKs. `NSPrivacyTracking` and `NSPrivacyTrackingDomains` must match whatever the SDK actually does.
- **App Tracking Transparency:** if "tracking" here means tracking in Apple's sense, it needs `ATTrackingManager.requestTrackingAuthorization` and `NSUserTrackingUsageDescription`. That covers linking data with other companies' data, ads or data brokers, or reading the IDFA. An in-app switch does not replace the ATT prompt. If tracking is first-party analytics only, ATT is not required. Even then, the email in #1 must appear on the privacy label.

## Proposed changes (diffs, not applied)

The names `AnalyticsSDK.shared.optOut / optIn / reset / flush`, `user.analyticsId`, `api.signOut` and `PrivacySettings` are assumptions or new helpers. Change them to match the real SDK and API.

### ResponseStore.swift: GET only, respects no-store, protected, not backed up, deletable
```diff
 enum ResponseStore {
-    static let dir = FileManager.default.urls(for: .documentDirectory, in: .userDomainMask)[0].appendingPathComponent("responses")
-    static func save(_ data: Data, for request: URLRequest) {   // called for every 2xx response, any method
-        try? data.write(to: dir.appendingPathComponent(key(request)))
-    }
+    // Caches/ is not backed up and the OS can purge it; this data can always be fetched again.
+    static let dir = FileManager.default.urls(for: .cachesDirectory, in: .userDomainMask)[0]
+        .appendingPathComponent("responses", isDirectory: true)
+
+    static func save(_ data: Data, for request: URLRequest, response: HTTPURLResponse) {
+        guard request.httpMethod == nil || request.httpMethod == "GET" else { return }
+        let cacheControl = (response.value(forHTTPHeaderField: "Cache-Control") ?? "").lowercased()
+        guard !cacheControl.contains("no-store"), !cacheControl.contains("private") else { return }
+        do {
+            try FileManager.default.createDirectory(at: dir, withIntermediateDirectories: true)
+            // key(request) must be a hash of method + path; never put query values or tokens in file names.
+            try data.write(to: dir.appendingPathComponent(key(request)), options: [.atomic, .completeFileProtection])
+        } catch {
+            Log.error("ResponseStore write failed: \(error)")   // no response body in logs
+        }
+    }
+
+    static func clear() {
+        try? FileManager.default.removeItem(at: dir)
+    }
+
+    /// One-time migration: remove the old copy in Documents/ (backed up).
+    static func purgeLegacyLocation() {
+        let legacy = FileManager.default.urls(for: .documentDirectory, in: .userDomainMask)[0]
+            .appendingPathComponent("responses")
+        try? FileManager.default.removeItem(at: legacy)
+    }
 }
```
- Call `ResponseStore.purgeLegacyLocation()` once at app launch. Existing installs already have data in `Documents/responses`, and it is in their backups.
- Better still, have the backend mark sensitive endpoints such as `/me`, `/account`, `/auth/*` and payments as `Cache-Control: no-store`. Alternatively, keep an allow-list of endpoints that may be cached.
- Pass the `HTTPURLResponse` in at the call site (not shown in the fixture).

## How to verify once there is a device or simulator
1. **Consent:** run a fresh install, keep the switch off and use the app. A proxy (Charles or Proxyman) should show **zero** requests to the analytics host. Turn it on and events appear. Turn it off again: no `tracking_toggled` event, and the queue is not flushed afterwards.
2. **PII:** inspect the analytics payloads. No email, name or phone should appear in the identify call, events or user properties.
3. **Cache:** sign in, open the account screen, then look at the app container in Xcode (Devices → Download Container). `Documents/` should have no `responses` folder. Files in `Library/Caches/responses` should be from GET requests only, with no auth or account bodies, and should have `NSFileProtectionComplete`.
4. **Sign-out:** sign in as A, sign out, sign in as B. B sees none of A's cached data. B's analytics events go under B's ID only. A's token is rejected by the API.
5. **Sync failure:** use airplane mode and toggle off. Tracking still stops on the device and the preference syncs once the device is back online. Toggle on while offline: the switch goes back and an error is shown.
6. **Backup:** take an encrypted local backup and check that no response files are in it.
7. Check the Xcode **Privacy Report** (Product → Archive → Generate Privacy Report) against the App Store Connect privacy label.

## What I would ask you (could not ask before writing this)
1. Does "Allow tracking" mean first-party analytics only, or ATT tracking (ads, IDFA, sharing with data brokers)? This decides whether an ATT prompt is required.
2. Which analytics vendor is `AnalyticsSDK`? What are its opt-out, reset and flush APIs, and does it ship a privacy manifest?
3. Does `User` have a stable opaque ID that we can use for analytics?
4. Which endpoints actually need offline caching? Is `ResponseStore` called today, and does the `responses` directory exist on real installs?
5. Should the tracking preference apply per user or per device? What should the default be in the EU and elsewhere?
6. Does the API have a logout or token-revoke endpoint?
7. Is `UIFileSharingEnabled` or `LSSupportsOpeningDocumentsInPlace` set in `Info.plist`? Is there already a `PrivacyInfo.xcprivacy`?
8. What does the current App Store privacy label declare for analytics and email?
