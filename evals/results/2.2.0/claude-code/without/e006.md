# Crash in `KeyboardAvoiding.keyboardWillHide`: diagnosis and fix (app-a and app-b)

## Summary

- **Most likely cause:** `keyboardWillHide` force-unwraps `originalContentSize!` (line 8). The value is only set in `keyboardWillShow` and is set back to `nil` after every hide. So any `keyboardWillHide` without a matching `keyboardWillShow` before it crashes with `Unexpectedly found nil while unwrapping an Optional value`.
- **app-b has the same bug.** `app-b/KeyboardAvoiding.swift` is byte-for-byte identical to app-a's (`diff` shows no differences). It has the same crash, whether or not app-b has reported it yet. The fix below should go into both apps, or better, into one shared module.
- **Not verified on a device.** I have no crash log, device, simulator or git history. This diagnosis comes only from reading the code. The verification steps are at the end.

## Evidence (code read)

Both files: `evals/fixtures/e006/app-a/KeyboardAvoiding.swift` and `evals/fixtures/e006/app-b/KeyboardAvoiding.swift`

```swift
func keyboardWillShow(_ n: Notification) {
    originalContentSize = formScrollView.contentSize        // overwritten on every show
    formScrollView.contentSize.height += keyboardHeight(n)
}
func keyboardWillHide(_ n: Notification) {
    formScrollView.contentSize = originalContentSize!       // <-- crashes when nil
    originalContentSize = nil
}
```

### Why `originalContentSize` can be `nil` when hide runs

The code assumes show and hide always come in strict pairs. iOS does not promise that. Real ways to get a hide without a show before it:

1. **Two hides in a row.** UIKit can post `keyboardWillHide` more than once, for example during interactive dismissal (`keyboardDismissMode = .interactive`), a drag that gets cancelled, or `endEditing` followed by a resign. The first hide sets the value to `nil`, so the second one crashes.
2. **The observer is registered while the keyboard is already on screen.** Examples: a screen is pushed or presented while another screen's text field is first responder, or observers are added in `viewDidAppear`. The screen never got `willShow`, but it does get `willHide`.
3. **Hardware keyboard, iPad floating/undocked/split keyboard, Stage Manager.** Here the show and hide notifications can arrive in unexpected combinations.
4. **Several instances observe at once.** If observers are added without filtering by `object`, or are not removed when the screen disappears, a hidden screen in the navigation stack also gets the notifications.

### Second crash candidate on the same line

`formScrollView` is declared `UIScrollView!`, an implicitly unwrapped IBOutlet. If a notification arrives after the view was unloaded, or before the outlet was connected (for example, observers added in `init` or not removed on `deinit`/`viewWillDisappear`), line 8 also crashes, this time on the outlet. Only the crash log can tell the two cases apart. Without it, the fix should handle both.

### Related bug (not a crash): content keeps growing

`keyboardWillShow` can fire several times in a row without a hide in between: switching keyboard type, the QuickType bar appearing, moving focus between fields, rotation. Each time, it saves the **already enlarged** `contentSize` as the "original" and adds the keyboard height again. The form then gets more empty space at the bottom each time. This is the same pairing assumption failing the other way.

Also, setting `contentSize` by hand on a scroll view managed by Auto Layout is fragile. The next layout pass can overwrite it, and then the "restore" puts back an old size. The usual approach is to change `contentInset.bottom` and the scroll indicator insets and leave `contentSize` alone.

## Proposed fix

### Option A: minimal, low-risk fix (use this for a hotfix in both apps)

It removes the crash and the growing content, and the behaviour stays the same as today.

```diff
--- a/app-a/KeyboardAvoiding.swift
+++ b/app-a/KeyboardAvoiding.swift
@@
 protocol KeyboardAvoiding: AnyObject { var formScrollView: UIScrollView! { get }; var originalContentSize: CGSize? { get set } }
 extension KeyboardAvoiding {
     func keyboardWillShow(_ n: Notification) {
-        originalContentSize = formScrollView.contentSize
-        formScrollView.contentSize.height += keyboardHeight(n)
+        guard let scrollView = formScrollView else { return }
+        // Save the size only once per show/hide cycle, so repeated willShow calls
+        // (keyboard type change, QuickType bar, focus moves) don't add the height again.
+        let base = originalContentSize ?? scrollView.contentSize
+        originalContentSize = base
+        scrollView.contentSize = CGSize(width: base.width,
+                                        height: base.height + keyboardHeight(n))
     }
     func keyboardWillHide(_ n: Notification) {
-        formScrollView.contentSize = originalContentSize!
+        // willHide can arrive without a matching willShow (double hide, observer added while
+        // the keyboard was already up, hardware/floating keyboard). Then there is nothing to restore.
+        guard let scrollView = formScrollView, let original = originalContentSize else { return }
+        scrollView.contentSize = original
         originalContentSize = nil
     }
 }
```

Apply the same diff to `app-b/KeyboardAvoiding.swift`, which is identical.

### Option B: more robust follow-up (use insets, not `contentSize`)

This doesn't change the design. Users see the same visible result: the form scrolls above the keyboard. It also needs no saved state, so the pairing problem can't happen.

```diff
 extension KeyboardAvoiding {
     func keyboardWillShow(_ n: Notification) {
-        originalContentSize = formScrollView.contentSize
-        formScrollView.contentSize.height += keyboardHeight(n)
+        guard let scrollView = formScrollView else { return }
+        let inset = keyboardHeight(n)   // ideally: keyboard frame converted to the scroll view, minus safe area
+        scrollView.contentInset.bottom = inset
+        scrollView.verticalScrollIndicatorInsets.bottom = inset
     }
     func keyboardWillHide(_ n: Notification) {
-        formScrollView.contentSize = originalContentSize!
-        originalContentSize = nil
+        guard let scrollView = formScrollView else { return }
+        scrollView.contentInset.bottom = 0
+        scrollView.verticalScrollIndicatorInsets.bottom = 0
     }
 }
```

(The `originalContentSize` protocol requirement can then be removed from the protocol and its conforming types. If a screen already has a non-zero bottom inset, keep its base value rather than resetting to 0.) Since iOS 15, `view.keyboardLayoutGuide` is another option. It is a bigger change, so it doesn't belong in a hotfix.

### Also check (I can't see these files)

- **Observer lifecycle in the conforming view controllers.** Add observers in `viewWillAppear` and remove them in `viewWillDisappear`, or keep the tokens and remove them in `deinit`. Pass `object: nil` only on purpose. If a block-based observer captures `self` strongly, use `[weak self]`.
- **`keyboardHeight(_:)`** is not in the fixture. If it force-unwraps `userInfo[UIResponder.keyboardFrameEndUserInfoKey]`, that is the next crash candidate, because it can be missing or zero for hardware or floating keyboards. Make it return `0` when the value is missing.

### Reduce duplication

app-a and app-b each have their own copy of this file. That is why the bug exists twice, and why a fix in one app can leave the other still crashing. Move `KeyboardAvoiding` into a shared Swift package or framework that both apps use, or at least add a CI check that the two files stay identical.
