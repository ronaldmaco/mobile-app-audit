# Audit: lists that load forever and images that show the wrong picture

**Scope:** the only code available was two files in the fixture: `HTTPClient.swift` (9 lines) and `UIImageView+Remote.swift` (9 lines). I did not see the view controllers, cells, the API, a device or the backend. Everything below comes from reading the code. I have **not** reproduced it on a device. Each finding says how sure I am.

## Summary

Both symptoms can be fully explained by the code:

| # | Symptom | Root cause | File:line | Confidence |
|---|---------|-----------|-----------|------------|
| 1 | Loads forever | `completion` is never called on a network error or a decode failure, so the caller's spinner never stops | `HTTPClient.swift:3`, `:4-5` | High (certain from the code) |
| 2 | Loads forever / wrong data | HTTP status code is never checked. A 401/404/500 is either decoded as if it succeeded or (more often) fails decoding and hits #1 | `HTTPClient.swift:7` | High |
| 3 | Wrong picture | Cell reuse race. The image download is never cancelled or tied to the URL it was started for. A slow response for an old row lands in the cell after it has been reused for a new row | `UIImageView+Remote.swift:3-5` | High (the call site says "used inside reusable cells"; I did not see the cell code) |
| 4 | Wrong picture | The old image is never cleared when a new load starts, and a failed load leaves it there. A reused cell keeps the previous row's picture until the new one arrives, or for good | `UIImageView+Remote.swift:2-5` | High |
| 5 | Slow / stuck lists, more #3 | `Data(contentsOf:)` is a synchronous download. It has no cache, no cancellation and no status check, and it blocks one GCD worker per image. Fast scrolling queues many of them, which makes #3 and #4 more likely and slows everything else | `UIImageView+Remote.swift:4` | High (behaviour), Medium (how much it affects users) |

## Findings in detail

### 1. Silent failures never call `completion` (the "loads forever" bug)

```swift
if let error = error { print("request failed", error); return }   // no completion
guard let data = data, let value = try? JSONDecoder().decode(T.self, from: data) else {
    print("decode failed"); return                                  // no completion
}
```

Any timeout, lost connection, cancelled request, empty body or schema mismatch ends in `return` without calling `completion`. Callers that show a spinner and hide it in the completion handler will show it forever. The bug is intermittent because it only happens when the network or server misbehaves. It is common on cellular, captive portals, and during backend deploys. `try?` also throws away the decoding error, so neither logs nor crash reports explain what happened. The only trace is a `print` that is stripped from release logs in practice.

### 2. HTTP status is never checked

The comment on line 7 says it outright. A `500` HTML page or `{"error": "..."}` JSON either:
- fails to decode, and you get the endless spinner from #1, or
- decodes "successfully" when `T` has all-optional fields or is a lenient wrapper, so the list shows empty or wrong content.

An expired token (`401`) looks the same as a parse failure, so the app can never trigger a re-login.

### 3. Image request is not bound to the cell (the "wrong picture" bug)

```swift
DispatchQueue.global().async {
    if let data = try? Data(contentsOf: url), let image = UIImage(data: data) {
        DispatchQueue.main.async { self.image = image }
    }
}
```

The sequence:
1. Cell X shows row 3 and starts downloading `img3`, which is slow.
2. The user scrolls. Cell X is reused for row 20 and starts downloading `img20`, which is fast.
3. `img20` arrives and the cell is correct.
4. `img3` arrives later and overwrites it. **Row 20 now shows row 3's picture.**

Nothing cancels the first load, and nothing checks that the image view still wants `url` when the data arrives. Responses can arrive in any order, which is why the bug is intermittent.

### 4. Stale image is never cleared, and failures keep it

`setRemoteImage` never sets `image = nil` (or a placeholder) at the start. A reused cell therefore shows the previous row's picture until the download completes. If the download fails (bad URL, 404, offline), the old picture stays **permanently**. That is a second, independent way to get "wrong picture".

### 5. `Data(contentsOf:)` for network images

- It is synchronous. Each image ties up a GCD global-queue thread for the whole download. Fast scrolling through 100 rows can start about 100 blocked threads (thread explosion), which delays all other background work, including the JSON requests in #1.
- It cannot be cancelled, so finding #3 cannot be fixed without replacing it.
- It does not check the HTTP status, and it has no memory cache. The same image is downloaded again every time a cell scrolls back on screen, which costs data and makes the race window longer.
- `self` is captured strongly, which keeps detached cells alive until their download finishes. This is minor.

### Minor / to confirm
- **Timeouts:** `URLSession.shared` uses the request's `timeoutInterval` (60 s by default). Even after fixing #1, the user can stare at a spinner for a minute before seeing an error. Consider a session with a 15–20 s request timeout and a retry button. Whether that is right depends on your API, so this is not a bug claim.
- **Threading:** once errors are reported, all completions should be delivered on the main queue, as success already is, so UI code can stay simple.
- **Server side (not verifiable here):** "wrong picture" can *also* come from the API returning the wrong `imageURL`, or a CDN serving a cached object under a reused URL, for example when an avatar is replaced at the same path. The client bugs above are enough to explain the symptom, but see the questions below.

## Proposed changes (diffs only, nothing was modified)

### `HTTPClient.swift`

```diff
-func send<T: Decodable>(_ req: URLRequest, completion: @escaping (Result<T, Error>) -> Void) {
-    URLSession.shared.dataTask(with: req) { data, response, error in
-        if let error = error { print("request failed", error); return }
-        guard let data = data, let value = try? JSONDecoder().decode(T.self, from: data) else {
-            print("decode failed"); return
-        }
-        DispatchQueue.main.async { completion(.success(value)) }   // status code never checked
-    }.resume()
-}
+enum HTTPError: Error {
+    case transport(Error)
+    case invalidResponse
+    case status(code: Int, body: Data?)
+    case decoding(Error)
+}
+
+/// Always calls `completion` exactly once, on the main queue.
+@discardableResult
+func send<T: Decodable>(_ req: URLRequest,
+                        session: URLSession = .shared,
+                        completion: @escaping (Result<T, Error>) -> Void) -> URLSessionDataTask {
+    let task = session.dataTask(with: req) { data, response, error in
+        let result: Result<T, Error>
+        if let error = error {
+            result = .failure(HTTPError.transport(error))
+        } else if let http = response as? HTTPURLResponse {
+            if !(200..<300).contains(http.statusCode) {
+                result = .failure(HTTPError.status(code: http.statusCode, body: data))
+            } else {
+                do {
+                    result = .success(try JSONDecoder().decode(T.self, from: data ?? Data()))
+                } catch {
+                    result = .failure(HTTPError.decoding(error))
+                }
+            }
+        } else {
+            result = .failure(HTTPError.invalidResponse)
+        }
+        DispatchQueue.main.async { completion(result) }
+    }
+    task.resume()
+    return task
+}
```

This keeps the existing call sites compiling: the new parameter has a default and the return value is `@discardableResult`. **Required follow-up at the call sites:** every `case .failure` branch must stop the spinner and show an error or retry state using the screens you already have. I could not see the callers, so I cannot list them. Search for `send(` and check that each one handles `.failure`. A caller that only handles `.success` will still spin forever.

+        remoteURL = url

+        if let cached = remoteImageCache.object(forKey: url as NSURL) {

+            return

+                self.remoteTask = nil

+        task.resume()
+    }

+        remoteTask?.cancel()
+        remoteTask = nil
+        remoteURL = nil
+    }

Design note: the default `placeholder: nil` makes the image view blank while it loads, instead of showing the *previous row's* image. If the design already has a placeholder asset, pass it. I did not add any new visual.

Alternative: if the project already depends on Kingfisher, SDWebImage or Nuke, or would accept one, `imageView.kf.setImage(with:)` and similar calls handle cancellation, reuse and caching correctly. That is a bigger change, so it is your call.

## How to verify (I could not run any of this)

1. **Unit tests for `send` with a stub `URLProtocol`:** assert that `completion` is called **exactly once** for each of: transport error, 500 with an HTML body, 401, 200 with malformed JSON, 200 with valid JSON. Each test fails on the current code because the completion never fires.
2. **Image race test:** stub URL A with a 2 s delay and URL B with no delay. Call `setRemoteImage(A)` and then `setRemoteImage(B)` on the same image view, wait 3 s, and assert that the image is B's. It fails today and should pass with the fix.
3. **Manual on device:** use Network Link Conditioner with "Very Bad Network" or 100% loss, and check that the list shows an error and retry option instead of spinning forever. Fling-scroll a long list on 3G, then stop, and check that every visible row's image matches its item (log `remoteURL` against the item ID if that helps). Turn on Airplane Mode in the middle of a load.
4. **Regression:** check pull-to-refresh and pagination, which probably share `send`, and any screen where several requests run at once.
