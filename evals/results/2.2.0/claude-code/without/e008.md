# Bug verification: "Saving the profile does not work"

## Verdict: not reproduced, and not ruled out either

I could not confirm this bug, and I can't call it a false report. The evidence doesn't settle it either way.

| Check | Result | What it tells us |
|---|---|---|
| User report | "Saving my profile doesn't work, I tried yesterday." No video, device, OS, app version, or fields that were changed. | It doesn't say what "doesn't work" means: an error, no response, a spinner that never stops, or changes that are later lost. |
| Code path (as described in the fixture) | `EditProfileViewController.save()` disables the button, sends `PATCH /profile`, updates the session user and closes on success, and shows the server error and re-enables the button on failure. | The happy path and the server-error path look correct on paper. This is a summary, not the source, so I have not reviewed the real code line by line. |
| API probe (test account) | `PATCH /profile` with "the same body" returns 200, and `GET /profile` shows the new values. | The backend works for **that** body on **that** account **now**. It says nothing about this user's data, account, or what happened yesterday. |
| Device test | Not run. No device or simulator was available. | The real UI flow has not been checked end to end. |

**Status: Unconfirmed / needs info.** I would not close it as "works as intended" yet.

## Why the 200 from the API is not enough

1. **"Same body" is not the user's body.** We don't know which fields the user changed. Validation that depends on the field or value (email format or uniqueness, phone, very long names, emoji, an empty optional field sent as `""` or `null`, an avatar upload) could still fail for them.
2. **Different account and time.** The user tried yesterday. A backend deploy, an outage, an expired token (401), or rate limiting could have hit them and not us. Backend logs for that user and day would answer this. I have no access to them.
3. **Paths the described code may not handle.** The summary only mentions "success" and "server error". If any of these fall through, the screen could look stuck or silently do nothing:
   - a network failure or timeout, with no HTTP response;
   - a non-2xx response with a body that doesn't decode into the expected error model;
   - a 401 or token refresh during the save;
   - a 2xx response with an unexpected payload, so decoding the updated user fails;
   - the completion running off the main thread, so the UI never updates.

   Any of these could leave the button disabled with no message, which a user would describe as "save doesn't work".
4. **The save may succeed but appear not to.** On success the app updates the *session user* and closes. If the profile screen (or another screen) reads a cached copy or stale local storage instead of the session user, or if a later app launch reloads an old cached profile, the user sees the old values and reasonably concludes the save failed. Our `GET /profile` check skips the app's display layer completely.
5. **Version.** We don't know which app version the user has. An older build may have different save code from the one described.

## What I would ask the user

- Which app version and device/OS are you on? (Settings > About, or the store page.)
- Which fields did you change? Did you change your photo?
- What exactly happened after you tapped Save: an error message (what did it say?), nothing at all, a button that stayed greyed out, or the screen closed but the old values came back (right away, or after reopening the app)?
- Does it still happen today? Were you on Wi-Fi or mobile data, or offline?
- Could you send a screen recording of it happening?

## Summary

The backend accepts a profile update for a test account today, and the code as described looks correct. The user's report has not been reproduced, and it hasn't been disproved. The likeliest explanations are a value-specific validation failure, a transient problem yesterday, an unhandled non-server error path, or a successful save that the UI shows stale. I need the answers and logs above to tell these apart.
