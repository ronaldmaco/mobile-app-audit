## Findings

### A1 [High] Venue ids of 0 are dropped, so the venue filter becomes "any venue"
Status: Verified (in code; not run)
Where: `VenueFilter.kt:3-4` (`filter { it != 0 }`), used by `FeedRepository.loadHome` at `VenueFilter.kt:9`
What the user sees: the user picks a venue and gets events from every venue instead.
Cause: `venueIdsForRequest` removes every id 0 to skip "No favourite venue". Real venues that the server could not map also have id 0 (the sentinel collision fixed on iOS), so they are removed without telling the user. If every selected venue has id 0, the list is empty, `api.search` gets no `venueIds`, and the API ignores the venue filter.
Trigger: the selection contains only id-0 venues (a real but unmapped venue, and/or "No favourite venue"). With mixed selections the id-0 venues are just lost.
Impact map (from code):
- Valid ids only: OK.
- Mixed valid + id 0: fails. The id-0 venue is silently dropped.
- Only id 0: fails. Empty list goes out and the result is unfiltered.
- "No favourite venue" only: needs a decision. Today it means "any", which may be what you want on Home but not on an explicit filter.
- Consumers: only Home (`loadHome`) is in the excerpt. The filter screen, chips, favourites and onboarding were **not checked** (not in the excerpt). Grep every caller of `venueIdsForRequest` and every `it.id != 0` / `id == 0`.
- Stored preferences from older versions, and the other account / logged-out states: not tested (no device).
Fix (port iOS): match selected venues by id, or by normalised name when the id is 0. Do not drop real venues. Treat "No favourite venue" as its own explicit flag, not as id 0. If every selected venue has no linked events, show the existing empty state (explicit filter) instead of calling the API without `venueIds`. No visual change.
Review gate: the fix must not make an empty `venueIds` reach the API by another path. That is the exact way the old filter failed.
Test: JUnit on `venueIdsForRequest` / the new matcher covering [valid], [valid, 0], [0], ["no favourite"], and an assertion that `search` is never called with an empty venue list when venues were selected.
Backend owner: real venues coming back with id 0 is orphan/unmapped data. Ask the backend/CMS team to fix the mapping too (same item as on iOS).

### A2 [High] Home shows "No results" everywhere instead of falling back
Status: Verified (in code; not run)
Where: `VenueFilter.kt:8-11` (`FeedRepository.loadHome`)
What the user sees: with preferences that have no matching events, every Home section says "No results".
Cause: `loadHome` makes one request with venues + categories and passes the list straight through (`onResult(events)`). There is no widening when the list is empty. This also mixes up two cases: an empty result is shown like a failure ("Empty result shown as an error").
Trigger: any venue/category combination with no events (more likely after A1 is fixed, because the filter will then actually narrow results).
Fix (port iOS): on an empty list, retry with venues + category, then venues only, then no preferences, in that documented order. Keep the honest empty state only after the last step. Home is a curated feed, so widening is allowed here. An explicit filter screen must *not* widen (see A1).
Test: JUnit with a fake `EventsApi` that returns empty for the first N calls, asserting the order of queries and the final list.
Not covered: error vs empty handling. The callback has no error path in the excerpt, so a network failure may also show as "No results" or as nothing. Suspected, check `EventsApi.search`.

### A3 [Medium] Tracking switch: event logged before save, save result ignored, no revert
Status: Verified (in code; not run)
Where: `SettingsFragment.kt:2-5`
What the user sees: the switch shows the new value even when the save failed, so the next launch shows the old value. Analytics records a change that never happened.
Cause: `Tracker.event("tracking_toggled", ...)` runs before `profileRepository.update(allowTracking = isOn)`, and the update's result is ignored (`// result ignored`). There is no revert on failure. It is an optimistic change with no confirmation.
Trigger: toggle while offline, on timeout or on a server error.
Fix (port iOS): wait for the `update` result. On success, log the event. On failure, set the switch back (without firing the listener again) and show the existing error message. Same layout.
Privacy note (Suspected, check): a tracking/consent switch that only saves to the profile may never reach the analytics SDK ("Consent not reaching the SDK"). Check that `Tracker` stops sending events when `allowTracking` is false, on both platforms. Logging "tracking_toggled" when the user turns tracking **off** is itself questionable.
Test: unit test with a failing fake repository: switch state is reverted and `Tracker.event` is not called. A success case logs exactly once.

### A4 [-] Late images in reused rows: probably handled by the library
Status: Suspected OK (not applicable if confirmed)
Where: `VenueFilter.kt:1` (comment: the image library cancels the previous request when a view is reused)
Reasoning: libraries such as Glide/Coil/Picasso cancel or ignore the old request when the same target view gets a new load, so the iOS bug's mechanism does not apply. Port nothing for now.
To confirm: grep the adapters for image loads that bypass the library's view target (a custom callback/`Target` that sets the bitmap manually, `into(object : CustomTarget…)`, `setImageBitmap` from a coroutine). Those are not cancelled and would bring the bug back. Then scroll fast on a slow network (device test) once.
