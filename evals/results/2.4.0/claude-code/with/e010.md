# List screen: Saved tab shows the All list, and the list never loads after a network error

## Summary
- **Mode:** A (bug verification), limited to static code review. I had one file, `ListFragment.kt`. It does not build, and there is no device, backend, git history or repository implementation. Every finding below comes from reading the code and tracing a concrete event order. I did not reproduce anything on a device.
- **Answer in short:** both symptoms come from the single `isFetching` flag in `ListFragment.load()` (lines 10-20).
  1. **After an error, the list never loads again.** `isFetching` is set back to `false` only in `onSuccess` (line 15), never in `onError` (line 19). After one failed request the flag stays `true`, so every later `load()` returns at line 11. No request goes out and no error appears. The screen is frozen until the fragment is recreated.
  2. **The Saved tab shows the All list.** Two guards work against each other. The "already loading" guard (line 11) **rejects the new query**. The "not current" guard (line 16) then **drops the old answer**. Nothing reloads the tab the user picked, so the adapter keeps showing the previous list (All) under the Saved tab. Finding 1 causes the same symptom: once the flag is stuck, switching to Saved does nothing and the All list stays on screen.
- **Assumptions:** `repository.fetch` calls exactly one of `onSuccess` / `onError` per request, on the main thread. Tab taps reach `onTabSelected`. A refresh (re-selecting a tab, pull-to-refresh, or the first load) also goes through `load()`. These callers are not in the excerpt.

## Findings

### F1 [High] After one failed request, the list never loads again
- **Status:** Verified in code (concrete trigger below). Not reproduced on a device.
- **Where:** `ListFragment.kt:12` sets `isFetching = true`; `:15` resets it only on success; `:19` `onError = { showError() }` never resets it; `:11` `if (isFetching) return`.
- **What the user sees:** after one network error, the list does not load on any tab. Tapping All or Saved does nothing: no spinner, no new error, no data.
- **Cause:** a loading flag that only a success clears (skill pattern *Flag reset only on success*). Once a request fails, `isFetching` stays `true` for the life of the fragment instance. Every later `load()` exits at line 11 before calling the repository.
- **Trigger:** any request that ends in `onError`: offline, timeout, DNS failure, a 5xx, or a parse error. Timeouts and offline have no response body, so they are the most likely path. After that, any `load()` call.
- **Evidence (trace):** `load(ALL)` sets `isFetching = true` → request → `onError` → `showError()` (flag still `true`) → user taps Saved → `onTabSelected` sets `currentQuery = SAVED` → `load(SAVED)` → line 11 returns. Same for every later tap or refresh.
- **Extra effect:** a fragment kept on the back stack keeps the same instance and the flag with it. So the screen can stay stuck even after the view is recreated. Only a new fragment instance (process death, a new navigation entry) recovers.

### F2 [High] Switching tabs while a request is in flight leaves the wrong list on screen (Saved shows All)
- **Status:** Verified in code (concrete trigger below). Not reproduced on a device.
- **Where:** `ListFragment.kt:6-7` (tab change updates `currentQuery` and calls `load`), `:11` (refuses the new query), `:16` (drops the old answer).
- **What the user sees:** the Saved tab is selected, but the list shows All. Sometimes it is the other way round. It happens "sometimes" because it depends on whether a request is still running when the user taps.
- **Cause:** *Refuse-new plus drop-stale guards*. The "already loading" check rejects the request for the newly selected tab. The "not current" check discards the answer that was in flight. Nobody fetches the selected tab afterwards, so the adapter keeps its previous contents.
- **Trigger (main one):**
  1. The All list is on screen. A refresh of All starts (re-select, pull-to-refresh or first load), so `isFetching = true`.
  2. The user taps Saved before it returns: `currentQuery = SAVED`, and `load(SAVED)` is refused at line 11.
  3. The All answer arrives: `isFetching = false`, `query (ALL) != currentQuery (SAVED)`, so it is dropped at line 16.
  4. Result: the Saved tab shows the old All list, and nothing loads Saved.
- **Other triggers:**
  - Saved request in flight, user taps All: the All tab keeps showing Saved.
  - Quick All → Saved → All: the middle request is refused, the first answer is dropped, and the selected tab shows the wrong or stale data.
  - Any tab change after F1 has happened: the old list stays under the new tab.
- **Related (same root):** `onError` (line 19) does not check `query != currentQuery`. A late failure from the tab the user already left shows an error on the tab they are looking at now. Status: Verified in code.

### F3 [Medium, Suspected] Callbacks may touch the view after it is gone
- **Where:** `ListFragment.kt:17` (`adapter.submit`), `:19` (`showError()`).
- **Concern:** nothing cancels the request or checks the view lifecycle. If the user leaves the screen while a request is in flight, the callback can update a destroyed view. It can also leak the fragment until the callback runs. Whether this crashes depends on the `repository` and `adapter` code, which I could not see. That is why this is Suspected.

## Proposed fix (not applied; needs your approval)

This is the smallest change at the cause, with no visual change. Replace the boolean with a request token so that the **newest request always wins**, and both outcomes are handled the same way:

```kotlin
private var currentQuery: Query = Query.ALL
private var requestId = 0

private fun load(query: Query) {
    val id = ++requestId            // newest request wins; never refuse a new one
    repository.fetch(query,
        onSuccess = { items ->
            if (id != requestId) return@fetch   // stale answer: ignore
            adapter.submit(items)
        },
        onError = {
            if (id != requestId) return@fetch   // stale failure: ignore
            showError()
        })
}
```

If the repository can cancel a request, also cancel the previous one. With coroutines, use a `Job` that you cancel, or `collectLatest` in a ViewModel tied to `viewLifecycleOwner`, which also fixes F3.

**Review gate:**
- **Hides any user choice or server value?** No. Today the user's tab choice is dropped silently. After the fix the selected tab always gets its own data or an honest error.
- **Empty value:** an empty Saved result must show the existing empty state, not the All list. Nothing in this change widens the query.
- **Rows that change:** all the F1 and F2 rows become correct. The "nothing in flight" row is unchanged.
- **Retry:** after an error, the next tap or refresh sends a request again. If the screen has an existing retry button in `showError()`, it now works. The layout and copy stay the same.
- **Backend change needed?** No.
