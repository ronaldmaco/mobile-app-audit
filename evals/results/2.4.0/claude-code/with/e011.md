# Network layer audit: offline likes lost, screens spinning forever

## 1. Summary

**Mode:** A (bug verification) for the two reports, scoped to the network layer as a C (targeted audit) of `NetworkService.send`.

**How it was checked:** static code review of `NetworkService.kt` only. The excerpt does not build. I had no device, no backend and no git history, so nothing was reproduced at runtime and there is no API oracle. Both reported symptoms trace to concrete lines with a concrete trigger. For that reason the two main findings are **Verified in code**, and they still need a reproduction on a device (section 4).

**Assumptions (not visible in the excerpt):**
- `http.execute` calls back with `error != null` for transport failures (offline, timeout, DNS, TLS). For those failures `error.response` is `null`.
- `request.key` identifies the endpoint/resource (for example `/items/{id}/like`). It may not include the HTTP method or body.
- Every screen's loading state ends only when `onSuccess` or `onError` is called. That is the usual contract.
- `ResponseCache` is a persistent cache that survives restarts. Liking the same item before is enough to fill the cache for that key.

**Answer in two sentences:** Offline likes "look saved" because, when the POST/PUT fails, `send` returns an old cached body as `onSuccess` (line 9-12). The write never reaches the server and is never queued, so it is lost. Screens "spin forever" because a failure with no response body (offline, timeout) calls neither `onSuccess` nor `onError` (line 14).

## 2. Findings (most severe first)

### F1 [Critical] A failed write is reported as success from the cache: offline likes are silently lost
- **Status:** Verified (in code, with a concrete trigger). Not yet reproduced on a device.
- **Where:** `NetworkService.kt:9-12` (cache fallback for every method, as the comment on line 11 says), and `NetworkService.kt:5` (write responses are cached too).
- **What the user sees:** They tap like while offline (or on a flaky network). The heart stays filled and no error appears. Later, after a refresh, on another device, or after reinstall, the like is gone.
- **Cause:** On any error, `send` looks up `cache.get(request.key)`. If anything was cached for that key, it calls `onSuccess(parse(cached))`. That happens whether the request was a GET or a POST/PUT. Line 5 also stores the response body of successful writes, so any earlier like/unlike of the item (or a GET that shares the key) fills the cache. The caller cannot tell a confirmed write from a replayed old response. It keeps the optimistic state and never retries, and there is no outbox, so the write is dropped. This is the "Cache returned as success" pattern.
- **Aggravating:** The cached body can be stale or even opposite. For example, it may be the response of an earlier *unlike* when `request.key` does not include the method or body (Suspected; key construction not in the excerpt). Parsed as success, it can also overwrite the local liked state with old server data.
- **Trigger:** The device is offline, the request times out, or the server returns an error, AND a body for `request.key` exists in the cache from an earlier call.
- **Without a cached entry:** For a first like on an item with no cache, the request falls through to line 14. Offline it then hits F2 (no callback at all), so the like button spins or stays in its optimistic state with no error. The like is lost either way.
- **Impact map:**

  | Row | Expected | Current |
  |---|---|---|
  | Like, online | saved on server, UI liked | OK |
  | Like, offline, cache present | error or queued + visible "pending", UI reverts or marks pending | **fails**: false success, data lost |
  | Like, offline, no cache | error, UI reverts | **fails**: no callback (F2) |
  | Like, server 5xx with body, cache present | error | **fails**: false success |
  | Unlike, same rows | same as like | **fails** (same code path) |
  | Any other POST/PUT/PATCH/DELETE (profile save, settings, comments, follows...) | error, input kept | **fails**: same path; not enumerated (callers not in excerpt) |
  | After app kill / relaunch | server state wins, no phantom like | **fails**: like never sent |
  | Other account on same device | no data from previous user | not tested: cache keying/clearing not in excerpt (Suspected per-user leak if key has no user id) |

- **Fix (proposed, not applied):** Allow the cache fallback only for safe reads (GET). Never let a write fall back to the cache. Do not cache write responses. Pass the cached read to the caller as **stale** together with the error, so the screen can still say "offline".
  ```kotlin
  val isRead = request.method == Method.GET
  if (error == null) {
      if (isRead) cache.put(request.key, response.body)
      deliver { onSuccess(parse(response.body)) }
      return@execute
  }
  val cached = if (isRead) cache.get(request.key) else null
  if (cached != null) {
      deliver { onSuccess(parse(cached)) }   // ideally onSuccess(value, stale = true) plus a non-blocking offline notice
      return@execute
  }
  onError(error.response?.body?.let(ApiError::from) ?: ApiError.network(error))
  ```
  The like screen must revert the optimistic state (or show the existing failure message) on `onError`. **Review gate:**
  - User input: nothing the user chose is hidden. A failed like now shows as failed instead of fake-saved.
  - Visual change: none beyond the existing error/revert states.
  - Other GETs: they still get offline content from the cache.
  - Product decision: if likes must work offline, a durable outbox is needed (for example WorkManager with a unique, idempotent job per item: `like`/`unlike` as the final desired state, not a toggle). That is a behaviour addition to propose, not a silent change. The server endpoint should be idempotent (PUT like / DELETE like), so that retries are safe.
- **Test:** JUnit with a fake `http` and an in-memory cache:
  1. Pre-fill the cache for a POST key, fail the POST with a transport error. Assert `onError` is called once and `onSuccess` never.
  2. A successful POST does not write to the cache.
  3. A GET with cache plus error returns the cached value (marked stale).
- **Also in:** every write endpoint that uses `send`. List them with `grep -rn "\.send(" app/src --include=*.kt` and check each caller's method. Check the other platform (iOS) network layer for the same "fallback to cache on error" logic (not provided here).
- **Delivery:** app build. Also clear write entries already persisted in the cache (on upgrade, or by bumping the cache version), because old builds have already cached write responses.

### F2 [High] Failures without a response body never call back: screens spin forever
- **Status:** Verified (in code, with a concrete trigger). Not yet reproduced on a device.
- **Where:** `NetworkService.kt:14`.
- **What the user sees:** Offline, or on a timeout, the spinner never stops, with no message and no retry, unless the same key happened to be cached.
- **Cause:** `error.response?.body?.let { onError(...) }` only reports errors that have a body. Offline, DNS failure, connection reset, TLS failure and timeouts have no response, so `response` is null and the `let` does nothing. Neither callback fires, and the caller's loading flag is never cleared. This is the "Errors without a body vanish" pattern. If callers also guard with an "already loading" flag, it becomes the "Flag reset only on success" pattern, and every later pull-to-refresh is also blocked until the screen is recreated (Suspected; callers not in excerpt).
- **Trigger:** Any request with no cache entry that fails at transport level. Also any HTTP error whose body is null or empty (for example 204/502 from a proxy with no body).
- **Impact map:**

  | Row | Expected | Current |
  |---|---|---|
  | GET, offline, no cache | error + retry | **fails**: no callback |
  | GET, timeout, no cache | error + retry | **fails**: no callback |
  | GET, 5xx with JSON body | error | OK |
  | GET, 5xx/502 with empty body | error | **fails**: no callback |
  | Write, offline (no cache) | error, UI reverted | **fails**: no callback |
  | Retry after the failure | new load runs | not tested: depends on caller flags (Suspected blocked) |

- **Fix:** Always call `onError`. When there is no body, call it with a network error type (`ApiError.network(error)` / `ApiError.timeout`, mapped to the app's existing offline message). See the snippet in F1, last line. No visual change: the screens' existing error state is shown instead of an endless spinner.
- **Test:** A fake transport error with `response = null` and an empty cache. Assert `onError` is called exactly once. Add the same case for a timeout and for an HTTP error with an empty body.
- **Also in:** callers that clear `isLoading` only in `onSuccess`. Grep for loading flags (`isLoading`, `loading.value = `) next to each `.send(` call and confirm that they are cleared in `onError`.

### F3 [Medium] Parse errors escape the callback: spinner or crash
- **Status:** Suspected (the behaviour depends on the `http` callback thread and on how it handles exceptions; neither is in the excerpt).
- **Where:** `NetworkService.kt:6` and `:11`.
- **What the user sees:** An unexpected payload (HTML from a captive portal, WAF or proxy, a changed schema, or a cached body from an older app version) causes either a crash or a spinner that never stops.
- **Cause:** `parse(...)` runs outside any try/catch. If it throws, `onSuccess` is never reached and `onError` is never called. On line 5 the bad body is cached *before* parsing, so the same failure repeats from the cache on every later offline load ("Bad local data survives updates").
- **Fix:** Wrap the parse. On failure, call `onError(ApiError.parse(...))`. Cache only after a successful parse, and only for GET. Version the cache, so that a schema change drops old entries.
- **Test:** A fake response with body `"<html>"` must call `onError` once and must not cache.

### F4 [Medium] Cached data is presented as fresh, with no stale signal
- **Status:** Verified in code (line 11 calls the same `onSuccess` as a live response).
- **What the user sees:** Offline, a list shows old counts or old like states as if they were current, with no "offline" hint. After reconnecting, values jump.
- **Fix:** Pass a `stale`/`fromCache` flag (or call both `onSuccess(cached)` and a non-blocking offline notice). The UI can then keep the same layout and show the existing offline message.
- **Related, not tested:**
  - Whether `ResponseCache` keys include the user and whether the cache is cleared on logout (per-user data leak to the next account).
  - Whether the cache lives in a non-backed-up location (`cacheDir`).
  - Whether `http` sets a timeout. Without one, "spins forever" can also come from a request that never fails.

### Notes, not tested (outside the excerpt)
- **Double callback:** within `send` each path returns once, so no double callback was seen. If `http.execute` can call back twice (for example on retry), add a "first answer wins" guard.
- **Callback thread:** check that UI updates are posted to the main thread and that callbacks are dropped when the screen is gone (lifecycle-aware scope). Otherwise a late response can crash or update a dead view.

## 4. How to reproduce and verify on a device (not done here)

**Like lost (F1):**
1. Online, like then unlike item X. This fills the cache for its key.
2. Disconnect: `adb shell svc wifi disable && adb shell svc data disable` (or airplane mode).
3. Like X. Expected now: the heart stays filled, no error.
4. Reconnect and force-stop: `adb shell am force-stop <package>`. Relaunch.
5. Check server truth with the same request the app sends for the item (curl GET of item X with a test account token kept in an env var, printing only the `liked` field). Expected now: not liked, so the bug is confirmed.
6. After the fix: step 3 shows the existing error and reverts the heart (or shows it as pending, if an outbox is approved). Step 5 matches the screen.

**Endless spinner (F2):**
1. Fresh install, or clear data (`adb shell pm clear <package>`) so the cache is empty.
2. Go offline and open any list screen. Expected now: it spins forever.
3. Also test with a slow or blackholed network (an emulator with `-netdelay`/`-netspeed`, or a proxy that drops the connection) to hit a timeout. Then pull to refresh after reconnecting, to see whether a stuck loading flag blocks the retry.
4. After the fix: the error appears within the timeout, and retry works.

Run each 5+ times. Run the final pass on the **release** build.

## 5. Fix order and delivery
1. **F2:** always call `onError`. This is a one-line change that removes every endless spinner, and it is a prerequisite for F1's error path.
2. **F1:** no cache fallback or caching for writes. The like screen reverts on error. Decide with product whether offline likes need a durable outbox.
3. **F3:** guard the parse, and cache only after a successful parse.
4. **F4:** add a stale flag.

**Delivery:**
- A new app build that clears or versions the persistent cache, so write responses already stored by old builds are dropped.
- The same check on the iOS app, if it shares the backend.
- Ask the backend owner to make like/unlike idempotent (set-state, not toggle), so that retries and an outbox are safe.
- Tell users which version contains the fix. Likes already lost offline cannot be recovered from the client, because they never left the device.
