# Promoted card: wrong item opened, and Home crash on open

## Summary

- **Mode:** A, bug verification (two user reports on the Home promoted card).
- **Scope:** `e012/PromotedItemService.kt` (`PromotedItemService` and `HomeFragment.bindPromoted`). This is a code excerpt only.
- **How it was checked:** static code review only. There is no build, device, backend or git history, so I could not reproduce on a device, call the API as an oracle, read crash telemetry or check earlier fixes (2.2).
- **Assumptions:** `catalog.promotable` is a `List<Item>` that can be empty (catalog not loaded yet, offline, or nothing promotable on the server). `owned` is the user's owned items. `random()` is Kotlin's `Collection.random()`.
- **Result:** both reports come from one cause, the same line. `promotedItem` is a computed property that calls `random()` every time something reads it.
  1. The card's title and its click handler each read the property, so each gets its own random item. That is the "opens a different item" report.
  2. `random()` on an empty list throws, so Home crashes in `bindPromoted()` when nothing is left to promote. That is the "Home crashes on open" report.

Both findings are **Verified in code**, because each has a concrete trigger. They are **not reproduced on a device**.

## Findings

### F1 [Critical] Home crashes on open when no promotable item is left
- **Status:** Verified in code, with a concrete trigger. Not reproduced on a device. No crash log available.
- **Where:** `PromotedItemService.kt:3` (`.random()`), called from `HomeFragment.bindPromoted()` at `PromotedItemService.kt:8`.
- **What the user sees:** the app closes as soon as Home opens. If Home is the start screen, the app will not open again until the data changes.
- **Cause:** `List.random()` throws `NoSuchElementException("Collection is empty.")` when the list is empty. Nothing catches it on the main thread, so the app crashes.
- **Trigger:** the filtered list is empty in any of these cases:
  - the user owns every promotable item (likely for heavy users, which fits "one user");
  - `catalog.promotable` is empty because the catalog has not loaded yet (cold start, offline, request failed);
  - the server or CMS currently promotes nothing.
- **Evidence:** line 3 calls `filterNot { owned.contains(it.id) }.random()` with no empty check. Line 8 reads it synchronously while Home binds.
- **To confirm on the reporter's data:** get a crash trace showing `NoSuchElementException` at `PromotedItemService.getPromotedItem` (store or crash console, see `references/store-and-telemetry.md`). Compare the reporter's owned items with the promotable list the API returns for their account and region.
- **Fix (proposed, needs approval):** pick with `randomOrNull()`. When the result is null, do not show a promoted item and do not crash.
  - Because the card's empty state is a design decision, I propose hiding the card (or showing the existing empty or placeholder state if there is one). Please decide.
  - If the empty list comes from a catalog that is not loaded yet, bind after load and show the normal loading state. Do not crash, and do not show a stale or made-up item.
- **Review gate:** the fix hides no user choice or server value. "No item to promote" is shown honestly as no card. No backend change is needed, unless an empty promotable list for every user is itself a data problem (owner: backend/CMS).
- **Test:** JUnit test. With a fake catalog where every item is owned, and another with an empty catalog, `bindPromoted()` / the service must not throw and must return null. It fails before the fix and passes after.

### F2 [High] Promoted card opens a different item than the one it shows
- **Status:** Verified in code, with a concrete trigger. Not reproduced on a device.
- **Where:** `PromotedItemService.kt:2-3` (a non-deterministic getter). It is read twice, at `:8` (title) and `:9` (click).
- **What the user sees:** the card shows item A, and tapping it opens item B.
- **Cause:** `promotedItem` has a custom `get()` and no stored value, so every read runs `random()` again.
  - Line 8 takes the title from one random pick.
  - The lambda at line 9 reads `service.promotedItem` again *at tap time*, which is a new random pick.
  - This is the "non-deterministic getter" pattern from the skill.
- **Trigger:** any tap when two or more items are eligible. The chance of a mismatch is `1 - 1/n` for n eligible items, so it is "sometimes" with few items and nearly always with many. With exactly one eligible item, it always matches, which explains why only some users see it.
- **Secondary effects of the same cause:**
  - **Crash on tap.** If the user comes to own the last eligible item (for example, buys it and comes back), the tap-time read can hit an empty list and crash on tap. This is a second path to F1.
  - **Changing card.** The card changes item on every rebind (rotation, returning to Home, recreating the Fragment). That is fine for "rotating promotion" but cannot be tracked.
  - **Analytics.** Any impression or analytics code that also reads `promotedItem` would log a third item. This is not visible in the excerpt.
- **Fix (proposed, needs approval):** pick once per bind and use that same object for both the title and the click:
  ```kotlin
  fun pickPromoted(): Item? = catalog.promotable.filterNot { owned.contains(it.id) }.randomOrNull()

  fun bindPromoted() {
      val item = service.pickPromoted() ?: run { /* hide card / empty state, see F1 */ return }
      promotedCard.title.text = item.title
      promotedCard.setOnClickListener { openItem(item.id) }
  }
  ```
  - Replace the property with a function so that callers can see it is non-deterministic.
  - If the pick should survive rotation, keep the chosen item id in the ViewModel or `SavedStateHandle`.
  - The layout, copy and navigation stay the same.
- **Review gate:** the fix drops no value. The item opened becomes the item shown.
- **Test:** JUnit with a seeded `Random` or a fake that returns a different item on each call. The id passed to `openItem` must equal the id of the item whose title is bound. It fails before the fix and passes after.

## Fix order and delivery
1. **F1** (crash): `randomOrNull()` plus the empty or loading handling. This blocks Home for affected users.
2. **F2** (wrong item): pick once and bind the same object. This is the same change set, so ship both together.
3. Add the two regression tests. First confirm that the unit-test target builds.
4. Delivery:
   - a new release build above the current store build number;
   - the same fix on iOS or sibling apps if the pattern exists there.
   - No backend change is needed unless the promotable list itself is empty or wrong.
   - Tell both reporters which version contains the fix.
