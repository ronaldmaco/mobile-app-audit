# Analytics audit: wrong `item_opened` titles from search

## 1. Summary

- **Mode:** C, a targeted audit of analytics event building and logging. I used the bug-verification steps (root cause, impact map, review gate) because a symptom was reported.
- **Scope:** `AnalyticsEvent.kt`, an excerpt that holds the `AnalyticsEvent` enum, the calls from `ItemDetailFragment` and `SearchFragment`, and `Analytics.log`.
- **How it was checked:** static code review only. The excerpt does not build, and there is no device, backend, analytics dashboard or git history. Every finding is therefore **Verified in code with a concrete trigger** and has not been reproduced on a device. The history check (2.2) was not possible.
- **Assumptions:**
  - Your dashboard marks an event as "from search" by something other than the `screen` param, for example a session funnel or the previous screen. Section 2, F1 explains why `screen` itself is also wrong.
  - `Analytics.log` sends the event at once or copies the map. If the SDK reads the values later, the race in F2 gets worse.
- **Not covered:** other events and screens outside the excerpt, the iOS app or sibling apps, and the SDK's consent and threading setup.

## 2. Findings

### F1 [High] Search `item_opened` reports the title (and `screen`) of the last item opened on the detail screen
**Status:** Verified (code, concrete trigger)

**Where:**
- `AnalyticsEvent.kt:5-6` (`var title` and `var screen` on the enum)
- `AnalyticsEvent.kt:10` (detail sets them)
- `AnalyticsEvent.kt:13` (search sets nothing)
- `AnalyticsEvent.kt:17` (log reads them)

**What the user sees (the analyst):** an `item_opened` event logged from search carries the title of a different item, which the user opened earlier from the detail screen. It also carries `screen = "detail"`.

**Cause:** the enum stores the event's context as mutable properties. This is the "mutable shared constants as context" pattern. An enum constant is a single object for the whole process, so `ITEM_OPENED.title` and `ITEM_OPENED.screen` act as global variables:
- `ItemDetailFragment.onItemOpened` writes `title = item.title` and `screen = "detail"` into that global object and never clears them.
- `SearchFragment.onResultOpened(item)` ignores its `item` parameter and logs `ITEM_OPENED` as it is.
- `Analytics.log` then reads whatever values the last caller left behind.

**Trigger:**
1. Open item A from the detail path, which logs `item_opened{title=A, screen=detail}`.
2. Go to search and open result B.
3. The app logs `item_opened{title=A, screen=detail}`. The correct event is `{title=B, screen=search}`.

If the user opens a search result before any detail open in the same process, the event has `title=null, screen=null` instead. The data is wrong in both cases.

**Impact on data:**
- Search opens carry wrong titles.
- Search opens are counted under `screen=detail`, which inflates detail and hides search in any breakdown by screen.
- Item rankings that use `item_opened.title` are skewed toward items that were opened from detail.

**Fix (proposed, needs your approval):** make the event immutable and pass the context with each call. There is no UI change. For example:
```kotlin
enum class AnalyticsEvent(val key: String) { ITEM_OPENED("item_opened"), ITEM_SHARED("item_shared") }

object Analytics {
    fun log(e: AnalyticsEvent, params: Map<String, Any?>) = sdk.track(e.key, params)
}

// detail
Analytics.log(AnalyticsEvent.ITEM_OPENED, mapOf("title" to item.title, "screen" to "detail"))
// search
Analytics.log(AnalyticsEvent.ITEM_OPENED, mapOf("title" to item.title, "screen" to "search"))
```
A `sealed class` / `data class ItemOpened(title, screen)` works just as well. The goal is that no event state outlives a single call. A real fix must change the API. Resetting the fields after `log` would hide the problem but not fix it:
- Search would then send `null` titles.
- The race in F2 would remain.

**Review gate:**
- Does the fix drop or hide a value? No. It sends the real title and screen for every open.
- Search events will now show `screen=search`. Dashboards that grouped by screen will show a visible shift. That shift is the correct data, but analysts should be told the date it starts.
- No backend change is needed. Historical events cannot be repaired: from release to fix, search-origin `title` and `screen` values are unreliable. Annotate that period in the dashboard.

**Regression tests (JVM unit tests, with a fake `sdk`):**
1. Log a detail open of A, then a search open of B. Assert that the second call has `title=B, screen=search`.
2. Log a search open first. Assert that the title is not null.
3. Log a share after an open. Assert that the share carries none of the open's fields.

Before adding them, confirm the unit test target builds and runs.

**Also in:** `ITEM_SHARED` and any other event or screen that uses this enum (F3). Also check the other platform for an event model built from shared or singleton state.

**Delivery:** the fix only reaches users in an app release, because analytics code cannot ship by OTA in a native Android app. Old app versions will keep sending bad data until users update, so filter or annotate by app version in the dashboard.

### F2 [Medium] Race: concurrent logs can mix fields from different events
**Status:** Suspected (follows from the code; I could not observe it without a device)

**Where:** `AnalyticsEvent.kt:5-6, 10, 17`

**Cause:** `apply { title = ...; screen = ... }` and the reads in `log` are not atomic, and the fields are shared across threads. Suppose two `ITEM_OPENED` logs run at the same time, for example from a background prefetch, a coroutine or a second fragment. Each one can read the other's `title` or `screen`. One event can even carry a title from one call and a screen from the other.

**Fix:** the F1 fix removes this class of bug, because nothing is shared any more.

**Verify:** after the fix, run a unit test that logs from two threads in a loop. Assert that each recorded event matches what its own caller passed.

### F3 [Medium] The same pattern is available to every event, including `ITEM_SHARED`
**Status:** Verified (code), and latent for `ITEM_SHARED` in this excerpt

**Where:** `AnalyticsEvent.kt:3, 5-6`

**Cause:**
- Every enum constant has the mutable `title` and `screen` fields.
- `ITEM_SHARED` is not set anywhere in the excerpt. If share is logged without `apply`, it sends `null` values, or stale values set by an earlier share.
- Any new event or screen that forgets `apply` will report stale context in the same way.

**Fix:** the same as F1. Then search the full codebase (`AnalyticsEvent\.` and `\.apply {`) and list every call site, so that no caller is left on the old API.

### F4 [Low] Item titles sent to the analytics SDK
**Status:** Suspected (this is a policy question, not a bug)

**Where:** `AnalyticsEvent.kt:17`

Free-text titles are sent as event params. If items can be created by users, titles may contain personal data, and they also count against the SDK's param-length and cardinality limits. A stable `item_id` param is the better key, with the title kept only for display, if at all. Also confirm that the user's analytics consent reaches `sdk` before `track` is called. The excerpt does not show this.

| Axis | Row | Expected | Current (from code) |
|---|---|---|---|
| Input | Search open after a detail open | `title=B, screen=search` | `title=A, screen=detail`: **F1** |

| States | Other platform / sibling apps | same behaviour | Not tested (not provided) |
| Data source | Historical dashboard data | — | Search-origin `title` and `screen` cannot be trusted until the fix release |

## 4. Fix order
1. F1, which also covers F2 and F3: change the event API, update every call site, add the unit tests, and ship it in the next app release.
2. Annotate the dashboard: before version X, search `item_opened` events have unreliable `title` and `screen`. Segment by app version.
3. F4: decide with the data and privacy owners whether to send `item_id` instead of `title`, and confirm the consent wiring.

## 5. Open questions and actions for others
- **Analytics owner:** how is "from search" derived today? If it relies on `screen`, search opens have been counted as detail, and search volume is under-reported as well as mislabelled.
- **Mobile team:** confirm the same event model is not used on iOS or in sibling apps (sibling check, 2.8).
- **Nothing has been changed or committed.** All fixes above are proposals waiting for approval.
