## 1. Venues with id 0 are dropped, and the API is called without `venue_ids`: STILL PRESENT

**Where:** `VenueFilter.kt:3-4` and `VenueFilter.kt:9`

```kotlin
selected.map { it.id }.filter { it != 0 }   // drop "No favourite venue"
```

- **Part A (id 0 venues are lost).** Android removes every venue with id 0. On iOS, venue options with id 0 are real choices that must stay selected, matched by normalised name when the id is 0. On Android those choices disappear from the request. They probably also fail to round-trip as "selected" if the selection UI matches by id. The code comment treats id 0 as a "No favourite venue" sentinel, but the iOS fix shows that the backend also uses id 0 for real venues. A sentinel needs its own representation; a numeric id that the backend reuses won't do.
- **Part B (an empty list becomes "no filter").** When every selected venue has id 0, or none has linked events, `venueIdsForRequest` returns an empty list. `FeedRepository.loadHome` still calls `api.search(venueIds = emptyList(), ...)`. Assumption: like the iOS client, `EventsApi` leaves out `venue_ids` when the list is empty. The backend then returns unfiltered results, or a different result set, instead of the empty state the user should see. Nothing on Android short-circuits this case.

**Fix (same as iOS):**
- Keep id 0 venues. Match them by normalised name when the id is 0, and model "No favourite venue" as a separate value (for example a nullable selection or a sealed type) instead of a magic id.
- In `loadHome`, if no selected venue resolves to linked events, show the empty state and skip `api.search`.

**How to verify:**
- Unit-test `venueIdsForRequest` with `[Venue(id=0, name="X")]` and with a mix of venues. Also test `loadHome` with a fake `EventsApi` and assert that `search` is not called when no selected venue has linked events.
- On a device, pick an id 0 venue, then reopen preferences and check it is still selected. Capture the `search` request with a proxy or the network inspector and confirm that `venue_ids` is never missing while the user has venues selected.

## 2. No step-by-step fallback on Home: STILL PRESENT

**Where:** `VenueFilter.kt:8-11`

```kotlin
api.search(venueIds = ..., categoryIds = prefs.categoryIds) { events ->
    onResult(events)            // empty list renders "No results" in every section
}
```

There is one call with venues and categories, and its result goes straight to the UI. An empty list shows "No results" in every section. iOS retries with venues + category, then venues only, then no preferences. Android has none of these steps.

**Fix:** if the venues + categories call returns nothing, run the same sequence as iOS: venues + category → venues only → no preferences. Pass on the first non-empty result. Show "No results" only after the last step also comes back empty. Keep the order and the stop conditions the same as iOS so the two apps show the same Home for the same account.

**Interaction with #1:** the fallback must not undo fix #1. If the user has venues selected and none has linked events, iOS shows the empty state. Reuse the iOS logic for where the "no preferences" step applies, rather than guessing.

**How to verify:** unit-test `loadHome` with a fake API that returns empty for the first call(s). Assert the call sequence and the final result. On a device, use an account whose venue + category combination has no events and check that Home is populated, not "No results" everywhere.

## 3. Tracking switch: event logged before the save, failure ignored: STILL PRESENT

**Where:** `SettingsFragment.kt:2-5`

```kotlin
Tracker.event("tracking_toggled", mapOf("on" to isOn))
profileRepository.update(allowTracking = isOn)   // result ignored
```

- The analytics event fires before the save, and it fires whether or not the save succeeds. It also fires when the user turns tracking **off**, which may matter for consent (see the note below).
- The result of `update` is ignored. If the save fails (offline, 4xx/5xx), the switch keeps the new position while the server keeps the old value. The UI then misreports the user's tracking choice.

**Fix (same as iOS):** call `update`, and only on success log `tracking_toggled`. On failure, put the switch back to its previous value without firing the listener again (to avoid a loop), and show an error. Disable the switch while the save is in flight so taps can't race each other.

**Note:** sending a tracking event at the moment the user opts *out* is a privacy and consent concern beyond the iOS parity bug. It's worth checking with whoever owns consent whether the "off" event should be sent at all.

**How to verify:** unit-test with a fake `profileRepository` that fails, and assert that the switch reverts and `Tracker.event` is not called. On a device, turn on airplane mode, flip the switch, then check that it reverts and that no `tracking_toggled` event shows up in the analytics debug view or logcat. Then repeat online and confirm the event is sent once.

## 4. Late images in reused cells: PROBABLY NOT AFFECTED (not verified)

**Where:** only the header comment in `VenueFilter.kt:1` covers this. It says the image library "cancels the previous request when a view is reused". The excerpt contains no adapter or ViewHolder code.

If every image load goes through that library's load-into-view API, a recycled `ImageView` cancels the old request, and the iOS bug can't happen. This is the default behaviour of the common Android image loaders. The bug can still come back where code bypasses that mechanism, for example:
- loading a bitmap manually (a coroutine or callback, then `setImageBitmap`) without checking that the holder still shows the same item;
- loading into a custom target or listener rather than the view itself;
- loading into a view that isn't the one being recycled (for example a parent or a sibling).

**How to verify:** in the RecyclerView adapters for event and venue lists, search for `setImageBitmap`, `setImageDrawable`, custom targets or listeners, and any image fetch done outside the library. Any such path needs a "same item?" check, such as a tag or a bound id, before it sets the image. On a device, throttle the network (emulator network speed or a proxy) and fling quickly through a long list. Then check that no row briefly or permanently shows another row's image.
