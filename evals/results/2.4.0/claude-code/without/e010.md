# List screen: Saved tab shows the All list, and the list stops loading after a network error

**Scope:** I only had `ListFragment.kt` (21 lines). It's an excerpt that doesn't build, and I had no device, backend or git history. Everything below comes from reading the code. I did not reproduce anything on a device.

**Assumptions:** `repository.fetch` is asynchronous, calls exactly one of `onSuccess`/`onError` once, and calls it on the main thread. `adapter.submit` replaces the visible list. Nothing else in the fragment clears the adapter or resets `isFetching`.

Both symptoms come from one flag, `isFetching`, which is used in two wrong ways:
- It **drops** new requests instead of replacing the old one.
- It is **never cleared** when a request fails.

---

## Bug 1: after a network error the list never loads again (certain)

`ListFragment.kt:19`
```kotlin
onError = { showError() })
```
`isFetching` is set to `true` at line 12. Only the success path sets it back to `false` (line 15). After one failed request:

1. `isFetching` stays `true` for as long as the fragment exists.
2. Every later `load()` call, whether from a tab tap or a retry, hits `if (isFetching) return` at line 11 and does nothing.
3. No request goes out, so no error appears either. The screen just stays stale or empty. Only recreating the fragment fixes it, which matches "never loads again".

**Confidence:** high. This happens on every error. It is not a race.

## Bug 2: the Saved tab sometimes shows the All list (race, timing-dependent)

`ListFragment.kt:5-20`. When a request is already running and the user changes tab:

- Line 6 updates `currentQuery` to the new tab.
- Line 11 then **drops** the new tab's request, because a fetch is still in flight.
- When the old request finishes, line 16 (`query != currentQuery`) correctly **throws away** its result.
- So nobody fetches the new tab's data, and nobody re-fetches it later. The adapter keeps whatever it showed before, which is the All list.

**Concrete sequence:**

| Step | `currentQuery` | `isFetching` | In flight | Shown |
|---|---|---|---|---|
| All is loaded and displayed | ALL | false | none | All items |
| Something triggers `load(ALL)` (first open, refresh, coming back to the tab) | ALL | true | ALL | All items |
| User taps **Saved** while ALL is still loading. `load(SAVED)` returns early at line 11 | SAVED | true | ALL | All items |
| ALL response arrives. `isFetching = false`, then it's discarded at line 16 | SAVED | false | none | **All items under the Saved tab** |

This only happens when the tab switch lands inside the request window, which is why it's "sometimes". Slower networks make it more likely. The same race works the other way: tap All while Saved is loading, and the All tab keeps showing Saved items.

**Related variant:** if the dropped request fails instead of succeeding, Bug 1 also kicks in. Line 19 shows the error under the *new* tab (there's no `query` check on the error path), and the screen then stays stuck.

**Confidence:** high that the code allows this. I couldn't observe it on a device.

## Other issues in the same code (lower priority)

- **Error path ignores which query it belongs to** (line 19). A late error from the old tab is shown on the current tab, even if the current tab has valid data.
- **Nothing cancels requests or checks the lifecycle.** The callbacks capture the fragment. If the response arrives after `onDestroyView`, then `adapter.submit` and `showError()` touch a dead view. That can crash, or at least leaks the fragment until the call finishes. I can't confirm the effect without seeing the `repository` and `showError` code.
- **Threading assumption.** If `repository.fetch` calls back on a background thread, `isFetching`, `currentQuery` and `adapter` are also being read and written from different threads without synchronisation. Check the repository implementation.
- **State is lost on rotation or process death.** `currentQuery` and the in-flight state live in the fragment, so a configuration change resets them to `ALL`. That may not match the tab the UI has restored.

## Recommended fix

The core change is to make the latest request win (cancel or ignore the old one), instead of letting the first request win by dropping new ones, and to always clear the loading state.

**Minimal fix inside the current structure:**
```kotlin
private var requestId = 0
private var currentQuery: Query = Query.ALL

fun onTabSelected(tab: Tab) {
    currentQuery = if (tab == Tab.SAVED) Query.SAVED else Query.ALL
    load(currentQuery)
}

private fun load(query: Query) {
    val id = ++requestId               // newest request always goes out
    showLoading(true)
    repository.fetch(query,
        onSuccess = { items ->
            if (id != requestId || view == null) return@fetch   // stale or view gone
            showLoading(false)
            adapter.submit(items)
        },
        onError = {
            if (id != requestId || view == null) return@fetch
            showLoading(false)          // loading state always cleared
            showError()                 // with a Retry action that calls load(currentQuery)
        })
}
```
If showing the old tab's data during the load is unwanted, also clear the adapter or show a placeholder when the tab changes.

**Better fix:** move loading into a `ViewModel`. Keep the selected query in a `MutableStateFlow` and use `flatMapLatest { repository.fetchFlow(it) }`, mapped to a `Loading / Content / Error` UI state. `flatMapLatest` cancels the previous request automatically. Then collect it with `repeatOnLifecycle(STARTED)` in `viewLifecycleOwner.lifecycleScope`. This fixes both bugs and the lifecycle issue, and it keeps the selected tab across rotation (use `SavedStateHandle` if it should also survive process death). No design changes are needed.

## How to verify

1. **Unit test with a fake repository** that holds on to callbacks so the test decides when they fire. (Run with `./gradlew test`.)
   - *Error recovery:* call `load(ALL)`, fire `onError`, call `load(ALL)` again. Assert the fake received **2** fetch calls. It receives 1 today.
   - *Tab race:* call `onTabSelected(ALL)`, then `onTabSelected(SAVED)` before ALL completes. Complete ALL, then complete SAVED if a request was made. Assert the adapter's final contents are the SAVED items. Today SAVED is never requested and the All items stay.
2. **On a device or emulator:**
   - Throttle the network (emulator Extended controls > Cellular > network speed, or a proxy such as Charles with a 3 s delay on the list endpoint). Open the screen and tap Saved while All is still loading. Today Saved shows All items.
   - Turn on airplane mode, open the list so it errors, then turn the network back on and switch tabs or retry. Today nothing loads. After the fix it should.
   - Log each `load()` call, each early return, and each callback (e.g. `adb logcat -s ListFragment`) to confirm the dropped requests.
3. **Lifecycle check:** start a slow fetch, then navigate away or rotate before it completes. Watch logcat for crashes or "view not attached" errors.
