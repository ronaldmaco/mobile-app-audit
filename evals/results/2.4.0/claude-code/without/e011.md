# Network layer audit: `NetworkService.send`

**Scope:** `NetworkService.kt` (17 lines), the only file in the excerpt. It doesn't build, and I had no device, backend or git history. Everything below comes from reading the code. Nothing was reproduced at runtime, so each finding includes a way to confirm it.

**Assumptions** (I couldn't see these types):
- `http.execute` calls back once with `(response, error)`. `error` is non-null for transport failures (offline, DNS, timeout, TLS).
- For HTTP 4xx/5xx, `error` is non-null and `error.response` holds the server reply.
- `request.key` comes from method + URL (maybe body) and doesn't include the user.
- The like action is a POST or PUT sent through `send`.

## Summary

Both user reports come from the same 10-line error branch:

| # | Severity | Finding | User symptom |
|---|---|---|---|
| 1 | Critical | A failed POST/PUT falls back to the cache and calls `onSuccess` | "Like looks saved offline but is lost" |
| 2 | Critical | A transport error with no response body calls no callback at all | "Some screens spin forever" |
| 3 | High | `parse` / `ApiError.from` exceptions are not caught, so again no callback (or a crash) | Spinner forever or crash, on bad or old payloads |
| 4 | High | Mutation responses are written into the read cache | Feeds #1, and stale data gets replayed |
| 5 | Medium | A 401/403/5xx is hidden by cached data shown as success | Session expiry and server outages don't show; stale data looks fresh |
| 6 | Medium | Cache written before the body is checked; no user scoping, no expiry | Bad bodies get cached; another user's data could show after logout |
| 7 | Low | No cancel/lifecycle handling and no stated callback thread | Callbacks after the screen is gone; UI touched off the main thread |

## 1. Offline writes reported as success (lost like)

```kotlin
val cached = cache.get(request.key)
if (cached != null) {
    onSuccess(parse(cached))          // used for GET, POST and PUT alike
```

When the like POST fails because the device is offline, the code looks in the cache under the request's key. If an earlier response for that key exists (for example, the user liked or unliked this item before, which #4 puts in the cache), the code calls `onSuccess` with the **old server reply**. The UI shows the like as saved. But:
- nothing was sent to the server,
- nothing is queued for retry,
- on the next GET (or a fresh launch) the server state comes back without the like, so it is "lost".

The comment on line 11 shows this was known: falling back to the cache only makes sense for idempotent reads.

**Fix:**
- Use the cache fallback only for `GET`. Never use it for `POST/PUT/PATCH/DELETE`.
- For writes made offline, either report the error to the UI so it rolls back the optimistic like and shows "Couldn't save, retry", or (to support offline likes) save the intent in a durable outbox: a DB table or WorkManager job with a network constraint and an idempotency key. Show it as *pending* until the server confirms.
- Pass the source to the caller (`Result.Fresh` / `Result.Cached` / `Result.Queued`) so screens can't mistake a cached result for a confirmed save.

**Verify:**
- Unit test with a fake `http` that returns a transport error for a POST whose key is already in a fake cache. Today `onSuccess` fires; it must not.
- On a device: like an item online, unlike it, turn on airplane mode, like it again, force-stop the app, go back online, reopen. Today the like is gone. Confirm on the server (backend log or GET of the item) that no request arrived. A proxy (Charles/mitmproxy) shows that no POST was sent and none was retried.

## 2. Silent failure: no callback when there is no response body

```kotlin
error.response?.body?.let { onError(ApiError.from(it)) }
```

Offline, timeout, DNS failure, TLS error and connection reset all have **no response**, so `error.response` is null. The same goes for an HTTP error with an empty body (for example a bare 502 or 504 from a proxy). Combined with a cache miss, the function returns **without calling `onSuccess` or `onError`**. Any screen that shows a spinner until a callback arrives keeps spinning. That explains "some screens spin forever": the ones whose data was never cached (first visit, cleared cache, detail screens never opened before), on a bad or no network.

**Fix:** every path must end in exactly one callback.
```kotlin
onError(error.response?.body?.let(ApiError::from) ?: ApiError.network(error))
```
Better still, change the API to return a single `Result` (or a `suspend fun` that throws or returns), so it can't finish without an outcome. Also check that `http` has connect/read/call timeouts set, or a request that stalls never calls back at all.

**Verify:**
- Unit test: fake `http` returns `error` with `response = null` and an empty cache. Assert that exactly one callback fires. Today it is zero.
- On a device: clear the app data, turn on airplane mode, open each screen that hasn't been visited yet. Each must show an error or retry state within the timeout. Also test with a proxy that returns 502 with an empty body, and with a throttled network (Network Link Conditioner, or the emulator's network delay settings) to hit timeouts.

## 3. Uncaught exceptions in `parse` and `ApiError.from`

`parse(response.body)`, `parse(cached)` and `ApiError.from(it)` all run with no `try/catch`. A changed schema, an HTML error page returned with 200, an empty body, or a cache entry written by an older app version will throw. Depending on the thread `http` uses, that either crashes the app or is swallowed by the HTTP library's executor. If it is swallowed, **no callback fires**, which is another cause of endless spinners.

**Fix:** wrap parsing and send failures to `onError(ApiError.parse(e))`. If parsing a cache entry fails, delete that entry.

**Verify:** unit test with `parse` throwing, for both the fresh and the cached path. Assert `onError` fires once. Search crash reports or logcat for parse exceptions on the network thread.

## 4. Mutation responses written to the read cache

`cache.put(request.key, response.body)` runs for every successful request, POST/PUT included. If the key depends only on method and URL, a like response is stored and later replayed (see #1). If the key ignores the method, a POST reply can even overwrite the GET entry for the same URL, and the list then gets a body in the wrong shape (see #3).

**Fix:** write to the cache only for successful `GET`s. Invalidate or refresh the matching GET entries after a confirmed write.

**Verify:** check how `request.key` is built (not in the excerpt). Add a unit test that a POST success leaves the cache unchanged.

## 5. Server errors hidden behind cached success

Any error, including 401/403/404/500, falls back to cached data and calls `onSuccess`. So an expired session never sends the user to log in, a deleted item still shows, and an outage looks like normal (but frozen) data with nothing telling the user it's stale.

**Fix:** fall back only on **transport** errors (no response) for GETs, and tell the UI the data is stale. Send 401 to the auth flow. Show 4xx/5xx as errors.

**Verify:** a proxy rewrites a GET to 401 or 500 while the cache is populated. Today the screen shows old data as fresh.

## 6. Cache hygiene

- The body is cached **before** `parse` succeeds, so a bad body gets stored and replayed. Move `put` to after a successful parse.
- Check whether `request.key` includes the user or account. If it doesn't, one user's cached responses can be shown to the next user after logout or login. Clear the cache on logout and scope keys to the user.
- No TTL or max age is visible, so stale data can be served indefinitely.

**Verify:** read `ResponseCache` and the code that builds keys. Log out, log in as a different test user, go offline, open a cached screen.

## 7. Lifecycle and threading

The callbacks don't say which thread they run on, and there is no cancel hook. If callbacks come back on the HTTP thread, the screens must switch to the main thread. If a screen is closed, a late callback can update a dead view or leak it.

**Fix:** move to coroutines (`suspend` + `viewModelScope`) or return a cancellable handle. Document the callback thread.

**Verify:** StrictMode / main-thread checks. Rotate or close the screen during a slow request (with network throttling on).

## Suggested shape after the fix (sketch)

```kotlin
suspend fun <T> send(request: Request, parse: (String) -> T): ApiResult<T> {
    val (response, error) = http.await(request)            // with timeouts configured
    if (error == null) {
        val value = runCatching { parse(response.body) }.getOrElse { return ApiResult.Failure(ApiError.parse(it)) }
        if (request.method == GET) cache.put(request.key, response.body)
        return ApiResult.Fresh(value)
    }
    if (request.method == GET && error.response == null) {
        cache.get(request.key)?.let { c -> runCatching { parse(c) }.getOrNull()?.let { return ApiResult.Stale(it) } }
    }
    return ApiResult.Failure(error.response?.body?.let { runCatching { ApiError.from(it) }.getOrNull() } ?: ApiError.network(error))
}
```
Offline likes then go through an outbox (persisted, retried with an idempotency key, shown as pending), not through this function's cache fallback.

## Test checklist to close this out
1. Unit tests on a fake `http` / `ResponseCache`. For each combination of {GET, POST} × {success, transport error, HTTP error with body, HTTP error without body, parse throws} × {cache hit, miss}, assert **exactly one** callback or result, and that a write never succeeds from the cache.
2. Device: airplane-mode like flow (#1) and visits to uncached screens (#2), on both a fresh install and an upgrade from the previous version (stale cache entries).
3. Proxy: empty-body 502, 401 with a populated cache, HTML returned as 200.
