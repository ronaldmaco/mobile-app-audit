# Analytics audit: wrong titles on `item_opened` from search

**Scope:** `AnalyticsEvent.kt`, the only file in the excerpt. It also contains snippets from `ItemDetailFragment.kt`, `SearchFragment.kt` and `Analytics.kt`. This is a static review only. The code does not build, and there is no device, SDK dashboard or git history to check against.

**Assumptions:** `sdk.track` sends the map as it is when called. Opening a search result usually goes on to `ItemDetailFragment`. `Analytics.log` can be called from more than one thread, for example from coroutines or SDK callbacks.

## Root cause (confirmed from the code)

**Event parameters are stored as mutable state on enum constants. Enum constants are process-wide singletons.**

```kotlin
enum class AnalyticsEvent(val key: String) {
    ITEM_OPENED("item_opened"), ...
    var title: String? = null     // one shared slot per constant, for the whole process
    var screen: String? = null
}
```

- `ItemDetailFragment.onItemOpened` (line 10) writes `title = item.title; screen = "detail"` into the single `ITEM_OPENED` instance, then logs it. These values **stay set** after the call.
- `SearchFragment.onResultOpened` (line 13) logs `AnalyticsEvent.ITEM_OPENED` **without setting anything**. Its `item` parameter is never used.
- `Analytics.log` (line 17) reads whatever is in the singleton at that moment.

So a search `item_opened` reports the title of the **last item opened on the detail screen**, which may be an item the user never touched in search. If the user has not opened any detail screen yet in this process, it reports `title = null`. This matches the symptom exactly.

### Example sequence
1. The user opens item A on the detail screen. The singleton becomes `{title: A, screen: detail}` and the event `item_opened(A, detail)` is correct.
2. The user searches and taps item B. The event is `item_opened(A, detail)`, which is **wrong**: it is item A, not B.
3. The app then navigates to detail for B. The event `item_opened(B, detail)` is correct, but it is a second event for the same open.

## Other findings

| # | Severity | Finding | Where |
|---|----------|---------|-------|
| 1 | High | **Stale title** on search events, as described above. | `SearchFragment.kt` line 13 and enum `var`s |
| 2 | High | **The source screen is wrong too.** Search events inherit `screen = "detail"` (or `null`), so they cannot be told apart from detail opens by `screen`. Any "from search" breakdown that relies on `screen` is unreliable. If your dashboard labels these events "search", check which property it actually uses. | same |
| 3 | Medium | **Double counting.** Opening a result from search logs once in search and again on detail (if search goes to detail). Counts of `item_opened` are inflated, and the funnel shows two opens per tap. | lines 10 and 13 |
| 4 | Medium | **Race condition.** `apply { title = ...; screen = ... }` followed by a read in `log` is not atomic, and the fields are not `@Volatile` or synchronized. Two concurrent logs can mix the title of one event with the screen of another. The same applies to `ITEM_SHARED`, which has the same design. | lines 5-6, 10, 17 |
| 5 | Low | **Leaking state across events.** Any future caller that sets only one field (for example only `screen`) silently inherits the other field from an earlier unrelated event. Nothing resets the fields after logging. | enum design |
| 6 | Low | **Title as the identifier.** Titles are not unique, can change, and are localised. They may also contain user content, which is a privacy concern for third-party analytics. Prefer a stable `item_id`, and send the title only if it is needed and allowed. | lines 10, 17 |
| 7 | Low | **Null values sent.** `mapOf("title" to null, ...)` passes nulls to the SDK. Depending on the SDK, these are dropped, sent as `"null"` or rejected. | line 17 |

## Recommended fix

Keep the enum as a plain list of event names, and pass parameters per call as immutable values:

```kotlin
enum class AnalyticsEvent(val key: String) { ITEM_OPENED("item_opened"), ITEM_SHARED("item_shared") }

object Analytics {
    fun log(event: AnalyticsEvent, params: Map<String, String?> = emptyMap()) =
        sdk.track(event.key, params.filterValues { it != null })
}

// ItemDetailFragment
fun onItemOpened(item: Item) =
    Analytics.log(AnalyticsEvent.ITEM_OPENED, mapOf("item_id" to item.id, "title" to item.title, "screen" to "detail"))

// SearchFragment
fun onResultOpened(item: Item) =
    Analytics.log(AnalyticsEvent.ITEM_OPENED, mapOf("item_id" to item.id, "title" to item.title, "screen" to "search"))
```

A type-safe alternative is a `sealed class` / `data class ItemOpened(val itemId: String, val title: String, val source: String)`. With it, the compiler forces every caller to provide all parameters.

On the double counting, decide on one rule:
- **Option A:** log only on detail and pass `source = "search"` through the navigation arguments.
- **Option B:** rename the search event to `search_result_clicked`.

## How to verify

1. **Unit test (JVM, no device).** Fake `sdk`, call `onItemOpened(A)`, then `onResultOpened(B)`, and assert that the second `track` call has `title == B` and `screen == "search"`. This test fails on the current code and passes after the fix.
2. **Code search for the same pattern:** `grep -rn "AnalyticsEvent\.[A-Z_]*\.apply\|AnalyticsEvent\.[A-Z_]*)" --include=*.kt` and `grep -rn "^\s*var " ` inside the enum file(s). Any other enum or `object` that holds event parameters in `var`s has the same bug.
3. **On a device:** enable the SDK's debug view (most SDKs have a debug/verbose mode or a live event view). Open item A on detail, then open item B from search, and check the parameters of each event as it arrives.
4. **In the data:** search events today should show `screen = "detail"` or `null`, never `"search"`, and their title should equal the title of that user's previous detail event. Run a query that pairs each search `item_opened` with the user's previous detail event; it confirms the diagnosis on historical data. Treat existing search `item_opened` titles and the screen split as unreliable until the fix ships.

## Not verified
This report does not cover the runtime behaviour of `sdk.track` (null handling, batching), whether search goes to `ItemDetailFragment`, or the threading of the callers. None of these were in the excerpt.
