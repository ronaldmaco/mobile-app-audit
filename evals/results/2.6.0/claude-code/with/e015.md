# Is 3.1 ready for the App Store? Not yet.

**Short answer: don't submit tomorrow as things stand.** The files show the most likely cause of the 2.1 rejection ("We were unable to sign in or reach any content"), and none of the changes since then fixes it. The crash fix on the map screen is good, but it doesn't touch sign-in. If you resubmit now, three things are almost certain to stop review again, and two more are likely to:

1. Your API blocks every country except Peru, Chile and Mexico, and App Review mostly tests from the US.
2. The demo account needs an SMS code that goes to a team member's phone, so the reviewer can't receive it.
3. You plan to upload build 42 again, but App Store Connect already has build 42 for 3.1.
4. "Delete account" opens a support contact page. Apple doesn't accept that (guideline 5.1.1(v)).
5. The camera permission text just says "Camera", and the app has Google login with no equivalent privacy-friendly option (5.1.1 and 4.8). Both are risks.

You can fix 1 and 2 on the server today, without a new build. Fixing 3 is a one-line change. Item 4 needs a small code change. Details are below.

**Mode:** E (store readiness, after a rejection). **How I checked:** static review of the files you sent (`Info.plist`, `LoginView.swift`, `SettingsView.swift`, `AvatarPicker.swift`, `release-notes.md`, including the CDN rule). I read the Apple rules again on the official pages today, 2026-11-17. **What I could not do:** run the app, call your API from the US, read the built binary or its SDKs, or see App Store Connect. Anything that depends on those is marked as not verified.

## Findings, most severe first

### F1 [Critical] The API blocks every country except PE, CL and MX, so reviewers can't sign in or load anything
- **Status:** Verified in the config. I have not tested it live.
- **Where:** CDN edge rule for `api.example.com` (`release-notes.md`, lines 8-14): `geo_access: allow_list [PE, CL, MX]`, `action_for_others: block_403`.
- **What the reviewer sees:** login fails, or every screen stays empty. That matches the rejection text word for word: "We were unable to sign in or reach any content."
- **Cause:** App Review testers are mostly in the US. Every request they send to the API gets a 403 at the CDN before it reaches your server.
- **Try to refute:** this would not be the cause if the reviewer had tested from one of the three countries, or if the app used another host for login. Nothing in the files points to either. The app has one API host, and the rejection says that both sign-in *and* content failed. A geo block produces exactly that. One check settles it: from a US connection (VPN, confirm with `curl -s ipinfo.io/country` → `US`), run `curl -s -o /dev/null -w "%{http_code}\n" https://api.example.com/<login endpoint>`. A 403 from the CDN confirms it.
- **Fix (server only, no new build):** add `US` to the allow list, or remove the geo restriction from the login and content routes. Apple can review from other countries too, so the safest option is to not geo-block the API that the app needs. If you must keep a block for business reasons, apply it to content, not to auth. Then check every host the app uses (API, images/CDN, auth provider) from the US.
- **Also affects:** your real users who travel or roam outside PE/CL/MX. Today they're locked out too.
- **Rule:** 2.1(a), "include demo account info (and turn on your back-end service!) if your app includes a login" (App Review Guidelines, read 2026-11-17).

### F2 [Critical] The demo account needs an SMS code that goes to a team member's phone
- **Status:** Verified from your notes (`release-notes.md`, line 6).
- **What the reviewer sees:** they type the email and password, then get stuck on the one-time code screen.
- **Cause:** the code goes to your colleague's phone, not to the reviewer. Even after F1 is fixed, sign-in can't be completed.
- **Try to refute:** this would not block review if you sent Apple a working code in the notes. A one-time SMS code can't be pre-shared, and nobody can promise to be awake and relay it during review in another time zone.
- **Fix (server only):** turn off the SMS step for the review account only, or give it a fixed code and write that code in the App Review notes. Make sure the account is not expired, has real content (studios near a US location, or explain in the notes how to browse PE/CL/MX), and is not locked by failed attempts. Keep the password out of chat and tickets. Only put it in the App Store Connect review notes field.

### F3 [Critical] Build number 42 is already used, so the upload will fail
- **Status:** Verified from your files: `Info.plist` lines 6-9 show `CFBundleShortVersionString` 3.1 and `CFBundleVersion` 42, and the notes say "TestFlight already shows 3.1 (42)" and "Version and build in Info.plist are unchanged."
- **What happens:** App Store Connect won't take a second upload with the same build number for the same version. Also, the map crash fix you made only reaches Apple if you upload a new binary.
- **Fix:** set `CFBundleVersion` to **43** (or anything higher than what's in TestFlight), archive, upload, and pick the new build for the 3.1 submission. If your server has a minimum-version or forced-update check, confirm that build 43 passes it.

### F4 [High] "Delete account" opens a support contact page, which guideline 5.1.1(v) doesn't allow
- **Status:** Verified in code: `SettingsView.swift` lines 10-13. The footer says "To close your account, email our support team." and the button opens `https://help.example.com/contact`.
- **Rule (read 2026-11-17):** 5.1.1(v): "If your app supports account creation, you must also offer account deletion within the app." Apple's account deletion page: "If people need to visit a website to finish deleting their account, include a link directly to the page on your website where they can complete the process", and apps outside highly regulated industries "should not require people to make a phone call, send an email, use a chat support flow, or go through other support flows."
- **Try to refute:** this would be acceptable if the app didn't support account creation, or if you were in a highly regulated industry. A studio finder isn't regulated, and Google login "used to create and sign in to the main account" (`LoginView.swift`, line 12) shows the app does create accounts. A reviewer who gets past login and opens Settings will likely flag this.
- **Fix (keeps the same row and the same look):** the "Delete account" button should start deletion inside the app (confirm, call a delete endpoint, log out). If deletion has to finish on the web, link **directly** to a page that does the deletion, not to a contact form. Replace the "email our support team" footer. After deleting, call the API with that account: the account and its data must be gone, not just disabled. Delete the same way for Google accounts (also revoke the Google token).

### F5 [Medium, rejection risk] The camera permission text is just "Camera"
- **Status:** Verified in `Info.plist` (lines 10-11). Whether the camera is used at all is not verified.
- **Rule (read 2026-11-17):** 5.1.1(ii): "Ensure your purpose strings clearly and completely describe your use of the data." "Camera" doesn't describe a use.
- **Note:** the avatar picker uses `PHPickerViewController` (`AvatarPicker.swift`), which needs no camera or photo permission. In the files I have, nothing uses the camera.
- **Fix:** if no code or SDK uses the camera, remove `NSCameraUsageDescription`. If something does, write a specific sentence, for example "Take a photo to use as your profile picture." To check, grep the project and the built app: `grep -rn "AVCaptureDevice\|UIImagePickerController\|sourceType = .camera" .` and `otool -L <App>.app/<binary> | grep AVFoundation`. The location text is fine.

### F6 [Medium, Suspected rejection risk] Google login without an equivalent privacy-friendly option (4.8)
- **Status:** Suspected. Whether your own email/password login counts as the equivalent option depends on the exemptions in 4.8, and I have not confirmed which one applies to you.
- **Rule (read 2026-11-17):** apps that use a third-party login such as Google Sign-In "to set up or authenticate the user's primary account" must also offer an equivalent login option. That option must limit data to name and email, let users keep their email private, and not collect interactions for advertising without consent. The rule asks for an equivalent option, not specifically Sign in with Apple, but Sign in with Apple is the usual way to meet it.
- **Where:** `LoginView.swift`, lines 8-13. The app offers email/password plus "Continue with Google", which creates the main account.
- **Fix / decision:** read the 4.8 exemptions on the guidelines page. If none applies, add Sign in with Apple (or another option with the three features above) next to Google, in the same button style. This isn't the cause of the current rejection, but it can be the next one.
