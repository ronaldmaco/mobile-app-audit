# Pre-launch security review: Android app (Kotlin + Firebase)

## Summary

- **Mode:** targeted security audit (mode C), with one future-risk item, because the database rules have an expiry date.
- **Scope:** the files you sent: `firestore.rules`, `app-config.json`, `HelpActivity.kt`, `PremiumManager.kt`, `RedeemCode.kt`.
- **How it was checked:** static review only. I could not run the app or reach your Firebase project, so nothing here has been tested on a device or with a live request. A finding marked "Verified in code" means the code or rules file shows the flaw and how an attacker triggers it. Whether it is live depends on what is actually deployed, and each finding gives the command to confirm that.
- **Not covered (files not provided):** `AndroidManifest.xml`, the release APK/AAB, `storage.rules`, Cloud Functions, Firebase Auth settings, App Check, network security config, the `Session` class, and the billing client code. See the coverage table.

**Short version:** today, anyone who downloads the app can read and rewrite your whole database. That includes every user's data, every coupon code, all paid lessons and everyone's credit balance. The help screen can also be used to steal a user's login token through a crafted link. Pro access and credits are decided on the phone, so users can grant them to themselves. And on **1 January 2027** the current rules lock everyone out, so the app stops working for every user even if nothing else changes.

| # | Severity | Attack | Needs |

## Findings

### F1 [Critical] Firestore is open to the whole internet
**Status:** Verified in code (`firestore.rules`). Not verified that this file is what is deployed.
**Where:** `app/firestore.rules:4-6`
```
match /{document=**} {
  allow read, write: if request.time < timestamp.date(2026, 12, 31);
}
```
**What the user sees:** nothing, until their data is leaked, changed or deleted.
**Cause:** these are Firebase "test mode" rules. Until the date passes they allow every read and write on every collection, with no login and no ownership check. The project id and API key come with the app (`app-config.json`), so anyone can call the Firestore REST API or the SDK directly.
**What an attacker can do:**
- Download every document in `users` (emails, names, credit balances and whatever else is stored there).
- List `coupons` and collect every unused code.
- Read `lessons_pro` without paying.
- Set any user's `credits` to any value, mark coupons as used or unused, or delete whole collections.
**Try to refute:** "Maybe the deployed rules differ from this file," or "maybe App Check blocks outside clients." Neither can be checked from the files. App Check is not mentioned anywhere, and the client code (`RedeemCode.kt`, `LessonRepository`) depends on these open writes to work, which strongly suggests these rules are the deployed ones. Severity stays Critical. The status stays "not verified as deployed" until you run the check below.
**Verify (read-only, safe):**
- Firebase console > Firestore > Rules: compare with this file.
- Without logging in: `curl -s "firestore.googleapis.com/v1/projects/$PROJECT/databases/(default)/documents/coupons?pageSize=1"`. A secure setup returns `PERMISSION_DENIED`. If you get a document back, you are exposed now.
- Logged in as test user A, try to read test user B's `users/{uid}` document. Expect a denial.

**Fix:** replace the rules with default-deny plus explicit rules per collection. A starting point that matches the code you sent (adjust it to your real schema):
```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{uid} {
      allow read: if request.auth != null && request.auth.uid == uid;
      // client may edit profile fields, never credits or entitlements
      allow update: if request.auth != null && request.auth.uid == uid
        && !request.resource.data.diff(resource.data).affectedKeys()
             .hasAny(['credits', 'isPro', 'entitlement']);
    }
    match /lessons_free/{id} { allow read: if request.auth != null; }
    match /lessons_pro/{id} {
      allow read: if request.auth != null && request.auth.token.pro == true; // set by server, see F3
    }
    match /coupons/{code} { allow read, write: if false; }   // server only, see F4
    // anything not matched above is denied
  }
}
```
Test them with the Firebase Emulator Suite and `@firebase/rules-unit-testing` before you deploy: one test that each allowed case passes and one test that each attack above is denied.
**Watch out:** these rules **break redeem (F4) and Pro lessons (F3) in the current app**, because both rely on writes from the phone. Ship the server-side changes from F3 and F4 together with the new rules. Otherwise you swap a security hole for a broken feature.
**After the fix:** assume the data may already have been read. Check whether real users are in `users` yet. If they are, look at Cloud Audit Logs (Data Access logs only exist if they were enabled) and consider whether you need to notify anyone. Regenerate any coupon codes that already exist.
**Source:** Firebase, "Avoid insecure rules" (firebase.google.com/docs/rules/insecure-rules).

### F2 [Critical] Help deep link leaks the user's access token to any website
**Status:** Verified in code. Whether it can be reached from outside depends on the manifest, which I don't have (see "Trigger").
**Where:** `app/HelpActivity.kt:9-14, 18-21`
**What the user sees:** they tap a link (in an email, chat or web page), a "help" page opens inside the app, and their account is taken over. Nothing looks wrong.
**Cause:** three problems combine:
1. The page URL comes straight from the deep link (`intent.data?.getQueryParameter("page")`).
2. The only check is `url.startsWith("https://help.example.com")`. That is a string prefix, not a host check. `https://help.example.com.<attacker domain>/x` passes, and so does `https://help.example.com@<attacker domain>/x`, where the real host is `<attacker domain>`.
3. With JavaScript on, `addJavascriptInterface(AccountBridge, "Account")` gives the loaded page `Account.authToken()`, which returns the session access token. On Android, this bridge is available to every frame and every page that WebView later loads. It is not limited to the first URL.

**Trigger:** the attacker publishes `myapp://help?page=https%3A%2F%2Fhelp.example.com.<attacker domain>%2Fh`. When a user taps it, the app opens their page, and the page's script calls `Account.authToken()` and sends the result to the attacker's server. Even without the bypass, an iframe or embedded content on the real help site (ads, widgets, user-generated content) can call the bridge.
**Try to refute:** "HelpActivity may not be exported." If the manifest has no `VIEW` intent filter for `myapp://help`, outside apps and websites cannot start it, and the risk drops to iframes or content on the help site. The code comment says help pages "can be opened from a deep link: myapp://help?page=<url>", so the intent filter very likely exists. Severity stays Critical. Confirm it with:
- `aapt2 dump xmltree --file AndroidManifest.xml app-release.apk | grep -A10 HelpActivity`, or `bundletool dump manifest --bundle app.aab`
- On a debug build: `adb shell am start -a android.intent.action.VIEW -d 'myapp://help?page=https%3A%2F%2Fhelp.example.com.<attacker domain>%2F'`. If the WebView loads that host, the bypass is confirmed. Use a domain you control, never a real attacker host.

**Fix (smallest first):**
1. **Remove the bridge** unless the help site really needs the token. Help pages rarely need a user's access token. If they do need it, use a short-lived, single-purpose token, not the session token.
2. Validate the URL by its parsed parts, never by string prefix:
   ```kotlin
   val uri = Uri.parse(url)
   val allowed = uri.scheme == "https" && uri.host == "help.example.com" && uri.userInfo == null
   ```
3. If you keep a bridge, replace `addJavascriptInterface` with `WebViewCompat.addWebMessageListener(webView, "Account", setOf("https://help.example.com"), listener)` from AndroidX WebKit. It only answers the exact origins you list. Also set a `WebViewClient` that sends any navigation outside the help host to the system browser.
4. Rotate or shorten the lifetime of access tokens, so a stolen token is not valid for long. Check the `Session` class (not provided).

The screen looks the same after these changes.
**Source:** Android Developers, security risks "Insecure WebView native bridges" and "WebViews: unsafe URI loading" (developer.android.com/privacy-and-security/risks).

### F3 [High] Pro access is decided on the phone and never verified
**Status:** Verified in code.
**Where:** `app/PremiumManager.kt:3, 6-8, 16-19`
**Cause:**
- `isPro()` reads a local SharedPreferences boolean.
- `onPurchaseCompleted` sets it to `true` without checking `purchase.purchaseState`. That means a `PENDING` purchase (for example a cash payment that is never completed) grants Pro.
- There is no server verification, and nothing ever sets the flag back to false after a refund, cancellation or expiry.
- The Pro content itself (`lessons_pro`) is protected only by the `if` on the phone. The server serves it to anyone (F1).

**Attacks:**
- (a) Read `lessons_pro` directly through the API. This needs no phone at all while F1 is open.
- (b) On a rooted device or a modified APK, set `is_pro=true` in `shared_prefs`.
- (c) Buy, get Pro, refund, and keep Pro forever.

**Verify:**
- On a debug build: `adb shell run-as <package> cat shared_prefs/<file>.xml`, set `is_pro` to `true`, then force-stop and relaunch the app. If Pro lessons load, the finding is confirmed.
- After the F1 fix: logged in as a free test user, query `lessons_pro`. Expect `PERMISSION_DENIED`.

**Fix:**
- On purchase, send `purchaseToken` to a backend endpoint (a Cloud Function). It verifies the purchase with the Google Play Developer API (`purchases.subscriptionsv2.get` or `purchases.products.get`), acknowledges it, and writes the entitlement where only the server can write: a custom claim `pro=true`, or a server-only document.
- Gate `lessons_pro` in the rules on that entitlement (see the F1 rules).
- Use Real-time Developer Notifications to remove Pro on refund or expiry.
- Keep the local flag only as a display cache.
- Also check that purchases are acknowledged. Google Play refunds purchases that are not acknowledged within 3 days, and acknowledgement does not appear in the code you sent (Suspected, because that code may be elsewhere).

**Source:** Android Developers, "Fight fraud and abuse" / "Verify purchases before granting entitlements" (developer.android.com/google/play/billing/security) and "Integrate the Google Play Billing Library: process purchases" (developer.android.com/google/play/billing/integrate).

### F4 [High] Coupon redeem can be replayed and credits can be written freely
**Status:** Verified in code.
**Where:** `app/RedeemCode.kt:4-12`
**Cause:** the whole redeem runs on the phone as read, then check, then two separate writes. There is no transaction and no server involved:
1. **Race:** N parallel calls with the same code all read `used == false` before any of them writes `used = true`, so the credits are added N times.
2. **No need to race at all:** the client is allowed to `update("credits", ...)` on its own user document. An attacker skips the coupon and writes any credit balance. While F1 is open, they can write it to anyone's document.
3. **Coupon harvesting:** the coupon id is the code itself. With open rules the collection can be listed. With "read own" rules, short codes could still be guessed with `get` requests, and nothing limits the rate.
4. **Partial failure (Medium):** if step 10 succeeds and step 11 fails (network loss, app killed), the coupon is burned and the user gets nothing. The redeem also does not record who used the coupon.

**Verify:** use a test environment and test coupons only, because these are writes and I need your OK before running them. Call redeem 10 times in parallel with one code and count how many times credits were added. Expect exactly one.
**Fix:**
- Move redeem into a callable Cloud Function. It checks `context.auth`, then runs `runTransaction` that reads the coupon, checks `used`, sets `used`, `usedBy` and `usedAt`, and increments the user's credits atomically.
- Deny all client access to `coupons` and to the `credits` field (F1 rules).
- Use long random codes, and add App Check plus per-user rate limiting on the function.
- The app's `redeem()` then becomes one function call. The UI stays the same.

### F5 [Critical, availability / future risk] The app stops working on 2026-12-31
**Status:** Verified in code (`firestore.rules:5`).
**Cause:** `request.time < timestamp.date(2026, 12, 31)` means that from 31 December 2026 00:00 UTC every read and write is denied. Free lessons, sign-up data and redeem would all fail for every user. That is 44 days from today (2026-11-17), so likely within weeks of your launch.
**Fix:** this is resolved by the F1 rules, which have no date. Do not "fix" it by moving the date forward: that keeps F1 open.
**Verify:** after deploying, run the Firestore Rules Playground in the console with a simulated time after 2027-01-01, plus the emulator tests from F1.

### F6 [Info] Firebase API key in `app-config.json`
**Status:** Verified in code. The value is a placeholder in the file you sent.
A Firebase `AIza...` key is not a secret: it identifies the project and ships in every app. Security comes from the rules (F1) and App Check, not from hiding the key. Still:
- In Google Cloud Console > Credentials, restrict the key to your Android package and SHA-256 signing certificate, and to the Firebase APIs you use.
- Turn on **App Check** with Play Integrity for Firestore, Storage and Functions, so scripts outside your app are rejected.

**Verify:** call a Google API the key should not allow (for example Geocoding) from a shell with only the key. A normal result means the key is unrestricted.

## Fix order

1. **Today:** write and emulator-test the new Firestore rules (F1, F5), but do not deploy them alone.
2. **Same release:** Cloud Functions for redeem (F4) and purchase verification (F3), plus app changes that call them. Deploy functions, then rules, then publish the app build. Old builds still write credits from the phone and will fail redeem after the rules change, which is acceptable before launch.
3. **Same release:** fix HelpActivity (F2). At minimum remove the token bridge and use an exact host check.
4. Enable App Check and restrict the API key (F6).
5. Before launch: rotate any coupons that exist, and check whether any real user data was exposed while the rules were open.

**What must ship:** a Firestore rules deploy (backend owner), Cloud Functions (backend owner), and a new app build with the HelpActivity, Premium and Redeem changes (app team). Play Console needs Real-time Developer Notifications set up, and Google Cloud needs the key restrictions.
