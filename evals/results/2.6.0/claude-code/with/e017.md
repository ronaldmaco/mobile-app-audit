# Profile crash: what happened and the fix

Mode used: **F. Autopsy** (a crash already in production), then the fix loop (impact map, review gate, regression tests).

## Short answer

**Release 4.2.0 did not cause this crash.** A backend change on **2026-03-09** did. Since that date the Profiles API leaves out fields that are null. For users without a profile photo, the response now has no `avatar` key at all. Before, it sent `avatar: ""`. The app decodes the profile with `try!` (`ProfileStore.swift:23`), and `avatar` is a required `String`. So the response from that day on fails to decode, and `try!` turns the error into a crash. **4.1.0 crashes in exactly the same way.** I fixed it in the app and added regression tests. You also need to act on the backend, because users on builds that are already installed will keep crashing until they update.

### Why it is not 4.2.0 (try-to-refute pass)
- `git log v4.1.0..v4.2.0` has five commits: release, ProfileHeader avatar styling (corners and placeholder colour), Settings redesign, dark-mode icons, an analytics SDK minor bump. None of them touches `ProfileStore` or the `Profile` model. The ProfileHeader commit is the closest suspect. The crash frame is in the decoder on a background URLSession thread (Thread 3), before any UI runs, so that commit is not the cause.
- The crash group lists **4.1.0 (410)** too, and 4.1.0 crash-free users drop on the same day (99.8 to 96.1).
- 4.2.0 was stable for three days (03-06 to 03-08) before the drop.
- The only change dated 2026-03-09 is the Profiles API change, and its example names `avatar`, the exact key in the exception.
- One caveat: the CSV gives sessions only as low/medium/high, so I cannot give the number of affected users, only the crash-free percentage.

## Fix (app)

Two changes, both in `ProfileStore.swift`:
1. **A missing or null `avatar` decodes as `""`.** That is the value the app already used for "no photo" (see the existing test `testDecodesProfileWithoutPhoto`, and the ProfileHeader placeholder). The screen looks and behaves exactly as before the backend change. This does not hide anything from the user: the server is saying "no photo", and the app shows the no-photo placeholder, as it did before.
2. **No more `try!`, and failures are reported.** `loadProfile` now completes with `Result<Profile, Error>`. A response the app cannot decode, or a network error, reaches the caller as `.failure` instead of crashing or hanging. The caller should show the screen's existing error/retry state. No new design is needed.

**Call sites need a one-line change.** The completion type changed from `(Profile) -> Void` to `(Result<Profile, Error>) -> Void`. The callers are not in the files I received, so I could not update them. The compiler will list each one. The pattern is:

```swift
store.loadProfile(id: id) { result in
    switch result {
    case .success(let profile): self.show(profile)
    case .failure:              self.showLoadError()   // existing error/retry state
    }
}
```

### Regression tests

Before the fix, this test would crash the test run.

## Impact map

| Case | Expected | With the fix |
|---|---|---|
| `avatar` is a URL | photo shown | unchanged |
| `avatar: ""` (old contract) | placeholder | unchanged |
| `avatar` missing (current API, the crash) | placeholder | decodes as `""`, placeholder (test added) |
| `avatar: null` | placeholder | decodes as `""`, placeholder (test added) |
| `name` or `id` missing or null | honest error, no crash | `.failure`, error state. Not tested: is `name` ever null? Ask the API team (below) |
| Invalid JSON, or an HTML error page from a proxy | error, no crash | `.failure` (test added) |
| Network error or offline | error, no hang | `.failure` (before: completion never called, screen hung) |
| Other models from the same API | must accept omitted null fields | **Not checked: only `ProfileStore.swift` was provided.** Search the app for `try!` and for every `Decodable` with non-optional fields that the server can now leave out. The change applies to the whole Profiles API, and maybe to other endpoints. |
| Android / sibling apps | same | **Not checked (no code provided).** Any client that requires `avatar` (Kotlin non-null, Moshi/Gson strict adapters) has the same crash. |

## Backend action (needed even with the app fix)

The app fix only helps users who install the new build. Everyone on 4.1.0 and 4.2.0 keeps crashing until they update. The fastest way to stop the crash for **all** users is on the API side. **Owner: API team.**
- Send `"avatar": ""` again for users without a photo. Do the same for any other field older clients require. Either do this for every client, or only for requests from app versions up to 4.2.x (based on the version header or User-Agent).
- Before omitting fields again, check the change against the shipped app models (a shared fixture or contract test), and announce it before deploying.
- Confirm which Profile fields can be null (`name` especially) so the app model matches the real contract.

## Prevention (proposed, not done)
- Never use `try!` or force-unwrap on server data. Add a lint rule (SwiftLint `force_try`).
- Keep one decoding test per API model that uses a real response where null fields are left out.
- Add a contract test or shared fixture between the API and the app, so a change in the response shape fails in CI before it ships.
- Watch crash-free users per app version **and** next to the backend deploy log. A drop that hits every version on the same day points to the server, not the release.
