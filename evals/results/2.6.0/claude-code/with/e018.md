# Will the Android app keep working for 12 months if nothing changes?

Mode: **G, Future risk**. The window is 2026-11-17 to 2027-11-17. I worked only from the files in `app/` and from official pages, which I read on 2026-11-17. I could not build or run the app, so none of this was reproduced on a device.

## Short answer

**No.** If nothing changes, the app breaks in two ways within the next 3 months. On top of that, Google Play already blocks updates today:

1. **From 2027-01-01, the app crashes every time the Home screen opens.** This happens on every installed copy, with no server involved. It is a hard-coded date in `PromoBanner.kt`.
2. **Around 2027-02-02, the app may lose all access to your API.** The app pins the public key of the current server certificate, with no backup pin. That certificate expires then. Your hosting provider renews it automatically and "may issue a new key". If the key changes, every installed copy rejects the server until 2028-01-15.
3. **You cannot ship a fix today without more work.** Google Play has accepted updates only from apps targeting API 36 since 2026-08-31, and the extension ended on 2026-11-01. The app targets API 34. Any release, including the fixes for points 1 and 2, needs the target API raised first.

Also, since 2026-08-31 the app is **no longer offered to new users on Android 15 and newer devices**. People who already installed it keep it.

The deadlines leave about 6 weeks before the first crash. One release has to carry the target API change and both fixes, and it has to get through Play review before 2027-01-01. Users who don't update will still crash after 2027-01-01. You can't prevent that on old builds; the only fix is getting people onto the new release.

## What I recommend, in order

**This week (decide on the release plan):**
1. **Ask the hosting provider to keep the same key pair when they renew `api.example.com`**, or to tell you the exact renewal date and whether the key will change. This is the only step that protects builds already installed on phones from risk #3. Then check it after each renewal:
   `openssl s_client -connect api.example.com:443 -servername api.example.com </dev/null 2>/dev/null | openssl x509 -pubkey -noout | openssl pkey -pubin -outform der | openssl dgst -sha256 -binary | base64`
   The output must equal the `<pin>` value in `network_security_config.xml`.
2. **Start the target API 36 migration now** (risk #1). Without it, nothing else can ship. Raise `compileSdk` and `targetSdk` to 36 and update AGP and `core-ktx` to match. Then work through the Android 15 and Android 16 behaviour-change pages (edge-to-edge is enforced, among others). Pay special attention to chartkit and paylib screens. Verify with `./gradlew lint` (no `OldTargetApi`), `./gradlew build --warning-mode all`, and a full test on an Android 16 emulator.

**In the same release (it must be live on Play well before 2027-01-01):**
3. **PromoBanner (risk #2):** after the end date, return no banner and hide the view instead of throwing. Add a unit test that calls `bannerText(LocalDate.of(2027, 1, 1))` and expects no exception. Better still, have the server send promo dates so the next promo needs no release.
4. **Pinning (risk #3):** add at least one backup pin, such as the key of the CA's intermediate certificate or a spare key the hosting provider holds for you. Choose an `expiration` that fits a twice-a-year release rhythm. Test it with a certificate that uses a different key, for example in a staging environment.
5. If your project has a forced-update mechanism, use it so that people move off the builds that crash.

**Before 2027-06-30:**
6. Plan the paylib 4 upgrade (risk #5) and decide whether to drop Android 6 (minSdk 24). Re-read the vendor's support page first to confirm the date.
7. Replace or take ownership of chartkit (risk #6).

## Not verified / limits
- I did not build or run the app, and I did not run lint, Gradle, `openssl` or `osv-scanner`. The certificate date, the chartkit status and the paylib dates come from your `maintenance-notes.md`, not from my own checks.
- I saw only `build.gradle.kts`, `PromoBanner.kt`, `network_security_config.xml` and the notes. I did not check the manifest, the other source files, the version catalog or the native libraries, so other risks may exist. Examples: 16 KB page-size alignment applies once you target 35 or higher if any library ships native code; foreground service types; other hard-coded dates. Run `grep -rnE '20[2-9][0-9]' app/src` across the whole codebase and `zipalign -c -P 16 -v 4` on the release APK during the migration.
- The rules come from official pages read on 2026-11-17. Google changes them every year, so re-read developer.android.com/google/play/requirements/target-sdk before you plan dates for 2027.
