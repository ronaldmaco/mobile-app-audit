# Is 3.1 ready for App Store submission tomorrow?

**Short answer: no.** The two things that most likely caused the 2.1 rejection ("unable to sign in or reach any content") are still there. A map crash fix doesn't address either of them. There are also a few other issues that would probably get the next build rejected. Most of them are quick fixes, but two need someone from backend/ops, not just the iOS team.

I reviewed only the files you sent (`Info.plist`, `LoginView.swift`, `SettingsView.swift`, `AvatarPicker.swift`, `release-notes.md`). I could not run the app, so everything below comes from reading code and config. I list what I could not verify at the end.

---

## Blockers: the 2.1 rejection will happen again

### 1. App Review cannot finish logging in (SMS code goes to your team's phone)
`release-notes.md` says logging in with the demo account sends a one-time code by SMS to the account's phone number, and that number belongs to a team member. The reviewer has the email and password but never sees the code, so they get stuck at the code step. That matches "unable to sign in" exactly.

**Fix (choose one):**
- Turn off the SMS step for the review account only, on the server side (an allow-list flag on that account), or
- Give that account a fixed code that never changes and put it in the App Review notes, or
- Use a demo mode that needs no second factor.

Apple asks for a working demo account, or a fully featured demo mode, with everything the reviewer needs to sign in. See App Review Guideline 2.1 and the App Review Information section in App Store Connect: https://developer.apple.com/app-store/review/guidelines/#app-completeness

**How to verify:** on a fresh device, sign out, log in with the exact credentials from the review notes, and confirm you get to content without touching anyone's phone.

### 2. Your CDN blocks Apple's reviewers by country
The edge rule for `api.example.com` uses an allow list of `PE, CL, MX` and returns `block_403` to every other country. App Review usually tests from the United States, though you shouldn't count on any particular country. Every API call from the reviewer gets a 403, so even a working login could not load any content. This alone can explain the rejection, and it's the most likely main cause.

**Fix (choose one):**
- Allow the US, or better, every country in the App Store territories you've selected, on the API host, or
- Exempt the login and content endpoints from the geo rule. You can keep geo restrictions on the content itself if that's a business or licensing requirement, but then the app has to show a clear message instead of failing with a 403.
- Also check that the app is only on sale in the territories you actually serve (App Store Connect → Pricing and Availability). Even then, the reviewer still has to be able to reach your backend.

**How to verify:** from a US exit point (a VPN or a US cloud machine), run
`curl -sI https://api.example.com/<login-endpoint>`
and confirm you get something other than a 403. Better still, run the app through a US VPN and log in with the demo account.

### 3. The build number has to change
`Info.plist` still says `CFBundleShortVersionString 3.1` / `CFBundleVersion 42`. That's the exact build that was rejected, and the notes say TestFlight already shows 3.1 (42). App Store Connect will not take a second upload with the same build number for the same version, so the map fix can't reach Apple as build 42.

**Fix:** bump `CFBundleVersion` to 43 or higher, archive, upload, and select the new build for the 3.1 version in App Store Connect. Keeping 3.1 as the version is fine.

**How to verify:** confirm App Store Connect → TestFlight lists 3.1 (43) as processed and that this build is the one attached to the submission.

## Other rejection risks to fix before submitting

### 4. Google login without an equivalent privacy-focused option (Guideline 4.8)
`LoginView.swift` offers "Continue with Google" to create and sign in to the main account. Guideline 4.8 says that if you use a third-party or social login for the primary account, you must also offer another login option that limits data collection to name and email, lets users keep their email private, and doesn't track them for ads without consent. Email and password with your own account doesn't count as that option. Sign in with Apple is the standard way to meet it.
Source: https://developer.apple.com/app-store/review/guidelines/#login-services

**Fix:** add Sign in with Apple next to the Google button, with its entitlement and backend token-verification.
**How to verify:** search the project for `ASAuthorizationAppleIDProvider` / `SignInWithAppleButton`. Right now there's none in these files.

### 5. Account deletion only through "email our support team" (Guideline 5.1.1(v))
`SettingsView.swift` has a "Delete account" button, but it opens a generic contact page and the footer says "To close your account, email our support team." Apps that support account creation must let users *initiate* deletion inside the app. A link to a web page is allowed only if that page goes straight to completing the deletion. A general contact form or an email to support is the pattern Apple rejects.
Sources: https://developer.apple.com/app-store/review/guidelines/#data-collection-and-storage and https://developer.apple.com/support/offering-account-deletion-in-your-app/

**Fix:** add an in-app flow: confirm the deletion, call a delete-account endpoint, sign the user out. If you have to keep a web flow, link directly to a page where a signed-in user can complete deletion. For Sign in with Apple users, also revoke their tokens through the Sign in with Apple REST API.
**How to verify:** with a test account, start deletion from Settings and confirm the account is actually gone or scheduled for deletion, with no email needed.

### 6. Vague camera permission text (Guideline 5.1.1)
`NSCameraUsageDescription` is just `Camera`. Apple requires purpose strings that explain clearly why the app needs the data, and one-word strings are a common rejection reason.
Also, the only image code I can see (`AvatarPicker.swift`) uses `PHPickerViewController`, which needs neither camera nor photo-library permission. If nothing else in the app uses the camera, delete the key.
**Fix:** either remove the key, or write a real sentence such as "Studio Finder uses the camera so you can take a photo for your profile picture."
**How to verify:** search the whole project for `AVCaptureDevice`, `UIImagePickerController` with `.camera`, or any barcode scanner SDK. If there are no hits, remove the key.

The location purpose string is fine.

## Before you click Submit
1. Fix the CDN rule (2), then test from a US network.
2. Remove the SMS step for the review account, or give it a fixed code (1). Update the review notes so they include the exact credentials and any code.
3. Add Sign in with Apple (4) and in-app account deletion (5). Fix or remove the camera string (6).
4. Bump the build to 43 or higher (3), upload it, and wait for processing.
5. In the App Review notes, explain briefly what changed since the rejection, for example: "Login no longer requires SMS for the demo account; backend is now reachable from all regions." Reviewers do read this.
6. Run a full smoke test on the uploaded build via TestFlight, on a US network, with the demo account: log in → reach content → open the map → delete account (on a throwaway account).

**Realistic timeline:** items 1–3 and 6 can be done in a day if backend/ops is available. Sign in with Apple and in-app deletion (4, 5) take more work, because they touch the backend. If you submit tomorrow without them, expect another rejection, possibly under 4.8 or 5.1.1(v) this time instead of 2.1. My recommendation is to move the submission back a day or two and send it once, clean.
