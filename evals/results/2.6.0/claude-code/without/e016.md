# Pre-launch security review: Android app (Kotlin + Firebase)

**Scope and limits.** I reviewed the five files you sent: `firestore.rules`, `app-config.json`, `HelpActivity.kt`, `PremiumManager.kt`, and `RedeemCode.kt`. I could not run the app or reach your Firebase project. That means I can't confirm that the rules file here matches what is **deployed**. I also didn't see Storage rules, Realtime Database rules, Cloud Functions, the `AndroidManifest.xml`, or the full billing code. Each finding below names the file it comes from and gives a way to confirm it on your side.

## Short answer

Right now, anyone who installs your APK can read, change or delete **every document in your database**, including all users, all coupons, and all paid lessons. They don't need an account or any special tooling. They can also give themselves Pro and unlimited credits. A crafted link can also steal a logged-in user's session token. Fix the four items below before launch, in this order:

| # | Severity | Issue | What an attacker does |
|---|----------|-------|-----------------------|
| 1 | Critical | Firestore rules allow anyone to read and write everything (until 31 Dec 2026) | Dumps or deletes the whole database, edits any user's data |
| 2 | Critical | Help WebView gives the auth token to any page that passes a weak URL check | Steals a user's session (account takeover) through one link |
| 3 | High | Pro status is decided only on the device and never verified | Gets Pro for free; paid content can be read even without the app |
| 4 | High | Coupon redemption runs on the client with no atomicity | Redeems one code many times, lists all codes, sets own credits |
| 5 | Medium | Firebase config and API key ship in the app | Not a secret by itself, but it is what makes 1, 3 and 4 trivial |
| 6 | Ops | The rules expire on 31 Dec 2026 | Fixing them "by date" makes the app stop working on 1 Jan |

## 1. Critical: the Firestore rules are open to the world

`app/firestore.rules`:

```
match /{document=**} {
  allow read, write: if request.time < timestamp.date(2026, 12, 31);
}
```

This is Firebase's "test mode" template. Until 31 Dec 2026, it lets **any** request, including unauthenticated ones, read, create, update and delete **any document in any collection**. The project ID and API key are inside every copy of the APK (see #5), so an attacker only needs to unzip the app.

**What an attacker can do**
- Download every user document, plus any personal data stored in it.
- Read `coupons` and take every unused code.
- Read `lessons_pro` without paying.
- Set `credits` or any other field on any user, including their own.
- Delete or overwrite whole collections. That is a full data-loss event, and you have no audit trail.

**There is a second problem: a time bomb.** Today is 17 Nov 2026. On 31 Dec 2026, every read and write is denied and the app stops working for everyone. You can't fix this by extending the date. You have to replace the rules.

**How to verify (on your side)**
- Firebase console → Firestore → Rules: check what is actually deployed. The console also warns about insecure rules.
- From any machine, with no login, run the request below. A 200 response with documents confirms that the data is publicly readable:
  `curl "firestore.googleapis.com/v1/projects/<project id>/databases/(default)/documents/coupons?key=<api key>"`
- Check Storage rules (`storage.rules`, for the `storage_bucket` in your config) and Realtime Database rules if you use them. I didn't receive them, and they are often left in test mode too.

**Fix**: default deny, with explicit rules per collection. Here is a starting point, to be adapted to your real schema:

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    match /lessons_free/{id} {
      allow read: if request.auth != null;
      allow write: if false;                       // admin / backend only
    }

    match /lessons_pro/{id} {
      allow read: if request.auth != null && request.auth.token.pro == true; // set by backend (see #3)
      allow write: if false;
    }

    match /coupons/{code} {
      allow read, write: if false;                 // only the backend touches coupons (see #4)
    }

    match /users/{uid} {
      allow read: if request.auth != null && request.auth.uid == uid;
      allow create: if request.auth != null && request.auth.uid == uid
                    && !request.resource.data.keys().hasAny(['credits', 'pro']);
      allow update: if request.auth != null && request.auth.uid == uid
                    && !request.resource.data.diff(resource.data).affectedKeys().hasAny(['credits', 'pro']);
      allow delete: if false;
    }
    // Anything not matched above is denied.
  }
}
```

Back the rules with tests in the **Firebase Local Emulator Suite**, using `@firebase/rules-unit-testing`. Cover at least these cases: unauthenticated read is denied, a user reading another user is denied, a user writing their own `credits` is denied, and a non-Pro user reading `lessons_pro` is denied. Then deploy with `firebase deploy --only firestore:rules` and repeat the `curl` check. It should now return 403.

Reference: Firebase, "Fix insecure rules" / "Avoid insecure rules": firebase.google.com/docs/rules/insecure-rules

## 2. Critical: session-token theft through the Help WebView (deep link)

`app/HelpActivity.kt`:

```kotlin
val url = intent.data?.getQueryParameter("page") ?: "https://help.example.com"
if (url.startsWith("https://help.example.com")) {
    webView.addJavascriptInterface(AccountBridge(this), "Account")
    webView.loadUrl(url)
}
...
@JavascriptInterface
fun authToken(): String = Session.current(context).accessToken
```

There are three separate problems here:

1. **The prefix check can be bypassed.** `startsWith("https://help.example.com")` also accepts URLs such as:
   - `https://help.example.com.<attacker domain>/steal`, where the host is `help.example.com.<attacker domain>`, which the attacker owns
   - `https://help.example.com@<attacker domain>/steal`, where the host is `<attacker domain>`
2. **The bridge is not tied to one origin.** `addJavascriptInterface` exposes `window.Account` to **every page and frame** loaded in that WebView. Even with a perfect URL check, the token leaks if any of these happen: a link or redirect on the help site leads elsewhere, the help site embeds a third-party iframe, or the help site has an XSS bug.
3. **What is exposed is the user's access token**, which is the most valuable thing the app holds.

**Attack.** The attacker sends a link by email, SMS, ad or web page: `myapp://help?page=https://help.example.com.<attacker domain>/x`. The victim taps it, the app opens, and the attacker's page runs `Account.authToken()` and sends the token to the attacker's server. That is account takeover with one tap. If the activity is exported for the `myapp://` scheme, any other app on the device can fire the same intent.

**How to verify**
- `AndroidManifest.xml`: check whether `HelpActivity` has an intent filter for `myapp://help` (which makes it exported).
- On a test device: `adb shell am start -a android.intent.action.VIEW -d "myapp://help?page=https://help.example.com.<attacker domain>/"`. Then confirm in Chrome remote debugging (`chrome://inspect`, with `WebView.setWebContentsDebuggingEnabled(true)` in a debug build) that `typeof Account` is `"object"` on that page.

**Fix (do all of these)**
- **Remove `authToken()` from the bridge.** Help pages should not need the user's token. If a help page truly needs to know who the user is, have the backend issue a short-lived, narrowly scoped ticket. Or open the help site in a Custom Tab with no bridge at all.
- **Validate the URL by parsing it**, not by comparing strings:
  ```kotlin
  val uri = Uri.parse(url)
  val allowed = uri.scheme == "https" && uri.host == "help.example.com" && uri.userInfo == null
  ```
- **Keep navigation on that host.** Override `WebViewClient.shouldOverrideUrlLoading` to block, or hand off to the browser, anything that is not `https://help.example.com`. If you keep any bridge at all, prefer `WebViewCompat.addWebMessageListener` with an explicit allowed-origin set, so that only that origin can call it.
- Don't enable JavaScript unless the help pages need it.

Reference: Android developers, WebView security / "Native bridges" risk guidance: https://developer.android.com/privacy-and-security/risks/insecure-webview-native-bridges

## 3. High: Pro access is decided only on the device and never verified

`app/PremiumManager.kt`:

- `isPro()` reads a boolean from `SharedPreferences`. On a rooted device or emulator, or with a patched APK, setting `is_pro=true` unlocks Pro. Patching `isPro()` to `return true` is a routine crack.
- `onPurchaseCompleted()` sets Pro for **any** `Purchase` object. It doesn't check the purchase state (`PURCHASED` versus `PENDING`), the product ID, or the signature. Nothing is checked on a server either.
- Paywalling `lessons_pro` in the app protects nothing. With the current rules (#1), anyone can download `lessons_pro` with `curl` without installing the app.
- I don't see the purchase being **acknowledged**. Google Play automatically refunds purchases that are not acknowledged within 3 days. Please check the rest of your billing code, because if this is missing you lose the revenue even from honest buyers. Reference: https://developer.android.com/google/play/billing/integrate#process

**Fix**
- Send `purchaseToken` to your backend, for example a Cloud Function. Verify it with the **Google Play Developer API** (`purchases.products` / `purchases.subscriptions`), acknowledge it, then record the entitlement on the server. Use a Firebase Auth custom claim such as `pro: true`, or a `users/{uid}` field that only the backend can write.
- Enforce Pro **in the Firestore rules** (see `lessons_pro` in #1), not in `LessonRepository`.
- Handle Real-time Developer Notifications so that refunds, cancellations and expirations revoke access.
- The local flag can stay as a UI cache, but never as the source of truth.

Reference: https://developer.android.com/google/play/billing/security

## 4. High: coupon redemption can be abused (double spend, enumeration, self-credit)

`app/RedeemCode.kt` does a read, then a check, then two separate writes, all from the client:

- **Race / double redeem.** Two devices, or two parallel calls, can both read `used == false` before either one writes `used = true`. Both then add the credits. This is easy to script.
- **No server authority.** With the current rules, the client can skip `redeem()` altogether. It can `update("credits", 999999)` on its own user document, reset `used` to `false` on a coupon, or create new coupons with any `credits` value.
- **Enumeration.** The coupon code is the document ID, so if `coupons` is readable or listable, an attacker gets every valid code.
- **Partial failure.** If the second write fails, the coupon is burned and no credits are given, and the user has no way to recover.

**Fix**
- Move redemption into a **callable Cloud Function**. It should check `context.auth`, then run a **Firestore transaction** that reads the coupon, checks `used` and any expiry or per-user limit, and in the same transaction sets `used = true` with `usedBy` and `usedAt` and increments the user's `credits`.
- Rules: no client access to `coupons`, and no client writes to `credits` (see #1).
- Use long random codes and add rate limiting (App Check plus per-user limits in the function) to slow brute-forcing.

**How to verify after the fix**: in an emulator test, fire two redemptions of the same code at the same time and assert that credits went up exactly once. Also try a direct client write to `users/{uid}.credits` and assert that it is denied.

## 5. Medium: the Firebase config and API key are in the app

`app/app-config.json` contains the project ID, the client API key (`AIza...`) and the bucket. This is **normal**: Firebase client API keys identify the project, they aren't secrets, and you can't hide them in an APK. The danger is #1, #3 and #4, because the security has to come from Rules and the backend, not from the key.

Defense in depth:
- Turn on **Firebase App Check** (Play Integrity provider) and enforce it for Firestore, Storage and Functions. This blocks most scripted traffic that doesn't come from your genuine app. It's an extra layer and **does not replace** correct rules.
- In Google Cloud Console → APIs & Services → Credentials, restrict this key to your Android package name plus SHA-1, and to the APIs it needs.
- Make sure no **server** secrets (service-account JSON, admin keys, third-party secret keys) are in the repo or APK. I didn't see any in these files. Scan the full project before release, for example with `gitleaks` on the repo and `apktool`/`jadx` plus a grep on the release APK.

Reference: firebase.google.com/docs/projects/api-keys

## What to fix first (launch blockers)

1. **Today:** replace `firestore.rules` with default-deny rules per collection, test them in the emulator and deploy. Re-run the `curl` check. Check Storage and Realtime Database rules too. This one change closes most of the damage from #1, #3 and #4.
2. **Remove the token from the WebView bridge** and validate the deep-link URL by parsed host (#2). Ship this in the same release.
3. **Server-side purchase verification and acknowledgement**, with Pro enforced in Rules (#3).
4. **Coupon redemption in a Cloud Function with a transaction** (#4).
5. **App Check plus API-key restrictions** (#5).

If the database has been in test mode while reachable from a public build, beta or internal test track, assume the data may already have been read. Check Cloud Audit Logs / Firestore usage for unexpected reads. Rotate any coupons that have not been used yet. Consider whether you have a breach-notification obligation for the personal data stored there.
