# Profile crash: what happened and the fix

## Short answer

**The crash was not caused by release 4.2.0.** A backend change on **2026-03-09** caused it. The Profiles API stopped sending `avatar` for users without a photo. The app has always crashed when that field is missing, so 4.1.0 crashes in exactly the same way. I fixed the app so it handles a missing or null `avatar` and can no longer crash on a profile response it doesn't expect.

## Evidence

1. **Crash report** (`crash-report.txt`): `Fatal error: 'try!' expression unexpectedly raised an error: DecodingError.keyNotFound(... "avatar" ...)` at `ProfileStore.loadProfile` (`ProfileStore.swift:23`). The same crash group shows up on **4.1.0 (410) and 4.2.0 (420)**, on both iOS 18 and iOS 26.
2. **Crash-free users** (`crash-free-users.csv`): both versions stayed at about 99.9% up to 2026-03-08. On **2026-03-09 both drop together**: 4.1.0 to 96.1% and 4.2.0 to 96.3%. 4.2.0 shipped on 03-06 and stayed stable for three days. A bug in the release would have hurt only 4.2.0, starting on its release day.
3. **Backend changelog** (`backend-changelog.md`), 2026-03-09: *"Profiles API: null fields are now omitted from responses … `avatar` is no longer sent for users without a photo (before: empty string)."* This matches the date and the missing key.
4. **What 4.2.0 changed** (`git-log.txt`, v4.1.0..v4.2.0): avatar corner rounding and a placeholder colour, the settings redesign, the icons and an analytics SDK bump. None of these touch `ProfileStore` or the decoding. The commit about avatars changed only how the avatar looks.
5. **Code**: `Profile.avatar` is a required `String`, and `loadProfile` decodes with `try!`. When the key is missing, decoding throws and `try!` turns that error into a crash. The existing tests only covered `"avatar": ""`, which is the old payload shape. They never tested a missing key.

**Who is affected:** users without a profile photo, on any app version, since 2026-03-09. "Some users" fits this group. Rolling back to 4.1.0 would **not** fix it.

## The fix (in `app/`)

- `Profile` now decodes `avatar` with `decodeIfPresent ... ?? ""`. A missing or `null` avatar becomes `""`, which the app already treats as "no photo". The UI and model type stay the same: the 4.2.0 placeholder still appears.
- `try!` is gone. A decoding or network failure now goes to a new `failure` callback on the main thread and is logged. The callback has a default value, so **existing call sites compile unchanged**. Callers can pass `failure:` to show an error state instead of a spinner that never stops.
- New tests cover the current backend payload (key omitted), `"avatar": null`, and a malformed payload that must throw instead of crash.

## Verification status

I couldn't build or run the app here, so **none of this has been compiled or run yet**. Before you ship:

1. Run `ProfileStoreTests` in Xcode (Product > Test, or `xcodebuild test -scheme <AppScheme> -only-testing:<TestTarget>/ProfileStoreTests`). The two new avatar tests fail on the old code (keyNotFound) and should pass with the fix.
2. On a device or simulator, open the profile of an account **without a photo** against the production API. The profile should load with the placeholder instead of crashing.
3. After release, confirm in the crash tool that crash group 1 drops to zero on the new build. Crash-free users for that build should go back to about 99.9%.

## Recommendations

- **Fastest relief, no app release needed:** ask the API team to send `"avatar": ""` again (or `null`) for profiles, at least for a while. This immediately stops the crash on the 4.1.0 and 4.2.0 builds already installed, which will stay in use until users update. The app fix protects future builds only.
- Ship the app fix as a 4.2.1 hotfix, and consider an expedited review.
- The backend change applies to **all** null fields, not just `avatar`. Search the app for other `try!` decodes and for required `Decodable` properties that could be null on the server, and make them optional or give them defaults. I only had `ProfileStore.swift`, so I haven't checked other models.
- Agree with the API team that removing or nulling a field is a breaking change. Old app versions stay installed for months, so tell the app team before such a change ships.
